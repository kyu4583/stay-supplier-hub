# stay-supplier-hub

여러 숙박 공급사의 상품을 하나의 검색 결과로 통합하는 백엔드입니다. 고객은 상품이 어느 공급사에서 왔는지와 무관하게 같은 형태의 결과를 봅니다.

## 로컬 실행

Java 25가 필요합니다. 저장소 루트에서 실행합니다.

시연 Mock A와 Mock B를 먼저 띄운 뒤 앱을 띄웁니다. Mock A는 9090, Mock B는 9091, 앱은 8080입니다. 단일 인스턴스 가정입니다.

```text
.\gradlew.bat :mock-a:bootRun
```

다른 터미널에서:

```text
.\gradlew.bat :mock-b:bootRun
```

세 번째 터미널에서:

```text
.\gradlew.bat bootRun
```

기본 포트는 8080입니다. 앱은 `http://localhost:9090`의 Mock A와 `http://localhost:9091`의 Mock B를 호출합니다.

숙소 목록을 수동으로 다시 받으려면 `POST /internal/mapping/sync`를 씁니다. 로컬 관리용이며 인증이 없습니다.

검색 예시:

```text
GET http://localhost:8080/api/v1/stays/search?checkIn=2026-09-20&checkOut=2026-09-23&adults=2&children=0
```

OpenAPI는 SpringDoc 기본 경로입니다.

- UI: http://localhost:8080/swagger-ui.html
- JSON: http://localhost:8080/v3/api-docs

## 연동의 성격

두 공급사는 같은 숙박 상품을 팔지만 표현이 다릅니다.

| 항목 | 공급사 A | 공급사 B |
|---|---|---|
| 요금 | 날짜별 1박 단가, 세금 별도 | 기간 전체 총액, 세금 포함 |
| 재고 | 날짜별 잔여 객실 수 | 같음 |
| 실패 표현 | HTTP 상태 코드 | 항상 200 + 본문의 결과 코드 |
| 조식 포함 여부 | 재고·요금 응답에만 있음 | 같음. 같은 객실이라도 공급사마다 값이 다를 수 있음 |

조회는 두 단계입니다. 공급사는 지역으로 검색해 주지 않고 **숙소 코드 목록을 받아** 재고·요금을 돌려줍니다. 그래서 어떤 숙소를 물어볼지 우리가 먼저 알고 있어야 하고, 숙소 목록은 미리 받아 내부 식별자와의 매핑으로 저장합니다.

숙소 목록은 자주 바뀌지 않고 재고·요금은 호출할 때마다 달라집니다. 이 성격 차이가 설계 전반을 가릅니다. 정적인 쪽은 미리 받아 두고, 검색 경로에서는 재고·요금만 호출합니다.

## 핵심 흐름

```
[사전] 공급사 숙소 목록 조회 → 내부 식별자로 매핑해 저장 → 메모리 스냅샷으로 올림

검색 요청 (날짜·인원)
  → 매핑 스냅샷에서 공급사별 숙소 코드를 꺼냄
  → 공급사별로 50개씩 묶어 병렬 조회
  → 공급사 응답 객체로 파싱 → 성공·실패 판정 → 표준 모델로 변환
  → 병합 (한쪽이 실패해도 나머지 결과로 응답)
  → 통합 검색 결과 + 결과가 빠진 공급사 목록
```

## 설계 결정 요약

| 결정 | 한 줄 이유 | 자세히 |
|---|---|---|
| 표준 요금은 세금 포함 기간 총액 하나 | 두 공급사에서 같은 뜻으로 정확히 얻을 수 있는 유일한 금액 | [도메인 모델](docs/domain-model.md) |
| 응답 구조는 숙소 → 객실 타입 → 오퍼 | 요금제나 공급사별 오퍼가 늘어도 구조를 바꾸지 않음 | [도메인 모델](docs/domain-model.md) |
| 연박 예약 가능 수는 날짜별 잔여 수의 최솟값 | 기간 내내 방이 있어야 예약할 수 있음 | [도메인 모델](docs/domain-model.md) |
| 예약 불가 상품도 0으로 노출 | "매진"과 "결과에 없음"을 구분할 수 있게 | [검색 API](docs/search-api.md) |
| 부분 실패는 실패한 공급사 목록으로 표현 | 어느 공급사 결과가 빠졌는지 드러나야 함 | [검색 API](docs/search-api.md) |
| 호출한 공급사가 모두 실패하면 503 | "조건에 맞는 숙소 없음"과 "검색을 못 함"은 다름 | [검색 API](docs/search-api.md) |
| MVC + 가상 스레드 + WebClient, 요청당 한 번만 대기 | 호출 사이의 동시성·시간 예산·부분 실패 수집을 Reactor가 계속 소유 | [아키텍처](docs/architecture.md) |
| 공급사별 어댑터 안에서 파싱 → 판정 → 변환 | 공급사 형식이 도메인으로 새지 않고, 파싱 실패와 변환 실패를 구분 | [아키텍처](docs/architecture.md) |
| 검색 전체 시간 예산 3초 | 호출별 제한만으로는 무응답 공급사에서 고객 대기가 누적됨 | [공급사 연동](docs/supplier-integration.md) |
| 규약을 어긴 항목은 보정하지 않고 제외 | 보정은 공급사의 의도를 추측하는 일 | [공급사 연동](docs/supplier-integration.md) |
| 숙소 목록은 기동 시·주기·수동·이벤트로 동기화 | 정적 데이터를 검색마다 받지 않기 위해 | [공급사 연동](docs/supplier-integration.md) |
| 같은 숙소를 공급사끼리 합치지 않음 | 위치 정보가 없어 같은 숙소임을 확정할 수단이 없음 | [범위 밖 설계](docs/deferred-design.md) |

## 무엇을 잃는지 알고 고른 것

- **공급사 A의 날짜별 요금과 세금 내역을 버립니다.** 표준 요금을 기간 총액 하나로 두었기 때문입니다. 살리면 A 상품에만 값이 있는 필드가 생겨, 고객이 공급사 차이를 보게 됩니다.
- **같은 숙소를 두 줄로 보여 줍니다.** 두 공급사가 같은 숙소를 팔아도 각각의 내부 식별자로 따로 노출됩니다.
- **규약을 어긴 항목은 결과에서 사라집니다.** 응답의 날짜가 요청 기간과 다르거나 값이 규약에 맞지 않으면 그 상품을 뺍니다. 고객에게는 없는 상품으로 보이고, 기록과 지표로만 드러납니다.

## 가정

1. 한 공급사의 한 응답에서 같은 (숙소 코드, 객실 타입 코드)는 한 번만 옵니다.
2. 공급사가 주는 금액은 고객 판매가입니다. 마진·수수료 구조는 다루지 않습니다.
3. 단일 인스턴스로 동작합니다. 인스턴스를 늘릴 때 필요한 조율은 [범위 밖 설계](docs/deferred-design.md)에 있습니다.
4. "오늘"의 기준 시간대는 Asia/Seoul입니다. 공급사가 위치 정보를 주지 않아 숙소 현지 날짜를 알 수 없습니다.
5. 공급사 코드 값은 안정적입니다. 같은 상품은 언제 조회해도 같은 코드로 옵니다.

## 정책값

아래 값은 측정으로 얻은 것이 아니라 정한 값입니다. 모두 설정으로 바꿀 수 있고, 실제 데이터를 본 뒤 조정할 대상입니다.

| 값 | 의미 | 정한 근거 |
|---|---|---|
| 3초 | 검색 한 건의 전체 시간 예산 | 검색 화면이 기다릴 수 있는 한도에서 역산 |
| 2초 / 1초 / 0.5초 | 호출별 응답 / 연결 / 커넥션 획득 대기 | 전체 예산 안에서 나눔 |
| 8 | 검색 한 건 안에서 공급사별 동시 호출 수 | 공급사 수용량을 모르는 상태의 초기값 |
| 6시간 | 숙소 목록 동기화 주기 | 정적 데이터이고 한 번 호출이 전체 목록임 |
| 3·10·30·90·270분 | 같은 코드로 동기화를 다시 시도하기까지의 대기 | 잠깐 늦은 반영은 앞 단계에서 따라잡고, 계속 어긋나면 호출이 빠르게 줄도록 |
| 30% | 목록이 이만큼 줄면 그 동기화를 반영하지 않음 | 공급사 쪽 결함으로 대량 비활성되는 사고 방지 |
| 30박 / 180일 / 36명 | 검색 요청의 상한 | 널리 쓰이는 숙박 앱의 검색 범위를 참고 |
