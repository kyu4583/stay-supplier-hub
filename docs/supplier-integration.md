# 공급사 연동

## 매핑 저장

공급사 코드와 내부 식별자의 매핑만 저장합니다. 재고와 요금의 원본은 공급사에 있으므로 쌓지 않습니다.

```
property
  id                     PK
  supplier               공급사
  supplier_property_code 공급사의 숙소 코드
  name                   숙소명
  active                 목록에서 사라졌는지
  last_seen_at           마지막으로 목록에서 확인한 시각
  unique (supplier, supplier_property_code)

room_type
  id                      PK
  property_id             FK → property.id
  supplier_room_type_code 공급사의 객실 타입 코드
  name                    객실 타입명
  max_occupancy           최대 인원
  active, last_seen_at
  unique (property_id, supplier_room_type_code)
```

- 객실 타입 코드는 숙소 안에서만 유일하므로, `(property_id, 코드)` 유니크 제약이 (공급사, 숙소 코드, 객실 타입 코드) 세 값을 표현합니다.
- **이 유니크 제약이 "같은 공급사 상품은 항상 같은 내부 식별자"를 보장하는 장치**입니다. 동기화는 이 키로 upsert하고, 동시에 두 번 들어와도 제약이 중복을 막습니다.
- 내부 식별자는 DB 시퀀스 숫자입니다. 같은 값이 돌아오는 것은 유니크 제약이 보장하므로 식별자 자체가 결정적일 필요가 없습니다. 공급사 코드를 조합한 문자열은 사실상 공급사 코드를 노출하는 것이라 쓰지 않습니다.
- 이름과 최대 인원을 함께 저장하는 이유는 재고·요금 응답이 그 값을 주지 않을 때의 기본값으로 쓰기 때문입니다.

## 숙소 목록 동기화

숙소 목록은 자주 바뀌지 않으므로 검색할 때마다 받지 않습니다. 검색마다 전체 목록을 받으면 검색이 느려지고 공급사 호출 한도를 씁니다.

| 계기 | 내용 |
|---|---|
| 기동 시 1회 | 매핑이 없는 상태로 검색을 받지 않기 위해 |
| 주기 (6시간) | 정적 데이터이고 한 번 호출이 전체 목록임 |
| 수동 | 공급사가 숙소 추가를 알려왔을 때 주기를 기다리지 않기 위한 관리용 경로 |
| 이벤트 | 매핑에 없는 객실 타입 코드가 재고·요금 응답에 왔을 때 |

### 실행 규칙

- 어느 계기든 검색 응답이 동기화를 기다리지 않습니다.
- 이미 동기화가 도는 중이면, 주기 계기는 건너뜁니다. 수동과 이벤트는 "갱신이 필요하다"는 신호이므로 건너뛰지 않고 **끝난 뒤 한 번 더** 돕니다. 돌고 있는 동기화는 신호가 오기 전에 목록을 받아 왔을 수 있기 때문입니다. 신호가 여러 번 와도 예약은 한 번으로 합칩니다.
- 한 공급사의 동기화(추가·수정·비활성 표시)는 **한 트랜잭션에서 커밋**합니다. 그래야 읽는 쪽이 갱신 전이나 후만 보고 중간 상태를 보지 않습니다.

### 매핑에 없는 코드가 응답에 왔을 때

그 검색의 응답에서는 해당 항목을 뺍니다. 내부 식별자가 없어 고객에게 돌려줄 수 없기 때문입니다. 동시에 그 공급사의 동기화를 요청해, 이후 검색부터는 포함되게 합니다.

검색 중에 응답 값으로 매핑을 바로 만들지 않습니다. 검색 경로에서 저장소에 쓰게 되어 동시 검색끼리 경합하고, 재고·요금 응답에 정적 정보를 주지 않는 공급사에서는 만들 수도 없습니다.

공급사의 두 API가 어긋나면(재고·요금 응답에는 있는 코드가 목록 API에 끝내 없으면) 검색마다 전체 목록을 받아오게 됩니다. 그래서 같은 코드로 다시 돌리기까지의 대기를 늘려 갑니다.

```
3분 → 10분 → 30분 → 90분 → 270분 → 이후 이벤트로는 돌지 않음
```

- 대기 상태의 키는 (공급사, 숙소 코드, 객실 타입 코드)입니다. 코드가 목록에 들어와 매핑이 생기면 상태를 지웁니다.
- 마지막 단계에서 이벤트 트리거가 멈춰도 주기 동기화는 계속 돕니다. 공급사가 나중에 목록을 고치면 그때 들어옵니다.
- 여러 코드가 동시에 신호를 내도 실행은 공급사 단위로 한 번입니다. 대기 판단만 코드별로 합니다.
- 단계가 올라갈 때마다 이상으로 기록합니다. 공급사 데이터가 어긋난다는 신호입니다.

### 목록에서 사라진 숙소

동기화에 성공한 목록에 없는 숙소·객실 타입은 바로 비활성으로 표시하고 검색 대상에서 뺍니다. **행을 지우지는 않습니다.** 지우면 같은 숙소가 다시 등록될 때 새 식별자가 부여되어 "항상 같은 식별자" 약속이 깨집니다.

목록이 비었거나 이전보다 크게 줄었으면(30% 이상) 그 동기화를 반영하지 않고 이상으로 기록합니다. 공급사 쪽 부분 장애나 목록 API 결함 한 번으로 대량 비활성되는 사고를 막기 위해서입니다.

### 검색이 매핑을 읽는 방법

검색은 메모리에 올린 스냅샷을 읽고, 동기화가 커밋된 뒤 스냅샷을 통째로 교체합니다.

- 갱신 중에 들어온 검색은 기다리지 않고 갱신 전 상태로 처리됩니다. 숙소가 추가되는 빈도가 낮고, 갱신 직전에 요청한 소수만 새 숙소를 한 주기 늦게 보게 됩니다.
- TTL은 두지 않습니다. 매핑이 바뀌는 시점이 동기화뿐이라 TTL은 근거 없는 지연만 만듭니다.

### 동기화가 실패하면

공급사마다 **매핑 준비 상태**를 둡니다. 한 번이라도 동기화에 성공해 유효한 매핑이 있으면 준비됨입니다.

- 준비되지 않은 공급사는 검색에서 빠진 공급사로 보고합니다. 호출도 못 한 것이니 결과가 빠진 것이 맞습니다.
- 기동 시 동기화가 실패해도 앱은 뜹니다. 이전에 저장된 매핑이 있으면 그대로 씁니다.
- 주기 동기화가 실패하면 이전 매핑을 유지합니다. 공급사 하나만 실패하면 그 공급사만 이전 상태로 둡니다.

## 실패 판정

공급사마다 실패를 알리는 방식이 다릅니다. 이를 하나로 모읍니다.

```
1단계  HTTP 상태     A는 2xx가 아니면 실패. B는 항상 200이라 여기서 성공으로 판정하지 않음
2단계  본문 봉투      B는 결과 코드가 성공이 아니면 실패, 데이터가 비면 실패
3단계  항목 검증      규약을 어기는 항목을 걸러냄
무응답  우리 타임아웃   공급사가 알려주지 않으므로 우리가 판정
```

- B가 200에 성공 코드인데 데이터가 비어 있으면 응답 이상으로 봅니다.
- A가 2xx인데 본문이 오류 형태면 파싱에서 걸리므로 역시 응답 이상입니다.
- 판정 자리는 어댑터 안의 파싱과 변환 사이입니다.

### 항목 검증

값을 보정하지 않고 그 항목을 뺍니다. 보정은 공급사의 의도를 추측하는 일입니다.

| 검증 대상 | 처리 |
|---|---|
| 날짜 목록이 요청 숙박일과 다름 | 항목 제외 |
| 음수 재고 | 항목 제외 |
| 최대 인원이 요청 인원보다 작음 | 항목 제외 |
| 음수·이상 금액, 모르는 통화 코드 | 항목 제외 |
| 같은 키가 두 번 옴 | 둘 다 제외 |
| 요청하지 않은 숙소 코드 | 항목 제외 |
| 매핑에 없는 객실 타입 코드 | 항목 제외 + 동기화 요청 |

제외한 항목은 지표와 기록에만 남기고 `failedSuppliers`에는 넣지 않습니다. 공급사는 정상 응답했고 데이터 일부가 규약을 어긴 것이기 때문입니다. **한 묶음의 항목이 전부 걸리면** 그 묶음을 실패로 봅니다. 비율 기준 같은 값을 정하지 않고도 쓸 수 있는 것이 없는 응답을 구분할 수 있습니다.

## 타임아웃

| 항목 | 값 | 걸리는 지점 |
|---|---|---|
| 검색 전체 예산 | 3초 | 공급사 호출 조합 전체 |
| 호출별 응답 | 2초 | 요청을 보낸 뒤 응답이 끝날 때까지 |
| 연결 | 1초 | 새 연결을 맺을 때만 |
| 커넥션 획득 대기 | 0.5초 | 풀에서 순서를 기다릴 때 |

공급사 응답 실측이 없으므로, 값의 근거는 검색 화면이 기다릴 수 있는 한도에서 역산한 것뿐입니다. 전체 예산을 먼저 정하고 나머지를 그 안에서 나눴습니다.

**호출별 제한만으로는 부족합니다.** 공급사가 무응답이면 묶음마다 2초를 기다리고, 동시 8개로 30묶음을 태우면 8초가 걸립니다. 전체 예산이 끝나면 남은 호출을 취소하고 그때까지 모인 결과로 응답합니다. 취소된 공급사는 빠진 공급사로 보고합니다. 이 지점이 부분 실패 허용이 실제로 동작하는 곳입니다.

값의 합(3.5초)이 예산보다 큰 것은 의도한 것입니다. 전체 예산이 마지막 방어선이고 나머지는 그보다 빨리 끊는 장치입니다.

## 신규 공급사 추가

공급사 식별자는 enum이 아니라 문자열을 감싼 값 객체입니다. 어댑터가 자기 식별자를 들고 있고 도메인은 어댑터 목록을 주입받아 순회하므로, 공급사가 늘어도 도메인은 바뀌지 않습니다. 설정에 없는 공급사나 중복된 식별자는 기동 시점에 검증해 실패시킵니다.

공급사별 설정 묶음: 기본 URL, API 키, 한 번에 보낼 코드 수, 타임아웃, 커넥션 풀 상한. 어댑터가 자기 것만 읽습니다.

추가할 때 하는 일은 다음이 전부입니다.

1. `supplier/<새 공급사>/` 패키지를 만든다
2. 응답 객체, 매퍼, 어댑터를 작성한다
3. 설정에 공급사 항목을 추가한다
4. Mock에 해당 공급사를 추가한다
5. 어댑터 변환 규칙과 연동 테스트를 작성한다

도메인, 검색 서비스, 응답 계약은 건드리지 않습니다.

## Mock 구성

실제 공급사가 없으므로 스펙대로 흉내 내는 Mock을 둡니다. 용도가 둘로 갈려서 수단도 나눕니다.

| 용도 | 방식 |
|---|---|
| 손으로 실행하고 장애를 재현 | 별도 모듈로 띄우는 Mock 서버 (다른 포트) |
| 자동 테스트 | 테스트 안에서 응답을 코드로 통제 |

시연용 Mock은 요청한 날짜와 숙소 코드를 반영해 응답합니다. 고정된 응답을 주면 위의 항목 검증에 걸려 결과가 비게 되는데, 규칙이 제대로 동작한 결과인데도 고장으로 보입니다. 정상 응답 외에 공급사 장애, 무응답, 지연을 재현할 수 있어야 하고, 숙소를 50개 넘게 만드는 옵션을 둬서 분할과 부분 실패가 실제로 도는 것을 보입니다.

테스트는 "묶음 일부만 실패", "응답 지연", "200인데 본문이 실패 코드" 같은 상황을 정확히 통제해야 하므로, 상태를 가진 공용 서버를 공유하지 않고 테스트 안에서 스텁을 세웁니다.
