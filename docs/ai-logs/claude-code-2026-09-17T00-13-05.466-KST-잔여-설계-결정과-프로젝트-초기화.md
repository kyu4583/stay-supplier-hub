````text
## 5. 매핑 스키마와 내부 식별자

요구사항 문서가 요구하는 것은 두 가지입니다.
- 공급사 코드와 자사 식별자의 매핑을 저장할 것. 숙소와 객실 타입 **두 단계 모두**.
- 같은 공급사 상품이 다시 조회되면 **항상 같은 내부 식별자**가 나올 것.

### 스키마 초안 (쟁점 아님)

공급사마다 내부 식별자가 따로인 기본 동작을 그대로 따른 모양입니다. 이름과 최대 인원은 2번에서 정한 덮어쓰기의 기본값으로 쓰려고 함께 저장합니다.

```
property
  id                     PK
  supplier               공급사
  supplier_property_code 공급사의 숙소 코드
  name                   숙소명
  unique (supplier, supplier_property_code)

room_type
  id                      PK
  property_id             FK → property.id
  supplier_room_type_code 공급사의 객실 타입 코드
  name                    객실 타입명
  max_occupancy           최대 인원
  unique (property_id, supplier_room_type_code)
```

객실 타입 코드는 숙소 안에서만 유일하니, `(property_id, 코드)` 유니크 제약이 (공급사, 숙소 코드, 객실 타입 코드) 세 값을 그대로 표현합니다. 이 유니크 제약이 "같은 상품은 항상 같은 내부 ID"를 보장하는 장치이고, 동기화는 이 키로 upsert합니다. 동시에 두 번 들어와도 제약이 중복을 막습니다.

### 쟁점 1. 내부 식별자를 무엇으로 할지

| 방식 | 얻는 것 | 잃는 것 |
|---|---|---|
| (가) DB 시퀀스 숫자 | 단순하고 인덱스가 작음 | 외부에 노출되면 전체 숙소 수와 증가 속도가 드러남 |
| (나) UUID | 노출돼도 수를 알 수 없음 | 인덱스가 크고, 무작위 UUID는 정렬이 흩어짐 (UUIDv7이면 완화) |
| (다) 공급사 코드로 만든 결정적 해시 | DB 없이도 같은 코드면 같은 ID | 코드 공간이 좁아 추측 가능. 코드가 바뀌면 ID도 바뀜 |
| (라) 코드 조합 문자열 (`A:A-10023`) | 만들기 쉬움 | 공급사 코드를 그대로 노출하는 셈이라, 자사 식별자를 주라는 요구와 어긋남 |

추천은 **(가)**입니다. 같은 ID 보장은 유니크 제약이 이미 해 주니 식별자 자체가 결정적일 필요가 없고, (다)의 단점(코드 변경 시 ID 변경)도 피합니다. (나)는 노출 관점에서 낫지만, 숙소 수가 드러나는 위험보다 얻는 게 적다고 봅니다.
````

```text
## 6. 숙소 목록 동기화

요구사항 문서는 매핑을 공급사의 숙소 목록 API로 만들라고 하고, **언제 호출할지를 직접 판단해 근거를 적으라**고 합니다. 이 항목의 핵심은 "숙소 목록은 자주 안 바뀌고 재고·요금은 매번 바뀐다"는 성격 차이를 설계에 어떻게 반영했는지입니다.

정할 것이 네 가지인데, 길어지니 두 개씩 나눠 보겠습니다. 뒤에 다룰 두 가지는 "사라진 숙소를 언제 비활성으로 볼지"와 "매핑을 검색마다 DB에서 읽을지 캐시할지"입니다.

### 쟁점 1. 언제 호출할지

| 방식 | 판단 |
|---|---|
| 검색할 때마다 | **제외.** 검색마다 전체 목록을 받아오면 검색이 느려지고 공급사 호출 한도를 씁니다. 정적 데이터를 매번 받는 것이라 이 항목이 요구하는 성격 차이 반영과 정반대입니다 |
| 앱 기동 시 1회만 | 부족합니다. 오래 떠 있는 프로세스는 갱신되지 않습니다 |
| 주기적으로만 | 첫 기동 직후 첫 주기까지 매핑이 비어 있습니다 |

추천은 **넷을 조합**하는 것입니다.
1. **기동 시 1회** — 매핑이 없는 상태로 검색을 받지 않기 위해
2. **주기적** — 제안값 6시간. 숙소 목록은 자주 바뀌지 않고, 한 번 호출이 공급사별 전체 목록이라 잦으면 낭비입니다. 설정값으로 빼고 측정값이 아님을 밝힙니다
3. **수동 트리거** — 공급사가 숙소를 추가했다고 알려올 때 주기를 기다리지 않기 위한 관리용 엔드포인트나 커맨드
4. **이벤트 트리거** — 2번 논제에서 정한 대로, 매핑에 없는 객실 타입 코드가 재고 응답에 오면 그 공급사 동기화를 요청

4번에 붙이자고 했던 조건도 여기서 확정하면 좋겠습니다.
- 검색 응답이 동기화를 기다리지 않게 합니다(요청과 분리해 실행).

- 동기화 후에도 코드가 목록에 없으면 최소 간격을 두고, 이상 신호로 기록합니다.
- 인스턴스가 여러 개면 각자 트리거합니다. 공유 락은 두지 않고, 위의 최소 간격으로 상한을 잡자고 제안합니다.
```

````text
### 판정 단계 (쟁점 아님)

```
````

```text
**읽기 타임아웃과 응답 타임아웃은 다릅니다.** 전통적인 socket timeout은 "바이트가 안 들어온 채 흐른 시간"이라, 조금씩 계속 흘려보내는 서버에는 안 걸립니다. Reactor Netty의 `responseTimeout`은 응답 전체가 끝날 때까지의 시간이라 이 구멍이 없습니다. 우리는 작은 JSON 하나를 받으니 후자가 맞습니다. 응답이 계속 흐르는 스트리밍이었다면 반대로 쓰면 안 됩니다.

**전체 예산은 클라이언트 설정이 아니라 우리 설계입니다.** 앞의 셋은 호출 하나에 걸리는 값이고, 전체 예산은 호출 수십 개를 묶은 작업에 겁니다. 여러 곳에 부채살로 호출하는 서비스에서 흔한 패턴이고(gRPC의 deadline이 같은 개념), 앞서 본 "A 무응답이면 8초" 계산이 이게 없으면 생기는 일입니다.
```

```text
## 핀닝 수정 위치

말씀하신 변경은 JEP 491(Synchronize Virtual Threads without Pinning)이고, **JDK 24에 들어갔습니다.** 25는 그걸 품은 첫 LTS입니다. `synchronized` 블록이나 `Object.wait()`에서 블로킹해도 캐리어 스레드를 붙잡지 않습니다. 다만 **네이티브 프레임(JNI) 안에서의 블로킹은 여전히 핀닝**됩니다. "핀닝이 전부 사라졌다"는 아니고, 가장 흔한 원인이 사라진 것입니다.
```

````text
## (나) WireMock 하나를 두 방식으로 쓰기

WireMock은 **응답 규칙을 JSON 파일로 두고 그 폴더를 가리켜 띄우는** 방식이 있습니다. 저장소에 이런 폴더가 생깁니다.

mock/
  mappings/                    ← 어떤 요청에 어떤 응답을 줄지
    a-hotels.json
    a-availability.json
    b-properties.json
    b-search.json

    a-availability-body.json
    b-search-body.json
```

`mappings/a-availability.json`은 이런 식입니다.

```json
{
  "request":  { "method": "GET", "urlPathEqualTo": "/a/v1/availability" },

}
````
