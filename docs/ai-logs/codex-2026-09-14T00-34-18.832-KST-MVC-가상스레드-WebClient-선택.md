```text
읽었습니다. 제 판단은 **당신의 마지막 핵심 반박은 타당하고, Claude는 잘못 세운 전제를 부분적으로 수정하면서 결론을 계속 방어하다가 논의를 흔들었습니다.** 마지막 답변은 방향이 나아졌지만, 그것까지 전부 정확하다고 받아들이면 안 됩니다.

확인한 Reactor Netty 공식 문서는 기본 `HttpClient.create()`의 공유 풀을 목적지별 활성 연결 최대 **500개**, 추가 획득 대기 최대 **1,000개**로 설명합니다. `max(16, CPU×2)`는 사용자 정의 `ConnectionProvider`의 기본 설정과 구분해야 합니다. 실제 버전과 생성 경로를 확인해야 하므로 이 프로젝트가 500개라고 확정할 수도 없지만, Claude처럼 16개를 당연한 출발점으로 삼을 수는 없습니다. [공식 연결 풀 문서](https://projectreactor.io/docs/netty/release/reference/http-client.html#_connection_pool)

또 최대 크기를 500으로 설정한다고 즉시 공급사에 연결 500개를 여는 것도 아닙니다. **허용하는 최대치와 실제 점유량을 혼동했습니다.**

둘째, 설령 연결 16개·대기 32개가 실제 설정이어도, 그것만으로 “Tomcat 스레드는 최대 96개 정도만 묶인다”는 결론은 나오지 않습니다.

그 숫자는 특정 풀에서 연결을 사용하거나 획득을 기다리는 호출의 수입니다. 서버에는 그 외에도 다음 상태의 검색이 있습니다.

- DB를 조회하거나 DB 연결을 기다리는 검색
- 재시도 간격을 기다리는 검색
- 결과를 병합하거나 응답을 전송하는 검색

검색 하나가 여러 공급사 호출을 만들기도 합니다. **공급사 호출 수와 사용자 검색 수를 같은 단위처럼 계산한 것**이 더 근본적인 오류입니다.

예를 들어, 대기열과 기타 처리 시간을 무시하고 검색 초당 100건, 검색마다 A·B를 각각 한 번씩 병렬 호출하며 둘 다 2초 걸린다고 가정하면:

| 자원 | 평균 점유량 |
|---|---:|
| 진행 중인 검색 | 약 200건 |
| A 연결 | 약 200개 |
| B 연결 | 약 200개 |
| 동기 MVC에서 요청을 처리하는 스레드 | 약 200개 |

이것은 계산을 설명하기 위한 가정입니다. 청크 수와 지연이 달라지면 관계도 달라집니다. 평균 점유량이 곧 충분한 풀 크기를 의미하지도 않습니다.

따라서 당신의 “아웃바운드 풀도 목표에 맞춰 늘릴 수 있는데 왜 제외했느냐”는 반박에 동의합니다.

**다만 당신의 주장에서도 구분할 부분은 있습니다**

“관측되지 않은 공급사 한도를 지어내어 우리 처리량을 낮추면 안 된다”에는 동의합니다. 그런데 이것이 “429를 보기 전에는 동시성을 제한할 근거가 없다”로 확장되면 동의하지 않습니다.

우리 메모리, DB 처리 능력, 응답 시간 목표도 제한의 근거입니다. 이는 공급사의 가상적인 한도와 별개입니다.

또 “실제 병목 지점에서 실패해야 원인 추적이 쉽다”는 관점은 이해하지만, 항상 좋은 정책은 아닙니다. 이미 과부하를 알 수 있다면 앞에서 거절하여 DB 조회와 객체 할당 비용을 아낄 수 있습니다. 원인 추적은 단계별 대기 시간과 포화 지표로 확보하면 됩니다.

여기서 중요한 구분은 **스레드 모델과 수용량 정책을 따로 선택하는 것**입니다. 플랫폼 스레드 풀의 상한은 실행 동시성을 제한하지만, 그것만으로 적절한 과부하 정책이 완성되지는 않습니다. 가상 스레드나 WebFlux를 선택해도 필요한 제한은 명시적으로 둘 수 있습니다.

**제가 특히 보강하고 싶은 것은 Reactor의 제한 범위입니다**

대화에서는 `flatMap(call, 8)`이 여러 문제를 해결하는 것처럼 반복해서 등장했습니다. 하지만 검색마다 별도 체인을 만들면 이 8은 **검색 한 건 안의 동시성**입니다. 검색 100건이면 최대 800개의 내부 호출 구독이 생길 수 있습니다. 공급사 전체에 걸리는 제한과는 다릅니다. [Reactor `flatMap` API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html)

Reactor가 조합 가능한 도구를 제공한다는 당신의 선택 근거는 타당합니다. 다만 제한을 어디에 적용하고, 전체 시간 초과 때 이미 받은 결과를 어떻게 보존할지는 여전히 설계해야 합니다. 연산자가 정책까지 대신 정해 주지는 않습니다.

**그렇다면 제 선택은 무엇인가**

현재 설명된 검색 흐름에서 **DB 매핑을 JDBC로 다룬다면, 저는 MVC + 가상 스레드 + WebClient를 우선 선택하겠습니다.**

이유는 역할이 분명하기 때문입니다. DB 조회와 일반 업무 처리는 명령형 코드로 두고, 여러 공급사 호출의 병렬 실행·실패 처리·취소는 Reactor에서 조합합니다. 요청 경계에서는 가상 스레드 하나가 최종 결과를 기다립니다. 이때 가상 스레드는 호출을 병렬화하는 수단이 아니므로 제어를 이중으로 구현하는 구조도 아닙니다.

이 추천은 “WebFlux보다 빠르다”는 주장이 아닙니다. **동기 DB 처리와 비동기 외부 호출을 함께 쓰는 구성에 잘 맞는 선택**이라는 판단입니다. Spring 공식 문서도 blocking 영속성 API를 사용하는 일반적인 구조에서는 MVC를 권합니다. [Spring의 선택 기준](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html)

다만 아직 JDBC·JPA를 선택한 것이 아니라면, 이를 기정사실로 삼아 WebFlux를 제외시켜서는 안 됩니다. DB까지 리액티브로 구성하고 요청부터 응답까지 같은 모델로 연결하려는 선택도 충분히 타당합니다.

그 비교에서 Claude의 다음 설명은 바로잡아야 합니다.

- **“MVC에서는 blocking 실수가 그 요청에만 영향을 준다”**: WebClient 체인의 콜백에서 blocking하면 MVC에서도 이벤트 루프를 막아 다른 호출에 영향을 줍니다. [Spring 실행 모델 설명](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html)
- **“WebFlux에서는 JPA를 쓸 수 없다”**: 별도 실행 자원으로 격리하면 사용할 수 있습니다. 격리 비용과 복잡성을 따져야 하는 것이지 불가능한 조합은 아닙니다. [Spring 선택 기준](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html)
- **“가상 스레드를 켜면 WebFlux에 남는 이점은 취소뿐이다”**: 요청·응답 I/O와 스트리밍 처리 방식에도 차이가 남습니다. 가상 스레드가 그 구조를 동일하게 만들지는 않습니다. [MVC 비동기 처리와 WebFlux 비교](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)

마지막 답변의 “TIME_WAIT는 아웃바운드 전용”도 틀렸습니다. 서버가 인바운드 TCP 연결을 능동 종료해도 발생할 수 있습니다. 아웃바운드의 임시 포트 제약과 구분해야 합니다. [TCP 표준](https://www.rfc-editor.org/rfc/rfc9293.html)

제 의견에서 가장 중요한 것은, **현재 증거로 플랫폼 스레드를 고수해야 할 강한 이유는 없지만, 그것만으로 WebFlux까지 불필요하다고 결론낼 수는 없다**는 점입니다. 풀 기본값 비교는 버리고, DB 접근 방식과 요청 전체를 어떤 실행 모델로 표현할지에서 선택을 이어가는 편이 맞습니다.
```

```text
세 경우를 비교하려면 먼저 **“연결을 몇 개 유지하는가”, “요청을 몇 건 진행하는가”, “코드를 실행하는 스레드가 몇 개인가”를 구분해야 합니다.** 이전 대화는 이 세 숫자를 섞으면서 잘못된 결론으로 이어졌습니다.

설명은 우선 HTTP/1.1을 기준으로 하고, HTTP/2의 차이는 뒤에서 짚겠습니다.

**먼저 연결과 스레드의 관계**

커넥션은 데이터를 주고받는 통로이고, 스레드는 코드를 실행하는 주체입니다.

공급사에 요청을 보낸 뒤 응답까지 2초가 걸린다고 하면:

- **커넥션:** 그 교환이 끝날 때까지 사용 중입니다.
- **Netty 이벤트 루프 스레드:** 전송·수신·콜백 처리 때 실행하고, 응답을 기다리는 동안에는 다른 연결을 처리합니다.
- **동기 MVC 요청 스레드:** `.block()`으로 기다린다면 그 2초 동안 해당 요청에 붙잡혀 있습니다.

따라서 **Netty가 절약하는 것은 대기 중인 요청마다 필요한 스레드이지, 요청마다 사용하는 커넥션이 아닙니다.**

---

**1. Tomcat으로 사용자 요청을 동시에 많이 받는 경우**

여기에는 서로 다른 상한이 있습니다.

| 설정·자원 | 제한하는 대상 | 의미 |
|---|---|---|
| `maxThreads` | 요청 처리용 플랫폼 스레드 수 | 동기 요청을 동시에 처리할 실행 자리 |
| `maxConnections` | Tomcat이 받아 유지하는 연결 수 | 처리 중인 요청뿐 아니라 유휴 연결 등도 포함 |
| `acceptCount` | OS의 연결 수락 대기열 | 연결 수용이 밀렸을 때 신규 연결이 기다리는 공간 |
| CPU·메모리·DB 등 | 실제 처리 능력 | 위 설정까지 도달하기 전에 병목이 될 수도 있음 |

Tomcat 10.1의 기본 내부 실행기를 기준으로 `maxThreads` 기본값은 200입니다. **이는 “TCP 연결을 200개만 받는다”는 뜻이 아닙니다.** NIO 커넥터는 다음 요청을 기다리는 유휴 keep-alive 연결마다 워커 스레드를 붙잡아 두지 않습니다. [Tomcat HTTP Connector 문서](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)

예를 들어 연결이 1,000개 있어도, 그중 100개만 요청 처리 중이고 나머지는 유휴 상태일 수 있습니다.

반대로 동기 검색 200건이 전부 공급사 응답을 기다리면, 플랫폼 워커 200개가 모두 점유됩니다. 새 요청은 처리 자리를 기다려야 합니다. 다만 **201번째 요청부터 곧바로 `acceptCount`로 들어간다는 설명은 틀립니다.** 요청 처리 대기와 신규 TCP 연결 수락 대기는 구분해야 합니다. [Tomcat 연결·대기열 설명](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)

가상 스레드를 사용하면 이 관계가 달라집니다. Spring Boot의 내장 Tomcat에서 가상 스레드 처리를 활성화하면, 플랫폼 워커 풀 200개가 동기 요청의 실행 자리를 제한하는 구조에서 벗어납니다. 그래도 연결 수, 요청 상태를 보관하는 메모리, CPU, DB와 공급사 호출 용량은 남습니다. [Spring Boot 가상 스레드 지원](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-3.2-Release-Notes)

즉, 가상 스레드는 **많은 요청을 기다리게 하는 비용을 낮추지만, 그 요청들을 모두 성공시킬 처리 능력까지 늘려 주지는 않습니다.**

**2. WebClient의 Netty로 공급사에 동시에 많은 요청을 보내는 경우**

이쪽은 우리가 연결을 만드는 클라이언트이므로, **아웃바운드 커넥션 풀**이 등장합니다.

풀은 공급사에 연결을 매번 새로 만들지 않고 재사용하면서, 관리하는 연결의 최대 개수도 제한합니다.

| 설정 | 제한하는 대상 |
|---|---|
| `maxConnections` | 해당 풀의 최대 연결 수 |
| `pendingAcquireMaxCount` | 연결을 얻으려고 대기할 수 있는 요청 수 |
| `pendingAcquireTimeout` | 연결 획득을 기다리는 최대 시간 |

예를 들어 **설명용으로** 연결 최대 100개, 획득 대기 최대 200개를 설정했다고 합시다.

- 100개 연결이 모두 사용 중이면 추가 호출은 연결 획득을 기다립니다.
- 대기 공간까지 가득 차면 추가 획득 시도는 실패합니다.
- 대기 중에도 정해진 시간이 지나면 실패할 수 있습니다.

대기 중인 호출은 아직 공급사와 HTTP 교환을 진행하는 호출이 아닙니다. 따라서 **“연결 100 + 대기 200 = 공급사에 동시 300건 전송”은 아닙니다.** [Reactor Netty 연결 풀 문서](https://projectreactor.io/docs/netty/release/reference/http-client.html#_connection_pool)

HTTP/1.1의 일반적인 비파이프라이닝 사용에서는 연결 하나가 한 번에 교환 하나를 처리하므로, 연결 최대 100개는 해당 풀을 통한 동시 교환의 상한이 됩니다. 하지만 실제 동시 호출이 항상 100개라는 뜻은 아닙니다. 애플리케이션이 20개만 시작하면 20개이고, 다른 자원이 먼저 막혀도 그보다 적습니다.

또 풀은 기본적으로 **목적지 호스트·포트별**로 구분됩니다. A와 B가 같은 호스트·포트의 서로 다른 URL 경로라면, 경로만 다르다는 이유로 풀이 분리되지는 않습니다. [목적지별 풀 설명](https://projectreactor.io/docs/netty/release/reference/http-client.html#_connection_pool)

그리고 최대 연결 수는 조정할 수 있습니다. 늘렸을 때 실제로 감당 가능한지는 소켓·메모리·CPU·네트워크 자원과 공급사 응답 특성에 달렸습니다. 공급사의 알려진 제한이 있다면 그것도 고려하지만, **알 수 없는 제한을 임의로 가정할 필요는 없습니다.**

**3. WebFlux의 Netty로 사용자 요청을 동시에 많이 받는 경우**

인바운드에서는 사용자 쪽이 연결을 만들고 서버가 받아들입니다. 따라서 앞서 설명한 **WebClient의 아웃바운드 풀 크기가 인바운드에 적용되지는 않습니다.**

Netty 이벤트 루프가 4개라고 가정해도, 연결이나 진행 중인 요청을 4개만 유지한다는 뜻은 아닙니다. 각 루프가 여러 연결의 이벤트를 번갈아 처리하고, 응답 대기 상태는 메모리에 유지합니다. Reactor Netty의 기본 이벤트 루프 워커 수는 사용 가능한 프로세서 수를 기준으로 하며 최소 4개입니다. [Reactor Netty 서버 실행 모델](https://projectreactor.io/docs/netty/release/reference/http-server.html#_event_loop_group)

실제 상한은 다음 요소들이 결정합니다.

| 요소 | 무엇이 한계가 되는가 |
|---|---|
| 소켓·파일 디스크립터, 연결 관련 메모리 | 유지할 수 있는 연결 수 |
| 요청 객체·버퍼·결과 보관 메모리 | 진행 중인 요청을 쌓아 둘 수 있는 양 |
| 이벤트 루프·CPU 처리 능력 | 수신·파싱·변환·전송을 처리하는 속도 |
| DB·아웃바운드 연결 등 | 검색을 완료하는 데 필요한 후속 처리 능력 |
| 별도로 설정한 수용 제한 | 연결·요청을 어디까지 받아들일 것인지 |

이벤트 루프가 처리할 수 있는 양보다 일이 많이 생기면 이벤트 처리가 밀리고 지연이 늘어납니다. **스레드 수가 요청 수의 직접적인 상한이 아닌 것과, 스레드 처리 능력이 무한한 것은 전혀 다릅니다.**

또 인바운드 서버와 아웃바운드 클라이언트는 기본적으로 이벤트 루프 자원을 공유할 수 있습니다. 따라서 서로 다른 연결을 사용하더라도 CPU와 이벤트 처리 자원에서는 영향을 주고받습니다. **공유하는 것은 이벤트 루프이고, 인바운드와 아웃바운드가 하나의 커넥션 풀을 나눠 쓰는 것은 아닙니다.** [Reactor Netty 이벤트 루프 공유](https://projectreactor.io/docs/netty/release/reference/http-server.html#_event_loop_group)

**이전 커넥션 풀 오해는 이렇게 고치면 됩니다**

| 이전 이해 | 바로잡은 이해 |
|---|---|
| Netty는 기본적으로 연결 16개만 처리한다 | 풀 생성 경로에 따른 설정값이다. Netty 자체의 처리 한계가 아니다 |
| 이벤트 루프 방식이면 연결도 전송·수신 순간에만 점유한다 | 연결은 교환 동안 사용 중이고, 이벤트 루프 스레드가 대기에서 자유롭다 |
| Tomcat 200과 Netty 연결 16을 비교하면 병목 순서가 나온다 | 요청 스레드와 공급사 연결은 다른 자원이다. 검색당 호출 수와 점유 시간을 함께 봐야 한다 |
| 풀 최대치를 높이면 그만큼 연결을 즉시 연다 | 최대 허용치를 높이는 것이며, 실제 연결은 수요에 따라 만들어진다 |
| WebFlux에서는 인바운드도 같은 풀 제한을 받는다 | WebClient 아웃바운드 풀 제한은 인바운드에 적용되지 않는다 |
| 연결 수 제한은 초당 요청 수 제한이다 | 동시에 진행할 양을 제한한다. 초당 처리량은 교환 시간에도 달렸다 |

숫자 자체도 정정해야 합니다. 확인한 공식 문서에서 기본 `HttpClient.create()`는 목적지별 최대 연결 **500개**, 획득 대기 **1,000개**로 설명됩니다. `max(16, CPU×2)`는 사용자 정의 `ConnectionProvider`의 기본값과 구분해야 합니다. **500 역시 권장 설계값이나 실제 프로젝트의 확정값은 아닙니다.** [기본 생성 경로와 사용자 정의 풀의 차이](https://projectreactor.io/docs/netty/release/reference/http-client.html#_connection_pool)

마지막으로 HTTP/2에서는 한 TCP 연결에서 여러 요청을 스트림으로 동시에 처리할 수 있습니다. 따라서 이때는 연결 수에 더해 **연결당 동시 스트림 제한**까지 봐야 하며, “연결 100개니까 동시 요청 최대 100개”라는 관계도 성립하지 않습니다. [Reactor Netty HTTP/2 풀 설명](https://projectreactor.io/docs/netty/release/reference/http-client.html#_http_2)
```

[2026-09-14 03:07:58.149 KST] codex

````text
커넥션은 **양쪽 OS가 상태와 버퍼를 유지하면서 만들어 놓은 TCP 통신 관계**입니다. Netty가 미리 정해진 개수의 커넥션을 공급하는 것이 아니라, 필요할 때 OS에 연결 생성을 요청하고, 만든 연결을 풀에 보관해 재사용합니다.

따라서 “커넥션이 고갈됐다”는 말부터 두 가지로 나눠야 합니다.

- **풀 고갈:** 새 연결을 만들 여력은 있지만, 프로그램에 설정한 최대치에 도달했고 기존 연결도 모두 사용 중이다.
- **시스템 자원 고갈:** 설정을 늘려도 소켓·메모리·사용 가능한 주소/포트 등의 부족으로 새 연결을 만들 수 없다.

이 둘은 원인과 해결 방법이 다릅니다.

**커넥션 하나는 실제로 무엇인가**

예를 들어 우리 서버가 공급사에 연결하면 다음과 같은 관계가 만들어집니다.

```text
우리 서버                         공급사
10.0.0.10:51001  ←── TCP ──→  203.0.113.20:443
```

이 연결은 다음 네 값으로 구분됩니다.

```text
우리 IP + 우리 포트 + 상대 IP + 상대 포트
```

양쪽 OS는 이 연결에 대해 송수신 순서, 확인 응답, 재전송, 연결 상태, 버퍼 등을 관리합니다. 애플리케이션은 소켓을 통해 그 연결을 사용합니다. 그러므로 데이터를 보내지 않고 대기하는 연결도 자원을 사용합니다. [TCP 표준](https://www.rfc-editor.org/rfc/rfc9293.html)

같은 공급사에 연결을 하나 더 만들면 보통 우리 쪽 포트가 달라집니다.

```text
10.0.0.10:51001 ↔ 203.0.113.20:443   연결 1
10.0.0.10:51002 ↔ 203.0.113.20:443   연결 2
10.0.0.10:51003 ↔ 203.0.113.20:443   연결 3
```

**공급사로 나가는 커넥션은 어떻게 제공되는가**

WebClient가 HTTP 요청을 보내려고 할 때, 연결 풀은 대략 다음 순서로 동작합니다.

```text
재사용 가능한 연결이 있는가?
  ├─ 있다 → 그 연결을 빌려 준다
  └─ 없다 → 풀 최대치까지 더 만들 수 있는가?
               ├─ 있다 → OS에 새 연결 생성을 요청한다
               └─ 없다 → 연결 반환을 기다리거나 실패한다
```

새 연결을 만들 때는 로컬 소켓과 주소·포트를 확보하고, 상대방과 TCP 연결을 맺습니다. HTTPS라면 TLS 연결 설정도 필요합니다. 연결 풀은 이러한 생성 비용을 반복해서 지불하지 않도록 연결을 재사용합니다. [연결 생성 API](https://man7.org/linux/man-pages/man2/connect.2.html), [Reactor Netty 연결 풀](https://projectreactor.io/docs/netty/release/reference/http-client.html#_connection_pool)

HTTP/1.1의 일반적인 사용을 예로 들면, 연결 하나의 수명은 다음과 같습니다.

```text
연결 생성
  → 요청 1에 사용
  → 응답 본문까지 소비
  → 재사용 가능하면 풀에 반환
  → 유휴 상태
  → 요청 2에 재사용
  → …
  → 연결 종료
```

**풀에 반환하는 것은 연결을 끊는 것이 아닙니다.** TCP 연결은 살아 있고, 다음 요청이 그 연결을 빌릴 수 있게 되는 것입니다. 응답을 기다리는 동안에는 해당 연결을 다른 교환에 빌려줄 수 없습니다.

반대로 연결이 끊어졌거나 재사용할 수 없는 상태가 됐다면 풀에서 제거하고, 필요할 때 새 연결을 만듭니다.

**‘풀 최대 100개’에서 정확히 언제 고갈되는가**

최대 100개인 풀을 가정하면:

| 풀 상태 | 추가 요청이 오면 |
|---|---|
| 사용 중 30개, 유휴 20개 | 유휴 연결을 빌려 줌 |
| 사용 중 50개, 유휴 0개 | 최대치까지 여유가 있으므로 새 연결 생성 가능 |
| 사용 중 100개, 유휴 0개 | 반환을 기다려야 함 |
| 사용 중 100개, 획득 대기열도 가득 참 | 추가 획득 시도가 실패 |

여기서 마지막 두 상태는 **우리 OS가 101번째 연결을 만들 수 없다는 뜻이 아닙니다.** “이 풀에서는 100개까지만 관리하겠다”는 프로그램의 정책에 걸린 것입니다. [풀 최대치와 획득 대기](https://projectreactor.io/docs/netty/release/reference/http-client.html#_connection_pool)

공급사 응답이 느려지면 기존 연결이 오래 반환되지 않으므로 이런 상황이 더 쉽게 생깁니다. 풀 최대치를 늘리면 추가 연결을 만들어 더 많은 교환을 진행할 여지가 생깁니다.

그래서 이전에 **16개를 Netty의 고유한 한계처럼 다룬 설명은 틀렸습니다.** 16이든 500이든 풀 설정값이며, 설정을 높이는 선택지는 당연히 검토할 수 있습니다. 또한 최대치를 높였다고 그만큼 연결을 즉시 생성하는 것은 아닙니다.

**그러면 실제로 새 연결을 만들 수 있는 상한은 무엇인가**

풀 설정을 충분히 높여도 다음 자원은 유한합니다.

| 자원 | 연결과의 관계 | 부족하면 |
|---|---|---|
| 소켓 핸들·파일 디스크립터 | 프로세스가 연결마다 소켓을 관리해야 함 | 새 소켓 생성·연결 수락 실패 |
| 커널 메모리 | TCP 상태와 송수신 버퍼 등에 사용 | 연결 생성 또는 통신 처리에 문제 |
| 애플리케이션 메모리 | 연결 관리 객체, 버퍼, TLS 상태 등에 사용 | 메모리 압박·할당 실패 |
| 로컬 주소·임시 포트 | 아웃바운드 연결을 구분할 주소 조합 필요 | 새 아웃바운드 연결 생성 실패 |

예를 들어 Linux는 연결 수락 시 파일 디스크립터 한도나 메모리 부족으로 실패할 수 있고, 아웃바운드 연결 시 사용 가능한 임시 포트가 없으면 실패할 수 있습니다. [소켓 수락 오류](https://man7.org/linux/man-pages/man2/accept.2.html), [연결 생성 오류](https://man7.org/linux/man-pages/man2/connect.2.html)

여기서 포트는 특히 오해하기 쉽습니다.

**“포트가 약 6만 개니까 서버 전체 연결도 약 6만 개가 한계”는 아닙니다.** 연결을 구분하는 것은 네 값의 조합이기 때문입니다. 다만 **같은 로컬 IP에서 같은 목적지 IP·포트로 연결을 많이 만들면**, 구분에 사용할 로컬 포트 공간이 제한 요소가 됩니다. 목적지나 로컬 IP가 달라지면 가능한 조합도 달라지고, 실제 재사용 규칙은 OS와 소켓 설정에 영향을 받습니다.

연결을 자주 끊고 다시 만드는 경우에는 종료된 연결의 `TIME_WAIT` 상태도 관련됩니다. 애플리케이션이 소켓을 닫았다고 모든 TCP 상태와 주소 조합을 즉시 재사용할 수 있는 것은 아닙니다. **살아 있는 연결 수가 적더라도 연결 생성·종료가 매우 빈번하면 새 연결 생성에 압박을 줄 수 있습니다.** [TCP 종료와 TIME_WAIT](https://www.rfc-editor.org/rfc/rfc9293.html)

**사용자로부터 들어오는 커넥션은 어떻게 다른가**

우리 서버가 `:8080`에서 연결을 기다리는 경우입니다.

```text
사용자 A 198.51.100.1:53001 ↔ 우리 서버 10.0.0.10:8080
사용자 B 198.51.100.2:54002 ↔ 우리 서버 10.0.0.10:8080
사용자 C 198.51.100.3:55003 ↔ 우리 서버 10.0.0.10:8080
```

우리 쪽 포트는 모두 8080이어도 상대 주소가 달라 서로 다른 연결입니다. **사용자 한 명을 받을 때마다 서버가 새 리스닝 포트를 마련할 필요는 없습니다.**

서버는 하나의 리스닝 소켓으로 연결을 기다리고, 연결을 수락하면 그 사용자와 통신하는 별도 소켓을 얻습니다. 따라서 포트는 같아도 사용자 연결마다 소켓과 메모리는 필요합니다. [연결 수락 동작](https://man7.org/linux/man-pages/man2/accept.2.html)

- 서버가 설정한 연결 수용 상한
- 소켓·메모리 등 실제 자원 한도
- 신규 연결을 수락하는 속도와 수락 대기열

수락 대기열은 기존 연결의 재사용 풀이 아닙니다. 애플리케이션이 수락하기를 기다리는 신규 연결을 보관하는 공간이며, 가득 차면 연결 시도가 실패하거나 지연될 수 있습니다. [Linux 연결 수락 대기열](https://man7.org/linux/man-pages/man2/listen.2.html)

이 구조는 Tomcat과 Netty 모두 같습니다. 둘의 연결 수용 정책과 설정 방법은 다를 수 있지만, **둘 다 OS의 TCP 소켓을 사용하며 같은 종류의 자원 비용을 냅니다.**

또 사용자 연결과 공급사 연결은 별개입니다.

```text
````

````text
우리 IP:51001 → 공급사 A:443

```

예를 들어 서버는 다음 이유로 연결을 닫을 수 있습니다.

- 서버 종료나 연결 관리 정책
````

````text
프로그램이 소켓을 만들면 OS는 그 소켓을 가리키는 번호를 줍니다. Linux에서는 이것이 파일 디스크립터, 즉 FD입니다.

  3 → 로그 파일

  5 → 사용자 B와 연결된 소켓

```

이 번호와 실제 소켓을 연결하는 관리 정보도 메모리에 있습니다. **‘소켓 핸들’이라는 별도의 하드웨어 부품을 하나씩 소비하는 것이 아닙니다.**

그런데 OS는 프로세스마다 사용할 수 있는 FD 범위를 제한합니다. Linux의 `RLIMIT_NOFILE`이 그것입니다. 예를 들어 이 값이 1,024이고 사용 가능한 FD가 모두 차면, RAM이 수십 GB 남아 있어도 추가 소켓을 얻지 못합니다. 파일이나 파이프도 같은 한도를 사용합니다. [Linux 프로세스 자원 제한](https://man7.org/linux/man-pages/man2/getrlimit.2.html)

여기서 1,024는 **“RAM에 마련된 테이블이 물리적으로 1,024칸 이상 커질 수 없다”는 뜻이 아닙니다.** 프로세스에 허용한 한도입니다. 권한과 상위 한도 범위에서 높일 수 있습니다. 시스템 전체 파일 핸들 한도인 `file-max` 등도 별도로 있습니다. [Linux 파일 핸들 한도](https://docs.kernel.org/admin-guide/sysctl/fs.html#file-max-file-nr)

**RAM이 남는데 왜 그런 한도를 두는가**

OS는 “현재 메모리가 남으니 어느 프로세스든 전부 사용해도 된다”는 방식으로 자원을 배분하지 않기 때문입니다.

프로그램 하나가 버그나 과도한 연결 유입으로 소켓을 계속 만들면, 다른 프로그램과 OS가 사용할 메모리까지 소진할 수 있습니다. 따라서 관리자가 다음 두 가지를 별개로 정할 수 있게 합니다.

- 이 컴퓨터가 물리적으로 감당할 수 있는 양
- 그중 이 프로세스나 기능에 사용을 허용할 양

RAM을 추가하면 첫 번째는 늘지만, 두 번째가 반드시 자동으로 바뀌지는 않습니다. **한도를 명시적으로 정해 뒀다면 RAM 증설 이후에도 그 설정은 유지될 수 있습니다.**

**TCP 버퍼의 메모리 제한도 비슷한가**

네. Linux에는 TCP 소켓들의 버퍼 사용량을 관리하는 `tcp_mem` 설정이 있습니다. 메모리 사용을 억제하기 시작하는 기준과 최대 허용량 등을 정의합니다. 기본값은 부팅 시 사용 가능한 메모리를 바탕으로 계산됩니다. [Linux TCP 메모리 설정](https://docs.kernel.org/networking/ip-sysctl.html#tcp-mem-vector-of-3-integers-min-pressure-max)

여기서도 **“TCP용으로 물리 RAM의 특정 구역을 고정 분할해 놓았고, 그 구역 밖은 절대로 사용할 수 없다”는 의미는 아닙니다.** 메모리를 할당하면서 사용량을 집계하고, 정해진 예산에 따라 추가 사용을 제어하는 것입니다.

서버의 최대 연결 수 설정은 더 직접적입니다. 최대 1만 개로 설정했다면, RAM에 여유가 있어도 프로그램이 그 수에서 연결 수용을 제한합니다. 역시 저장 공간의 물리적 한계와는 별개입니다.

**그렇다면 제한값도 함께 높이면, 결국 RAM에 따라 더 많은 인바운드 연결을 유지할 수 있는가**

**네. 당신이 가정한 것처럼 처리 속도가 충분하고, 관련 OS·프로그램의 한도도 적절히 높였다면, 더 많은 RAM으로 더 많은 연결을 유지할 수 있다는 이해가 맞습니다.**

제가 앞서 말한 것은 “RAM과 무관한, 늘릴 수 없는 소켓 자원이 따로 있다”는 뜻이 아니었습니다. 정확한 표현은 다음과 같습니다.

> 연결 상태와 버퍼를 저장할 메모리가 충분해야 하고, OS와 서버도 그만큼의 자원 사용을 허용하도록 설정되어 있어야 한다.

이는 앞서 설명한 **TCP 포트 필드의 16비트 제한**과 성격이 다릅니다. 포트 번호 범위는 현재 프로토콜 형식의 제한이고, FD 사용 한도나 서버 최대 연결 수는 주로 조정 가능한 운영 설정입니다.
````

````text
제품 차원의 근거도 있습니다. ThingsBoard는 외부 HTTP 호출용 Reactor Netty 풀의 최대 연결 수를 설정으로 제공하고, 많은 연결을 지원하는 원격 서비스에 대한 고처리량 호출에서는 이를 높이도록 설명합니다. 다만 특정 수천·수만 개를 권장하지는 않습니다. [ThingsBoard 공식 설정](https://github.com/thingsboard/thingsboard/blob/master/application/src/main/resources/thingsboard.yml)

**어떤 상황이면 수천~수만 개가 합리적인가**

HTTP/1.1에서 연결을 요청·응답 교환 동안 하나씩 사용한다고 할 때, 필요한 평균 활성 연결 수는 대략 다음 관계를 따릅니다.

```text
평균 활성 연결 수 ≈ 초당 공급사 호출 수 × 평균 연결 점유 시간
```

설명용 계산을 하면:

| 한 인스턴스가 특정 공급사에 보내는 호출 | 평균 연결 점유 시간 | 평균 활성 연결 수 |
|---|---:|---:|
| 초당 5,000건 | 50ms | 약 250개 |
| 초당 5,000건 | 500ms | 약 2,500개 |
| 초당 5,000건 | 2초 | 약 10,000개 |

이는 운영 사례의 수치가 아니라 계산 예시입니다. 평균값 자체가 적절한 최대 풀 크기를 정해 주지는 않지만, **같은 처리량도 응답이 느리면 필요한 연결 수가 수천·수만 개로 커질 수 있다**는 점을 보여줍니다.

그러므로 공급사가 2초 걸리는 것이 정상적인 특성이고, 그 응답을 기다리는 요청을 초당 5,000건 처리해야 한다면, 연결 수를 크게 확보하는 것은 합리적인 용량 설계입니다. “너무 큰 숫자이니 설계가 잘못됐다”고 할 수 없습니다.

당신의 서버에서는 여기에 **검색 한 건당 공급사 호출 횟수**가 들어갑니다. 청크 분할 때문에 검색 하나가 공급사 호출 여러 건으로 늘어나면 필요한 아웃바운드 연결 용량도 커집니다.

**그런데 왜 무조건 수만 개로 크게 잡지는 않는가**

“현업에서는 쓰지 않는다”는 사실을 확인한 것은 아닙니다. 다음은 **큰 풀을 선택하지 않거나, 크기를 제한할 기술적 이유**입니다.

첫째, **필요한 동시 교환 수가 적으면 큰 풀로 얻는 것이 없습니다.**

앞의 50ms 예시에서는 평균적으로 약 250개가 필요합니다. 최대치를 1만으로 설정해도 실제로 그만큼 연결이 생성되는 것은 아니지만, 평상시 처리량이 자동으로 높아지는 것도 아닙니다.

둘째, **연결을 많이 유지할 능력과 한꺼번에 많이 생성할 능력은 다릅니다.**

이미 연결된 1만 개를 재사용하는 상황과, 배포 직후나 연결 단절 이후 1만 개를 새로 맺는 상황은 다릅니다. 후자는 TCP 연결 설정과 TLS 핸드셰이크가 집중됩니다.

Reactor Netty 공식 문서도 최대 연결 수를 매우 높게 설정한 고부하 상황에서는, 동시 연결 생성·획득이 많아 연결 타임아웃이 발생할 수 있다고 명시합니다. 이것은 “큰 풀은 금지”가 아니라 **연결 생성이 집중되는 상황까지 감당해야 한다**는 제약입니다. [공식 연결 풀 주의사항](https://projectreactor.io/docs/netty/release/reference/http-client.html#_connection_pool)

셋째, **연결 수 증가가 성공 처리량 증가로 이어지지 않는 상황도 있습니다.**

공급사 처리 능력에 여유가 있고 우리 풀만 작았다면, 풀을 늘려 처리량을 높일 수 있습니다.

반면 실제 운영에서 공급사의 CPU·DB 등이 이미 포화됐다면 연결을 더 열어도 그쪽에서 대기하는 요청만 늘어날 수 있습니다. 이는 확인되지 않은 공급사 한도를 지어내자는 말이 아닙니다. **풀을 늘렸을 때 성공 처리량도 늘어나는지, 지연과 타임아웃만 늘어나는지를 구분해야 한다**는 뜻입니다.

넷째, **큰 동시성을 확보하는 방법이 단일 인스턴스의 TCP 연결 수 증가만 있는 것은 아닙니다.**

- 여러 인스턴스에 부하를 분산하면 인스턴스당 필요한 연결 수를 낮출 수 있습니다. 전체 연결 수가 줄어드는 것은 아닙니다.
- 공급사가 HTTP/2를 지원하면 한 연결에서 여러 요청을 처리하여 필요한 TCP 연결 수를 줄일 수 있습니다. 실제 동시성은 스트림 제한 등의 영향을 받습니다. [Reactor Netty HTTP/2 풀](https://projectreactor.io/docs/netty/release/reference/http-client.html#_http_2)

이런 선택지가 있으므로 서비스 전체에서 연결 수만 개를 사용하더라도, 한 인스턴스의 한 풀을 수만 개로 설정하지 않을 수 있습니다.

제 판단은 **당신이 제안한 “아웃바운드 풀을 충분히 키워 불필요한 병목을 없앤다”는 접근은 현실적인 엔지니어링 선택**이라는 것입니다. 이를 “이론적으로만 가능하다”거나 “현업에서는 그런 식으로 하지 않는다”고 배제할 근거는 없습니다.

다만 **수천 개 설정은 공개 사용·실험 보고가 확인되고, 수만 개를 한 목적지에 실제 점유하며 안정 운영한 사례는 이번 조사로 확인하지 못했습니다.** 당신의 시스템에 적용할 때 판단 기준은 숫자의 크기 자체보다, 풀 확대가 실제로 성공 처리량과 응답 시간을 개선하는지입니다.
````

````text
이제 비교의 중심은 **“명령형 코드를 유지하면서 동시성을 확보할 것인가”와 “요청부터 응답까지 비동기 모델로 연결할 것인가”**입니다. 두 후보 모두 플랫폼 요청 스레드 200개에 묶이지 않으므로, 이전의 병목 논쟁을 그대로 가져올 필요는 없습니다.

비교에서는 동일하게 **목적지별 아웃바운드 풀 상한 2,500개**를 가정하겠습니다. 이 값은 초기 설계 목표이며, 실제 병목 위치나 처리량을 검증한 수치는 아닙니다.

| 비교 축 | MVC(VT on) + WebClient | WebFlux(Netty) + WebClient |
|---|---|---|
| 코드 구성 | 일반 업무는 명령형, 공급사 조합은 Reactor. 두 모델의 경계를 둠 | 요청부터 응답까지 Reactor로 연결. 하나의 모델로 구성 |
| JDBC·JPA 등 동기 라이브러리 | 요청을 처리하는 가상 스레드에서 직접 사용하기 편함 | 별도 실행 자원으로 격리하거나 리액티브 대안을 사용 |
| 요청 대기 비용 | 가상 스레드 상태와 Reactor 상태를 유지 | 요청 전용 대기 스레드 없이 구독·요청 상태를 유지 |
| 클라이언트 연결 종료 | `.block()` 대기와 연결 종료가 자동으로 연결되지 않음 | 종료 감지 시 연결된 파이프라인으로 취소를 전파하기 자연스러움 |
| 응답 전송·스트리밍 | Servlet의 blocking 응답 쓰기. VT로 대기 비용 완화 | non-blocking 응답 쓰기. 스트리밍과 흐름 제어에 유리 |
| blocking 코드 혼입 | 명령형 구간에서는 다루기 편함. WebClient 체인에서는 여전히 주의 | 이벤트 루프에서 실행되지 않도록 명시적으로 분리해야 함 |
| 디버깅·문맥 관리 | 명령형 구간은 호출 스택·`try/catch`·`ThreadLocal`이 자연스러움 | Reactor Context와 비동기 추적을 요청 전체에 일관되게 적용 |

이 중 당신의 서버에서 의미가 큰 차이는 다음과 같습니다.

**1. MVC(VT on)의 가장 확실한 장점은 동기 코드와의 호환성입니다.**

예를 들어 검색 처리를 다음처럼 구성할 수 있습니다.

```text
가상 스레드에서 매핑 DB 조회
→ Reactor로 공급사 호출들을 조합
→ 최종 결과를 한 번 block하여 받음
→ 일반 코드로 후처리하고 응답
```

JDBC·JPA를 쓰거나 동기 라이브러리를 호출할 때 자연스럽습니다. 일반 업무 로직은 익숙한 순차 코드로 읽을 수 있고요. Spring도 blocking 영속성 API를 사용하는 일반적인 구성에서는 MVC를 적합한 선택으로 설명합니다. [Spring의 선택 기준](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html)

대가는 **명령형 구간과 Reactor 구간의 경계를 관리해야 한다는 점**입니다. 요청 정보, 예외 처리, 취소가 그 경계를 어떻게 넘는지 알아야 합니다.

특히 MVC라는 이유로 WebClient 내부까지 동기 코드처럼 다룰 수는 없습니다. WebClient의 `map` 안에서 JDBC를 호출하면 이벤트 루프를 막을 수 있습니다.

**2. WebFlux의 가장 확실한 장점은 요청 전체의 수명을 하나의 파이프라인으로 다루는 것입니다.**

```text
요청 수신
→ 매핑 조회
→ 공급사 호출 조합
→ 결과 변환
→ 응답 전송
```

이 흐름을 하나의 `Mono`·`Flux` 체인으로 연결합니다. 결과뿐 아니라 오류·취소·요청 문맥도 같은 구조를 따라갑니다. `.block()`으로 값을 꺼내서 다른 실행 모델로 넘기는 경계가 없습니다.

공급사 호출 조합을 이미 Reactor로 만들기로 했으므로, WebFlux의 추가 비용을 “Reactor를 처음부터 전부 배워야 한다”로 계산하면 부정확합니다. **이미 사용하는 모델을 DB와 요청·응답 경계까지 확대하는 비용**입니다.

반대로 JDBC·JPA가 필요하면 다음 중 하나를 선택해야 합니다.

- DB 접근을 R2DBC로 구성한다.
- JDBC·JPA 작업을 별도 실행 자원으로 격리한다.

두 번째도 유효한 설계입니다. 다만 DB 작업과 트랜잭션 범위를 함께 격리해야 하고, 명령형 트랜잭션과 리액티브 트랜잭션의 문맥이 다르다는 점을 알아야 합니다. [Spring 트랜잭션 모델 설명](https://spring.io/blog/2019/05/16/reactive-transactions-with-spring/)

**아직 JPA를 선택하지 않았다면, JPA 호환성을 WebFlux의 결정적인 약점으로 미리 잡을 수는 없습니다.**

**3. 취소 전파는 WebFlux의 실제 장점이지만, 범위를 정확히 봐야 합니다.**

두 후보 모두 다음은 가능합니다.

> 검색 전체 시간 예산 초과 → 진행 중인 WebClient 호출 취소

이것은 Reactor 내부에서 처리하므로 MVC도 동일합니다.

차이는 다음 경로입니다.

> 사용자 연결 종료 감지 → 검색 파이프라인 취소 → 진행 중인 공급사 호출 취소

WebFlux·Netty는 요청 처리가 연결된 구독으로 유지되므로 이 경로를 구성하기 자연스럽습니다. 반면 동기 MVC에서 `.block()`으로 기다리는 요청은 사용자 연결이 종료됐다는 사실만으로 자동 중단되지 않습니다. Servlet API에는 원격 클라이언트 이탈을 즉시 알리는 일반적인 통지가 없다는 제약도 있습니다. [MVC 연결 종료 감지](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html#_disconnects), [Reactor Netty 종료 처리](https://github.com/reactor/reactor-netty/blob/main/reactor-netty-core/src/main/java/reactor/netty/channel/ChannelOperations.java)

다만 WebFlux도 프록시가 연결을 유지하거나, 별도로 `subscribe()`한 작업처럼 요청과 수명이 분리되면 기대한 취소가 전달되지 않을 수 있습니다. 로컬 HTTP 호출을 취소했다고 공급사에서 이미 시작한 업무까지 중단되는 것도 아닙니다.

당신의 검색 화면에서 사용자가 조건을 바꿔 이전 검색을 자주 취소한다면 이 차이에 무게를 둘 수 있습니다.

**4. 응답을 한 번에 주는지, 흘려보내는지에 따라 WebFlux의 이점이 달라집니다.**

WebFlux는 응답 전송도 non-blocking이므로, 결과를 순차적으로 흘려보내거나 느린 클라이언트에 맞춰 전송하는 구성을 만들기 좋습니다. MVC도 스트리밍을 지원하지만 응답 쓰기의 실행 방식은 다릅니다. [Spring의 응답 처리 비교](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html#_async_spring_mvc_compared_to_webflux)

하지만 현재처럼 **공급사 결과를 모아 JSON 하나로 반환한다면**, 이 장점의 비중은 줄어듭니다. WebFlux에서도 `collectList()`로 전부 모으면 결과를 보관할 메모리가 필요합니다. WebFlux를 선택했다는 이유만으로 대량 응답의 메모리 비용이 없어지지는 않습니다.

**5. 처리량·메모리의 우열은 아직 단정할 수 없습니다.**

MVC(VT on)는 검색마다 가상 스레드 상태를 추가로 유지하고, WebFlux는 그것 없이 요청을 이어갑니다. 그렇다고 곧바로 “WebFlux가 의미 있게 적은 RAM으로 더 많이 처리한다”고 결론낼 수는 없습니다. 파이프라인 객체, 버퍼, 응답 크기, 스케줄링과 변환 작업의 배치도 함께 작용합니다.

또 WebFlux·Netty는 기본적으로 서버와 WebClient가 이벤트 루프 자원을 공유합니다. 자원 공유의 이점이 있지만, 그곳에 긴 작업이 들어가면 인바운드와 아웃바운드 양쪽에 영향을 줄 수 있습니다. MVC에서는 서버 처리가 분리되지만 WebClient 쪽 이벤트 루프의 영향은 그대로 남습니다. [Spring 실행 자원 설명](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html#webflux-threading-model)

현재 결정에 가장 직접적인 기준은 다음 두 가지입니다.

- **DB와 일반 업무를 명령형 코드로 유지하는 가치가 크다:** MVC(VT on)에 무게.
- **DB도 비동기로 구성하고, 사용자 연결부터 공급사 호출·응답까지 수명을 일관되게 관리하는 가치가 크다:** WebFlux에 무게.

아웃바운드 풀을 크게 잡았다는 결정은 두 후보 모두와 양립합니다. 그 결정 자체가 어느 쪽의 승리를 의미하지는 않습니다.

결정과 비교는 [비동기 모델 기록](/C:/Users/kxu45/ProgramStudy/integration-workspace/notes/async-model-choice.md:7)에 반영했고, [풀 상한 2,500개 결정](/C:/Users/kxu45/ProgramStudy/integration-workspace/notes/outbound-pool-capacity.md)도 별도로 기록했습니다. 최종 모델 선택은 미결로 유지했습니다.
````

````text
**아니요. 현재 비교 중인 ‘MVC(VT on) + WebClient’와 ‘WebFlux + WebClient’에서는 그 세 가지를 구현하는 용이성이 사실상 같습니다.**

타임아웃·재시도·병렬 호출 제어는 **WebClient의 설정과 Reactor 연산자**로 구현하기 때문입니다. 서버가 MVC인지 WebFlux인지에 따라 사용할 수 있는 기능이 달라지지 않습니다.

| 구현할 내용 | 두 구성에서 사용하는 방법 |
|---|---|
| 연결·응답 타임아웃 | WebClient에 연결한 HTTP 클라이언트 설정 |
| 호출 시간 제한 | `timeout` |
| 재시도·백오프·재시도할 오류 선별 | `retryWhen` |
| 여러 공급사 동시 호출 | `Mono.zip`, `flatMap` 등 |
| 동시 호출 수 제한 | `flatMap`의 동시성 인자 등 |
| 부분 실패 처리 | 개별 호출의 `onErrorResume` 등 |

호출들을 조합한 결과가 `Mono<SearchResponse>`라면, **그 조합 코드 전체를 두 구성에서 그대로 공유할 수 있습니다.** 마지막 소비 방식이 달라질 뿐입니다.

```java
// MVC(VT on): 가상 스레드에서 최종 결과를 기다림
return searchService.search(request).block();

// WebFlux: 프레임워크가 구독하도록 반환
return searchService.search(request);
```

첫 번째도 **공급사별로 호출하고 기다리는 것이 아니라, 이미 병렬로 조합한 작업 전체를 한 번 기다리는 것**입니다. 그 안의 타임아웃·재시도·동시성 제어는 그대로 작동합니다. Spring 공식 문서도 여러 WebClient 호출을 조합하고 마지막에 한 번 `block()`하는 사용법을 설명합니다. [공식 동기 사용 예시](https://docs.spring.io/spring-framework/reference/web/webflux-webclient/client-synchronous.html)

WebFlux의 편의성이 더 드러나는 것은 범위를 **사용자 요청의 수명까지** 넓혔을 때입니다. 사용자 연결 종료에 따른 취소, 비동기 DB 접근, 응답 스트리밍까지 하나의 파이프라인으로 연결하기 자연스럽습니다.

따라서 **“공급사 호출의 타임아웃·재시도·병렬 제어를 잘 구현하려고 WebFlux를 선택한다”는 근거는, 이미 WebClient·Reactor를 사용하는 MVC와의 비교에서는 차별점이 되지 않습니다.**
````
