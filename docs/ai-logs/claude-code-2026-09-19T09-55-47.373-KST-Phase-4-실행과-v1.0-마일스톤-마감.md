## Findings

**WARNING-1: a chunk where every result is filtered out is counted as a failure.** REQ: SRCH-05, SRCH-06, ADPT-04, MAP-05, SRCH-07.
- In `SupplierAAdapter.java` `toSearchResult` (and the same code in `SupplierBAdapter.java` at lines 149-151), `items.isEmpty() || !offers.isEmpty() ? [] : INVALID_RESPONSE` marks a chunk as failed whenever the supplier returned items but none survived filtering.
- Items get filtered for being unmapped room types (Phase 2 rule), over capacity (`maxOccupancy &lt; guests`), wrong currency, or missing nights.
- Chunking makes this more likely. The check now runs on each 50-code chunk instead of the whole supplier, so one chunk made entirely of newly added room types marks the supplier failed. If no other chunk has offers, the search returns 503 even though "no rooms" should be a 200 with empty results.
- The mocks hide this because they filter by guest count on their side (`SupplierAMockController.java:105-114`).

**WARNING-2: a chunk that succeeds with no offers counts for nothing when another chunk fails.** REQ: SRCH-05, SRCH-06.
- In `DefaultStaySearchService.assemble`, a supplier result that has any failures only counts as a successful call if it has offers.
- Example: A has one chunk that succeeds with 0 offers and one that fails, and B is down. The result is 503, although one chunk actually succeeded.
- The single-call rules from Phase 3 aren't written for this chunked mixed case.

**INFO (by design):** when the service-level safety timeout fires, offers from chunks that had already finished are dropped. This only happens if `take(budget)` itself doesn't finish, so it is acceptable.
