**③ 통합 검색 API**: 아래 정보만 담기면 필드명과 구조는 자유입니다.

## 4. 공급사 A와 B의 차이

| | Supplier A | Supplier B |
|---|---|---|
| 숙소 목록 | `GET /a/v1/hotels` | `GET /b/api/properties` |
| 재고·요금 | `GET /a/v1/availability?hotelCodes=` | `GET /b/api/search?propertyIds=` |
| 식별자 | `hotelCode` / `roomTypeCode` | `propertyId` / `roomId` (이름과 달리 객실 타입) |
| 요금 | **날짜별 1박 단가** `dailyRates[]` | **숙박 전체 총액** `totalPrice` |
| 세금 | **별도**: `nightlyRate`(세전) + `taxAmount` | **포함**, 세금액은 따로 안 줌 |
| 재고 | `dailyRates[].remainingRooms` | `inventory[].remainingRooms` |
| 실패 표현 | HTTP 4xx/5xx + `{error, message}` | **항상 HTTP 200** + `resultCode`, `data: null` |

두 공급사가 똑같이 따르는 규약:
- 인증은 `X-Api-Key` 헤더, 날짜는 `YYYY-MM-DD`, 체크아웃일은 숙박일에 포함되지 않음
- 재고·요금 조회는 한 번에 숙소 코드 최대 50개
- `maxOccupancy`는 성인+아동 합산이고, 공급사는 요청 인원을 수용하는 객실 타입만 반환
- 조식 포함 여부는 재고·요금 API에만 있음

예시 데이터로 검증할 수 있는 값:
- A `A-10023` Deluxe Twin: 132,000 + 165,000 + 132,000 = **429,000원**, 조식 미포함, 예약 가능 min(3,1,5) = **1실**
- B `B77120` Deluxe Twin Room: **452,000원**, 조식 포함, 1실. A-10023과 실제로 같은 숙소지만 이를 알려주는 공통 키는 없음
- A `A-10044` Namsan Garden Stay: 9/2 재고가 0이라 **예약 불가**

| 선택 범위 1–2개 (예: Resilience4j 재시도·서킷 브레이커, 연동 지표) | +5–10h |

시간을 바꾸는 요인:
- **WebClient·Reactor 경험이 적으면 5~10시간을 더 잡으세요.** 타임아웃 설정, 에러를 결과 값으로 바꾸는 연산자, 비동기 코드 테스트에서 주로 막힙니다.
- **AI로 줄어드는 건 코드 작성 시간 정도입니다.** 코드 리뷰에서 모든 코드를 설명해야 하고 판단 근거는 직접 써야 해서, 전체의 30~40%인 문서·설계 시간은 거의 줄지 않습니다.
- **7일에 나눠 보면:** 온종일 쓸 수 있으면 하루 5~6시간으로 여유가 있습니다. 직장과 병행해 평일 저녁 2~3시간과 주말 이틀을 쓰면 25~30시간 정도라 필수 범위도 빠듯하고, 선택 범위은 설계 문서로만 다루는 게 현실적입니다.

## 2. 다시 보니 놓쳤던 지점

### 제외·불리한 판단 위험 (가장 중요)
1. **AI 활용 기록에 대화 원문을 붙이면 안 됩니다.** 이 세션 기록에는 제가 읽은 PDF 전문과 스펙 요약표가 들어 있습니다. 원문 로그를 커밋하면 "요구사항 항목 일부 게시"에 걸립니다. 무엇을 묻고 어떻게 판단했는지만 본인 말로 요약하세요.
2. **도구가 만드는 파일도 같은 문제가 있습니다.** GSD를 쓰면 `.planning/`에 요구사항을 옮겨 적은 문서가 생기고, CLAUDE.md도 마찬가지입니다. 게다가 CLAUDE.md는 AI에게 지시하는 파일이라, AI가 저장소를 먼저 읽는 검토에서는 프롬프트 인젝션 시도로 보일 위험도 있습니다. 둘 다 `.gitignore`에 넣는 게 안전합니다.
3. **폴더명이 빌드 결과물에 자동으로 들어갑니다.** Gradle은 `rootProject.name`이 없으면 폴더명을 프로젝트명으로 써서 jar 이름(`integration-workspace-0.0.1-SNAPSHOT.jar`)과 README 실행 명령에까지 들어갑니다. IDE로 이 폴더에서 프로젝트를 만들어도 기본 이름이 폴더명이 됩니다. 프로젝트를 만들기 전에 폴더명부터 바꾸는 게 가장 깔끔합니다.
4. **README에 요구사항 문서를 옮겨 붙이면 안 됩니다.** 프로젝트를 설명할 때도 본인 말로 요약하라고 명시돼 있습니다. 지난 요약에서 빠뜨린 부분입니다.

### 문서에서 놓친 요구
5. **"설계는 전체 도메인, 구현은 핵심 흐름, 무엇을 왜 구현했는지 설명"이 요구됩니다.** README에 구현한 범위 / 설계만 한 범위 / 포기한 것과 이유를 나눠 적어야 합니다. 선택 항목을 전부 설계할 필요는 없지만 설계만 해도 가점이라, 구현 대신 문서로 다루는 전략이 통합니다. 또 스펙이 README.md를 콕 집은 항목(모델에서 버린 정보와 근거, 예약 불가 상품 처리 방식)은 docs/가 아니라 README에 있어야 합니다.
6. **검토자가 직접 재현할 수 있어야 합니다.** Mock을 "연동 동작을 검증하는 수단으로 확인한다"고 했습니다. README에 Mock 기동 → 앱 기동 → curl로 A 무응답·B 장애 만들기 → 기대 응답까지 순서대로 적어 두세요. 설치할 게 적을수록 좋으니 H2가 유리하고, PostgreSQL을 쓰면 docker compose가 필요합니다.

### 구현하다 걸릴 함정
7. **메모리 모드 H2를 쓰면 재시작할 때마다 내부 ID가 바뀔 수 있습니다.** 기동할 때 동기화하고 ID를 자동 증가로 매기면, 공급사 목록 순서가 바뀌거나 숙소가 추가될 때 번호가 밀립니다. 그러면 "같은 상품은 항상 같은 내부 ID" 요구를 어기게 됩니다.
   - 해결책은 파일 모드 H2나 PostgreSQL을 쓰거나, 공급사 키에서 항상 같은 ID가 나오도록 만드는 것입니다. 파일 모드 H2면 6번과 함께 해결됩니다.
   - 다시 동기화할 때 목록에서 사라진 숙소는 삭제하지 말고 비활성으로 두어야 ID가 유지됩니다.
8. **제공된 Mock은 요청 파라미터를 무시하고 항상 같은 응답을 줍니다.** 이 때문에 생기는 문제는 세 가지입니다.
   - 다른 날짜로 검색해도 9/1~9/3 데이터가 옵니다. 응답 날짜가 요청 기간과 맞는지 검증하면 예시 날짜 외의 검색은 전부 빈 결과가 됩니다.
   - 3명으로 검색해도 2인실이 옵니다.
   - 50개 분할을 시험하려고 여러 번 호출하면 매번 전체 숙소가 와서 중복이 생깁니다.

   Mock을 조금 고칠지(요청 날짜로 데이터 생성, 요청한 코드만 반환), 우리 쪽 검증을 어디까지 둘지 정해야 합니다.
9. **앱 기동 순서에 의존하게 됩니다.** 기동할 때 동기화하면 Mock이 먼저 떠 있어야 합니다. 그렇지 않으면 앱이 뜨지 않거나, 매핑이 0건이라 검색 결과가 에러 없이 빈 채로 나옵니다.
10. **스펙은 "일부 실패"만 정의합니다.**
    - 두 공급사가 모두 실패하면 200과 빈 결과를 줄지, 503을 줄지 직접 정해야 합니다.
    - checkOut이 checkIn보다 이르거나 같은 잘못된 요청은 공급사에 보내기 전에 400으로 막아야 합니다. 그래야 공급사가 돌려준 400을 공급사 장애로 잘못 표시하지 않습니다.
    - 실패를 고객 입력 오류 / 공급사 거절(400·401) / 일시 장애(429·5xx, B는 E429·E5xx) / 타임아웃으로 나눠 두면 재시도 정책까지 자연스럽게 이어집니다.
11. **타임아웃은 두 겹이 필요합니다.** 하나는 공급사 호출 1회의 연결·응답 타임아웃이고, 다른 하나는 50개씩 나눠 여러 번 호출할 때 검색 전체에 거는 시간 한도입니다. WebClient는 기본 응답 타임아웃이 없어서, 설정하지 않으면 무응답 Mock에 600초 동안 묶입니다.
12. **숙소명·객실명·수용 인원을 어디서 가져올지 정해야 합니다.** 목록 API와 검색 API가 둘 다 이 값을 줍니다. 매핑 DB 값을 쓸지 실시간 검색 값을 쓸지, 둘이 다르면 무엇을 믿을지가 "자주 안 바뀌는 데이터 vs 매번 바뀌는 데이터" 판단과 바로 연결됩니다.
13. **금액은 통화의 최소 단위 정수입니다.** KRW는 원 단위지만 USD라면 센트 단위입니다. 금액이 항상 통화 코드와 함께 다니도록 모델을 잡으세요. 통화 처리 자체는 선택이지만, 모델은 처음부터 이렇게 잡는 게 안전합니다.
14. **스펙 안에 사소한 불일치가 있습니다.** A의 필드 사전에는 `HotelCode`(대문자 H), 예시 JSON에는 `hotelCode`로 적혀 있습니다. 예시 기준으로 판단했다고 JOURNAL에 적어 두면, "궁금한 점은 스스로 판단하고 과정을 남기라"는 요구에 맞는 소재가 됩니다.
