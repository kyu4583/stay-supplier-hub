````text
| 재고 | `dailyRates[].remainingRooms` | `inventory[].remainingRooms` |
````

````text
NestJS 경험이 있으니 JavaScript의 Promise에 빗대서 설명하겠습니다.

## 1. WebClient란

Spring이 제공하는 HTTP 클라이언트, 즉 외부 API를 호출하는 도구입니다. 용도는 RestTemplate·RestClient와 같지만, **요청을 보낸 뒤 응답이 올 때까지 스레드가 멈춰서 기다리지 않는다(non-blocking)**는 점이 다릅니다.

- **RestTemplate / RestClient (동기, blocking):** 호출하면 응답이 올 때까지 그 스레드가 멈춥니다. 호출 1건마다 기다리는 스레드가 1개씩 생깁니다.
- **WebClient (비동기, non-blocking):** 호출하면 결과 대신 "나중에 올 값"인 `Mono`를 돌려받습니다. 실제 네트워크 대기는 Netty(비동기 네트워크 라이브러리)의 소수 스레드가 한꺼번에 처리하므로, 기다리는 동안 스레드를 붙잡지 않습니다.

`Mono`는 Promise와 비슷하고, 이를 다루는 연산자는 Reactor라는 라이브러리가 제공합니다.

| 하고 싶은 일 | Node.js | WebClient + Reactor |
|---|---|---|
| 나중에 올 값 | `Promise` | `Mono`(0~1개), `Flux`(0~N개) |
| 여러 호출을 동시에 보내고 모두 기다리기 | `Promise.all` | `Mono.zip`, `Flux.merge` |
| 일부가 실패해도 나머지는 살리기 | `Promise.allSettled` | 호출마다 `onErrorResume`으로 실패를 값으로 바꾼 뒤 `zip` |
| 시간 제한 | `AbortController` + `setTimeout` | `.timeout(Duration)`, `responseTimeout` |
| 재시도 | 직접 반복문 작성 | `.retryWhen(Retry.backoff(...))` |
| 동시 호출 수 제한 | `p-limit` | `flatMap(함수, 동시성)` |

결정적인 차이가 하나 있습니다. Promise는 만들자마자 실행되지만 **`Mono`는 누군가 결과를 요청하기(`subscribe`/`block`) 전까지 아무 일도 하지 않습니다.** 요청도 그때 나갑니다.

## 2. 이 프로젝트의 흐름으로 비교

A는 무응답이고 B는 0.2초 만에 응답하는 상황입니다.

**동기 클라이언트:**
```java
var a = restClient.get().uri(...).retrieve().body(AResponse.class); // 스레드가 멈춤. A가 끝나야
var b = restClient.get().uri(...).retrieve().body(BResponse.class); // B가 출발
```
- 순서대로 호출하므로 총 시간은 A 시간 + B 시간입니다.
- 동시에 부르려면 스레드 풀과 `CompletableFuture`를 직접 관리해야 하고, 기다리는 동안 그 스레드들이 모두 묶입니다.

**WebClient:**
```java
Mono<SupplierResult> a = supplierA.search(req)                         // 요청을 정의만 함
        .timeout(Duration.ofSeconds(2))                                // 2초가 넘으면 실패
        .onErrorResume(e -> Mono.just(SupplierResult.failed("A", e))); // 실패도 결과 값으로

Mono<SupplierResult> b = supplierB.search(req)
        .timeout(Duration.ofSeconds(2))
        .onErrorResume(e -> Mono.just(SupplierResult.failed("B", e)));

SearchResponse res = Mono.zip(a, b)            // 두 요청을 동시에 출발시키고
        .map(t -> merge(t.getT1(), t.getT2())) // 둘 다 끝나면 병합
        .block();                              // MVC라면 여기서 최종 결과만 기다림
```
약 2초 뒤에 "B 결과 + A 실패"가 담긴 응답이 나갑니다. 타임아웃, 부분 실패, 병렬 호출이 각각 연산자 하나씩으로 코드에 드러납니다.

## 3. 이 문장의 의도

**(1) 외부 연동에서는 기다리는 비용이 문제입니다.** 공급사 API는 느려지거나 멈출 수 있습니다.
- blocking 방식이면 공급사가 멈춘 시간만큼 서버 스레드가 묶입니다. 트래픽이 몰리면 Tomcat 스레드(기본 200개)가 공급사 응답을 기다리느라 꽉 차서, 공급사와 상관없는 요청까지 멈춥니다.
- 한 공급사에 숙소가 3,000개라면 50개씩 60번 호출해야 합니다. 이 호출마다 스레드를 하나씩 붙잡고 기다리게 할 수는 없습니다.
- non-blocking 방식이면 응답을 기다리는 호출이 스레드를 거의 쓰지 않습니다.

**(2) 제어를 어떻게 표현하는지 보겠다는 뜻입니다.** 이 문장의 핵심은 WebClient 자체가 아니라 뒤쪽의 "타임아웃·재시도·병렬 호출 제어를 어떻게 다루는지"입니다. WebClient와 Reactor에서는 이런 제어가 명시적인 설정과 연산자로 드러나서, 검토자가 코드만 보고 바로 판단할 수 있습니다.
- **타임아웃:** 연결 타임아웃, 응답 타임아웃, 호출 전체에 거는 `.timeout()`을 어디에 몇 초로 걸었는지
- **재시도:** 무엇(429·503)은 재시도하고 무엇(400·401)은 안 하는지, 재시도 간격을 늘리는지
- **병렬:** 공급사와 50개 묶음을 동시에 부르면서 동시 호출 수를 제한했는지. 한꺼번에 너무 많이 부르면 429(호출 한도 초과)를 받습니다.
- **부분 실패:** 한 공급사의 실패가 전체 응답을 깨뜨리지 않게 막았는지

사실 Java 21의 가상 스레드와 RestClient로도 같은 기능을 만들 수 있습니다. 그러니 WebClient를 지정한 이유는 "다른 방법이 불가능해서"가 아니라 **모든 작성자를 같은 도구 위에서 비교하려는 것**으로 보입니다. "RestClient 기반 구현은 검토 의도와 맞지 않는다"는 문구도 그렇게 읽힙니다.

## 4. "MVC 위에서 WebClient만 써도 된다"의 의미

- **WebFlux 전면 도입:** 서버 자체를 Netty 기반 non-blocking으로 만들고, 컨트롤러도 `Mono`를 반환합니다. 코드 전체를 Reactor 방식으로 짜야 해서 배울 게 많습니다.
````

````text
## 선택지 2. WebFlux 전면 도입

서버 자체가 Netty 기반이고, 컨트롤러부터 응답까지 하나의 리액티브 파이프라인입니다. `block()`이 없습니다.

```java
@GetMapping("/api/v1/stays/search")
public Mono<SearchResponse> search(SearchRequest req) {
    return mappingRepository.findAllActive()          // R2DBC면 Flux
            .collectList()
            .flatMap(codes -> searchService.search(req, codes));
}
```

**장점**
- 요청 스레드도 묶이지 않습니다. 공급사가 느려도 서버 처리량을 갉아먹지 않아서, 스레드 고갈로 번지는 연쇄 장애에 강합니다.
- 클라이언트가 연결을 끊으면 취소가 파이프라인을 타고 전파되어 진행 중인 공급사 호출까지 끊을 수 있습니다.
- 동시 호출 수 제한과 흐름 제어를 공급사 호출과 같은 언어로 표현합니다.

**단점**
- **JPA를 쓸 수 없습니다.** blocking JPA를 이벤트 루프에서 호출하면 서버 전체가 막힙니다. R2DBC로 가거나 별도 스케줄러로 격리해야 하는데, 매핑 저장 정도에 R2DBC는 학습 비용이 과하고, 격리하면 "굳이 WebFlux인 이유"가 흐려집니다.
- 디버깅이 어렵습니다. 스택 트레이스가 연산자 체인으로 나와서 `checkpoint()` 같은 장치를 따로 넣어야 하고, 로깅에 요청 정보를 실어 나르려면 설정이 더 필요합니다.

- **이점을 증명할 부하 실험이 프로젝트 범위 밖입니다.** 문서에 "성능 때문"이라고 쓰면 근거 없는 주장이 됩니다.
````

````text
## 왜 그 구성이 두 겹이 되는가

```java
// 공급사 호출마다 가상 스레드 하나

    .map(s -> executor.submit(() -> s.search(req).block()))  // Mono를 만들자마자 무효화

`block()`을 거는 순간 WebClient가 주는 것이 대부분 사라집니다. 그러면 타임아웃, 재시도, 동시 호출 수 제한, 부분 실패 수집을 전부 스레드 쪽 API로 다시 만들어야 합니다. 결과적으로 **비동기 제어가 두 군데에 생기고, 하나는 쓰이지 않습니다.** 블로킹 지점도 호출 수만큼 늘어납니다. 숙소가 수천 개라 공급사당 60번씩 호출해야 하면 블로킹 지점이 120개가 됩니다. 여기서 "그럴 거면 RestClient가 정직하다"는 결론은 논리적으로 옳고, 실제로 그 구성은 요구사항을 문구로만 지킨 셈이 됩니다.

## 한 겹으로 유지되는 구성

```java
// 병렬은 Reactor가 만든다. 스레드는 관여하지 않는다.
Mono.zip(a, b).map(this::merge).block();   // 블로킹은 요청당 한 번
```

여기서 **가상 스레드는 병렬화 수단이 아닙니다.** 공급사 호출은 여전히 Netty 이벤트 루프에서 논블로킹으로 나가고, 가상 스레드는 마지막 `block()` 한 번을 값싸게 기다리는 실행 기반일 뿐입니다. 역할이 겹치지 않으니 두 겹이 아닙니다. 비유하면 `Promise.all`을 await하는 코드가 어느 스레드에서 돌든 Promise가 무의미해지지 않는 것과 같습니다.

## 그런데 그 한 번을 위해 가상 스레드가 필요한가

필요 없습니다. **앞선 제 권고를 축소하겠습니다.** MVC의 약점 보완책으로 가상 스레드 활성화를 제안했는데, 이 프로젝트 규모에서는 이득이 없습니다. 검색 요청이 동시에 수백 건 들어오지 않는 이상 Tomcat 기본 200스레드로 충분하고, 근거 없이 켜면 "왜 켰냐"는 질문만 생깁니다. 켜지 않으면 방금 지적하신 "두 겹" 논쟁 자체가 사라집니다.

## WebClient가 실제로 해주는 것

스레드로 다시 만들면 코드가 늘어나는 것들입니다.

- **취소 전파:** 검색 전체 시간 예산을 넘기면 진행 중인 나머지 호출이 취소됩니다. `Future.cancel(true)`는 blocking 소켓 읽기를 즉시 끊지 못해서 소켓 타임아웃을 따로 걸어야 합니다.
- **동시 호출 수 제한:** 60개 묶음을 한꺼번에 던지지 않고 `flatMap(호출, 8)`처럼 동시 8개로 제한합니다. 스레드 방식이면 세마포어를 직접 씁니다.
- **재시도 정책:** 어떤 실패만 재시도하고 간격을 늘리는 걸 `retryWhen` 한 줄로 표현합니다.
- **부분 실패 수집:** 실패를 값으로 바꿔 병합 단계로 흘려보냅니다.

솔직히 말하면 `StructuredTaskScope`로도 비슷하게 만들 수 있습니다. 다만 Java 25에서도 미리보기 기능이고, 무엇보다 요구사항이 지정한 방향이 아닙니다.

호출마다 block하는 구성으로 짜면, 코드만 봐서는 RestClient로 짠 것과 구분되지 않습니다. 검토자가 보겠다고 한 "타임아웃·재시도·병렬 제어를 WebClient로 어떻게 다뤘는가"가 코드에 남지 않습니다. 요구사항 위반으로 읽힐 위험이 실제로 있습니다.
````

````text
```java
// 어댑터: 호출 1건 = Mono 1개
Mono<SupplierResult> callChunk(Call c) {
    return webClient.get().uri(c.uri())
        .retrieve()

        .timeout(Duration.ofSeconds(2))                      // ① 호출별 타임아웃

                        .filter(this::isRetryable))

## 블로킹 경계를 호출마다 둘 때

```java
SupplierResult callChunkBlocking(Call c) {
    return webClient.get().uri(c.uri()).retrieve()

    var futures = calls.stream().map(c -> executor.submit(() -> callChunkBlocking(c))).toList();
    // 이제부터 ③④⑤를 직접 만들어야 한다
}

### ① 타임아웃 — 유지할 수 있지만 의미가 달라짐

`block(Duration.ofSeconds(2))`로 걸면 Reactor가 호출을 취소하고 예외를 던집니다. 여기까진 같습니다. 문제는 바깥에서 거는 경우입니다.

```java
future.get(2, TimeUnit.SECONDS);   // 호출한 쪽만 포기한다
```

이건 기다리기를 그만둘 뿐, **작업 스레드는 계속 돌고 HTTP 연결도 잡혀 있습니다.** 끊으려면 `future.cancel(true)`를 따로 불러야 합니다. 타임아웃이 두 겹이 되면 어느 쪽이 먼저 터졌는지에 따라 동작이 달라져서, 그것부터 정리해야 합니다.

### ② 재시도 — 유지되지만, Reactor를 안 쓰면 직접 짜야 함

`block()` 앞에 `retryWhen`을 두면 그대로 씁니다. 반대로 RestClient처럼 순수 블로킹으로 가면 이렇게 됩니다.

```java
for (int attempt = 0; ; attempt++) {
    try { return call(); }
    catch (Exception e) {
        if (!isRetryable(e) || attempt == 2) throw e;
        Thread.sleep(200L << attempt);   // 백오프. 지터도 직접, 전체 예산 차감도 직접
    }
}
```

### ③ 동시 호출 수 제한 — 사라짐

`newVirtualThreadPerTaskExecutor()`에는 상한이 없습니다. 60건을 공개하면 60건이 즉시 출발해서 공급사의 호출 한도(429)에 걸립니다. 직접 막아야 합니다.

```java
var gate = new Semaphore(8);
executor.submit(() -> {
    gate.acquire();
    try { return callChunkBlocking(c); } finally { gate.release(); }   // 예외 경로 누락에 주의
});
```

Reactor에서는 `flatMap(this::callChunk, 8)`의 숫자 하나입니다. 참고로 이 제한은 성능 문제만이 아닙니다. WebClient의 커넥션 풀에도 기본 상한이 있어서, 제한 없이 던지면 풀 대기에서 또 다른 종류의 타임아웃이 나고 원인을 찾기 어려워집니다.

### ④ 부분 실패 수집 — 사라짐

Reactor에서는 `onErrorResume` 한 줄로 실패를 결과 값으로 바꿔 병합 단계로 흘려보냅니다. 스레드 쪽에서는 이렇게 됩니다.

```java
var results = new ArrayList<SupplierResult>();
for (var f : futures) {
    try {
        results.add(f.get(remaining(deadline), TimeUnit.MILLISECONDS));
    } catch (TimeoutException e) {
        f.cancel(true);
        results.add(SupplierResult.failed(TIMEOUT));
    } catch (ExecutionException e) {
        results.add(SupplierResult.failed(classify(e.getCause())));  // 껍질을 벗겨 원인 분류
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();                          // 인터럽트 상태 복구
        throw new SearchInterruptedException(e);
    }
}
```

예외 세 종류를 각각 다뤄야 하고, `ExecutionException`에서 원인을 꺼내 분류해야 하며, 인터럽트 처리도 직접 해야 합니다. 이 프로젝트에서는 여기에 공급사 B의 규칙(HTTP 200인데 본문 코드가 실패)까지 얹혀야 합니다.

### ⑤ 전체 예산과 취소 — 사라짐

Reactor는 맨 위에 `.timeout(Duration.ofSeconds(5))` 하나면 됩니다. 초과하면 진행 중인 호출들이 취소됩니다. 스레드 쪽에서는 위 코드의 `remaining(deadline)`처럼 남은 시간을 매번 계산해서 넘기고, 포기할 때마다 `cancel(true)`를 전파해야 합니다. `StructuredTaskScope`가 이 부분을 정리해 주지만 Java 25에서도 미리보기 기능입니다.
````

````text
배경부터 다시 깔고 가겠습니다. 핵심 개념은 하나입니다. **WebClient는 호출을 바로 하지 않고, "주문서"를 만듭니다.**

## 1. WebClient는 호출을 즉시 하지 않는다

동기 클라이언트는 그 줄에서 바로 호출이 나갑니다.

```java
var res = restClient.get().uri(url).retrieve().body(Response.class);
// 이 줄이 끝났을 때 이미 응답이 와 있다
```

WebClient는 다릅니다.

```java
Mono<Response> plan = webClient.get().uri(url).retrieve().bodyToMono(Response.class);
// 이 줄이 끝나도 네트워크 요청은 아직 나가지 않았다. plan은 "이렇게 호출해라"라고 적힌 주문서다.
```

`Mono`는 "나중에 값 하나를 주는 주문서"입니다. JavaScript의 Promise와 비슷하지만 결정적 차이가 있습니다. **Promise는 만드는 즉시 실행되지만, Mono는 누군가 주방에 넣기 전까지 아무 일도 일어나지 않습니다.** 값이 여러 개면 `Flux`를 씁니다.

## 2. 주문서에는 조건을 적을 수 있다

주문서 상태에서는 조건을 덧붙일 수 있습니다. 이때 붙이는 것들을 연산자라고 부릅니다.

```java
Mono<Response> plan = webClient.get()...bodyToMono(Response.class)
    .timeout(Duration.ofSeconds(2))                 // "2초 안에 안 나오면 버려라"
    .retryWhen(Retry.backoff(2, ofMillis(200)))     // "이런 실패면 두 번까지 다시 시도해라"
    .map(this::정규화)                               // "결과가 오면 이 형태로 바꿔라"
    .onErrorResume(e -> Mono.just(실패결과));        // "실패하면 예외 대신 이 값으로 처리해라"
```

아직도 호출은 나가지 않았습니다. 조건이 더 적힌 주문서가 됐을 뿐입니다.

## 3. 주문서끼리 묶을 수 있다 — 여기가 핵심입니다

주문서는 값이 아니라 계획이라서, 여러 장을 한 장으로 합칠 수 있습니다.

```java
Mono<List<결과>> 전체주문 = Flux.fromIterable(호출목록)   // 호출 60건
    .flatMap(this::주문서만들기, 8)                      // "동시에 8건씩만 진행해라"
    .collectList()                                      // "다 모아서 목록 하나로 만들어라"
    .timeout(Duration.ofSeconds(5));                    // "전체가 5초 넘으면 진행 중인 것도 다 끊어라"
```

동시에 몇 건씩 돌릴지, 전체 제한 시간이 얼마인지, 결과를 어떻게 모을지는 **주문서가 여러 장일 때만 적을 수 있는 조건**입니다. 한 장짜리 주문서 안에는 쓸 자리가 없습니다.

## 4. `block()`은 주방에 넣는 순간이다

```java
List<결과> 결과목록 = 전체주문.block();   // 여기서 실제 호출이 나가고, 다 끝날 때까지 기다린다
```

`block()`을 부르면 주문서가 음식이 됩니다. **그리고 음식은 더 이상 조립할 수 없습니다.** 접시 두 개를 들고 "이 둘을 동시에 시작했어야 했는데"라고 되돌릴 수 없는 것과 같습니다.

그래서 **어디서 주방에 넣느냐가 조립할 수 있는 범위를 결정합니다.**

```
[맨 끝에서 한 번 넣는 경우]
  주문서 60장 + 동시 8건 + 전체 5초 + 실패는 값으로  ──block──▶  결과 목록
                    조건을 전부 주문서에 적어 둠

[주문서마다 넣는 경우]
  주문서1 ─block─▶ 결과1 ┐
  주문서2 ─block─▶ 결과2 ├─ 이 바깥에서 벌어지는 일은 내가 직접 관리
  ...                    ┘
```

## 5. 그래서 무엇이 남고 무엇이 사라지나

조건이 "한 호출 안의 이야기"인지 "호출들 사이의 이야기"인지로 갈립니다.

| 조건 | 어디에 속하나 | 호출마다 block하면 |
|---|---|---|
| 타임아웃 | 한 호출 안 | 남는다 |
| 재시도 | 한 호출 안 | 남는다 |
| 동시 호출 수 제한 | 호출들 사이 | 사라진다 |
| 실패한 것 빼고 모으기 | 호출들 사이 | 사라진다 |
| 전체 제한 시간과 취소 | 호출들 사이 | 사라진다 |

### 남는 것: 타임아웃과 재시도

주문서 한 장에 적는 조건이라 `block()` 앞에 붙여 두면 그대로 동작합니다.

다만 조건을 주문서가 아니라 **바깥에서** 걸면 의미가 달라집니다.

```java
future.get(2, TimeUnit.SECONDS);   // "난 2초만 기다릴래"
```

이건 기다리기를 포기하는 것일 뿐, 주방은 계속 요리 중입니다. 호출은 진행되고 연결도 잡혀 있습니다. 실제로 끊으려면 취소를 따로 걸어야 합니다.

### 사라지는 것 ①: 동시 호출 수 제한

"동시에 8건까지"는 여러 주문서를 어떻게 돌릴지에 대한 조건이라 한 장에는 적을 수 없습니다. 주문서마다 주방에 넣으면 60건이 한꺼번에 출발해서 공급사의 호출 한도(429)에 걸립니다. 직접 막아야 합니다.

```java
var gate = new Semaphore(8);          // 8개짜리 입장권을 만들어
gate.acquire();                       // 하나 받고 들어가서
try { 호출(); } finally { gate.release(); }   // 나올 때 반납. 예외 경로에서 반납을 빠뜨리면 그대로 멈춘다
```

주문서 방식에서는 `flatMap(주문서만들기, 8)`의 숫자 `8` 하나입니다.

### 사라지는 것 ②: 실패한 것 빼고 모으기

주문서 방식은 맨 위에 `.timeout(5초)` 한 줄이면 되고, 넘기면 진행 중인 호출까지 끊깁니다. 반대쪽은 위 코드의 `남은시간`처럼 매번 남은 예산을 계산해 넘기고, 포기할 때마다 취소를 직접 전파해야 합니다.
````

````text
- **상한:** 4번과 비슷하지만 병목 지점이 다릅니다. 커넥션 풀 기본값이 구현체에 따라 더 작습니다. 예를 들어 Apache HttpClient는 기본이 전체 25개, 대상 호스트당 5개입니다. 이 값을 모르면 동시 호출이 조용히 직렬화됩니다.
- **특징:** 스레드 종류가 두 가지(가상 스레드, HikariCP 뒤의 DB 연결)로 단순합니다. 호출 코드도 짧습니다. 대신 타임아웃·취소·동시 실행 수·실패 수집을 전부 스레드 쪽 API로 다룹니다.

## 6. WebFlux

```
클라이언트 ─▶ Netty 이벤트 루프 #2 (요청을 받고 곧바로 반납)
                  │ 파이프라인 등록만 하고 스레드는 다른 요청을 처리하러 감
                  ├▶ 같은 이벤트 루프 풀 ⇉ 공급사 호출 120청크
                  └▶ DB: R2DBC면 논블로킹, JPA면 boundedElastic(코어×10) 격리 필요
       응답 준비되면 ─▶ 이벤트 루프가 응답을 씀
```

- **받는 스레드:** Netty 이벤트 루프. 요청을 붙잡고 있지 않습니다.
- **보내는 스레드:** 같은 이벤트 루프 풀입니다. 서버와 클라이언트가 자원을 공유합니다.
- **연결 관계:** 어떤 스레드도 특정 요청에 묶여 있지 않습니다. 요청 상태는 스레드가 아니라 메모리에 있는 파이프라인이 들고 있습니다.
- **요청 1건당 점유 스레드:** 0개(처리 중인 순간에만 잠깐 사용).
- **상한:** 스레드가 아니라 메모리, 커넥션 수, 백프레셔가 상한입니다. 동시 수만 건도 가능합니다.
- **주의:** 이벤트 루프 스레드는 코어 수만큼뿐이라 **하나라도 블로킹되면 처리량이 급락합니다.** JPA 호출이 섞이면 바로 이 문제가 됩니다. 그래서 boundedElastic으로 격리하거나 R2DBC로 바꿔야 합니다.

**작업 스레드 풀 (2)**
- 장점: 풀 크기가 곧 동시 호출 수 제한이라 브레이크 역할을 겸합니다.

**가상 스레드 (3, 4, 5)**
- 장점: 대기 비용이 거의 없습니다. 기다리는 요청 수가 스레드 수에 묶이지 않습니다. 코드는 동기 방식 그대로라 디버깅이 쉽습니다.
````

```text
좋은 질문입니다. 이 지점이 두 선택지의 실질 차이입니다. 먼저 전제부터 확인하겠습니다.

## 전제: 연결 상한은 양쪽 다 있다

맞습니다. **가상 스레드가 아무리 많아도 동시 호출 수는 연결 수를 못 넘습니다.** HTTP/1.1에서는 연결 1개가 한 번에 요청 1건만 처리하기 때문입니다. 그래서 "가상 스레드 무제한 = 동시 호출 무제한"은 성립하지 않습니다. WebClient도 마찬가지로 호스트당 풀 상한(기본 `max(16, 코어×2)`)이 있습니다.

다만 여기서 제 이전 표를 한 군데 정정해야 합니다. **"동기 REST는 가상 스레드가 직접 I/O를 한다"는 구현체에 따라 다릅니다.**

- Apache HttpClient(classic): 호출 스레드가 소켓 읽기를 직접 합니다.
- JDK HttpClient(Spring Boot에서 별도 설정이 없을 때의 기본): 동기 호출이어도 내부적으로 selector 스레드가 I/O를 하고, 호출 스레드는 결과만 기다립니다. 구조가 Netty와 비슷합니다.

그리고 더 근본적으로, **가상 스레드의 블로킹 소켓 읽기 자체가 JDK 내부에서는 논블로킹 소켓 + poller로 구현되어 있습니다.** 커널이 보는 그림은 이벤트 루프와 크게 다르지 않습니다. 차이는 완료 이벤트가 왔을 때 **가상 스레드를 재개하느냐, 이벤트 루프가 콜백을 실행하느냐**, 그리고 **대기 상태를 스택에 담느냐 객체에 담느냐**입니다.

## 상한에 걸렸을 때 무엇이 기다리는가

여기서 갈립니다.

| | 동기 REST + 가상 스레드 | WebClient (reactor-netty) |
|---|---|---|
| 연결을 못 얻으면 | 호출 스레드가 멈춰 대기. **스레드가 큐 역할** | 대기 요청이 풀의 pending 큐에 **객체로 등록**, 스레드 관여 없음 |
| 큐 크기 | 스레드 수만큼. 사실상 무제한 적체 | 유한(기본 `2×maxConnections`). 넘으면 즉시 실패 |
| 대기 제한 시간 | 연결 요청 타임아웃을 설정해야 함. 안 하면 무한 대기 | `pendingAcquireTimeout` 기본 45초 |
| 한 건당 대기 비용 | 가상 스레드 스택 (대략 수 KB~수십 KB) | 힙 객체 (수백 바이트 수준) |
| 취소 | 스레드 인터럽트 필요. 소켓 읽기 중이면 즉시 안 끊길 수 있음 | 구독 취소로 큐에서 빼고 연결 반환 |
| 풀 격리 | 구현체에 따라 다름. Apache는 전체 상한(기본 25)을 공유 | **호스트별 풀**이라 공급사끼리 자연히 격리됨 |

## 이 차이가 실제로 나타나는 지점

**1. 적체가 보이느냐, 안 보이느냐**

동시 검색 100건에 검색당 120청크면 대기 요청이 12,000건입니다.
- WebClient: 연결 16개 + pending 큐 32개를 넘는 순간 **예외로 즉시 실패**합니다. 부하가 상한을 넘었다는 사실이 바로 드러납니다.
- 동기 + 가상 스레드: 12,000개의 가상 스레드가 조용히 쌓여 기다립니다. 메모리는 수십~수백 MB로 늘고, 응답 시간만 길어집니다. 연결 요청 타임아웃을 설정하지 않았다면 장애가 "느려짐"으로만 나타나서 원인 찾기가 어렵습니다.

**2. 취소가 연결 반환 속도를 좌우한다**

연결이 병목일 때 실효 처리량은 "연결이 얼마나 빨리 반납되느냐"로 결정됩니다. Reactor는 전체 예산을 넘기면 구독을 취소해 진행 중인 호출을 끊고 연결을 즉시 돌려놓습니다. 동기 쪽은 포기해도 연결은 소켓 타임아웃이 터질 때까지 잡혀 있는 경우가 많습니다. **느린 공급사 하나가 연결을 오래 물고 있으면 그동안 다른 요청이 굶습니다.**

**3. 공급사 간 격벽**

reactor-netty 풀은 호스트별이라 공급사 A가 느려도 B 호출은 자기 연결을 씁니다. Apache HttpClient는 전체 상한을 공유해서, 라우트별 상한을 따로 설정하지 않으면 A가 25개를 다 먹고 B를 굶길 수 있습니다. 반대로 JDK HttpClient는 명시적 상한 개념이 약해서, 상한이 없는 대신 공급사 쪽 호출 한도(429)나 로컬 포트 고갈이 먼저 오기도 합니다.

**4. 구성 요소 수**

동기 방식에서 동시 실행 수를 제어하려면 세마포어나 크기 제한 executor를 따로 둬야 하고, 그 값과 커넥션 풀 상한 두 개가 서로 어긋나면 한쪽이 무의미해집니다. WebClient는 `flatMap`의 동시성 인자와 풀 상한을 맞추면 되고, 둘 다 같은 계층에 있습니다.

## 동기 REST 쪽의 진짜 장점

공정하게 반대편도 적겠습니다.

- **스레드 덤프에 호출별 스택이 그대로 남습니다.** 어디서 막혔는지 바로 보입니다. Reactor는 스택 트레이스가 연산자 체인이라 별도 장치를 붙여야 합니다.
- **이벤트 루프를 막을 위험이 없습니다.** WebClient에서는 응답 파싱이나 `map` 안의 변환이 이벤트 루프 스레드에서 돌기 때문에, 무거운 작업이 들어가면 전체 처리량이 떨어집니다. 동기 방식은 실수해도 자기 스레드만 느려집니다.
- **구성 요소가 적습니다.** 이벤트 루프, pending 큐, 구독 같은 개념을 몰라도 됩니다.

## 그래서 존재 이유가 있는가

요구사항을 빼고 보면, `MVC(가상) + WebClient`의 존재 이유는 **처리량이 아닙니다.** 규모가 작으면 둘 다 커넥션 풀이 상한이라 결과가 거의 같습니다. 남는 이유는 세 가지입니다.

1. **대기를 스레드가 아니라 객체로 담는다.** fan-out이 클수록 메모리와 스케줄링 비용 차이가 벌어집니다.
2. **상한을 넘었을 때의 동작이 명시적이다.** 유한 큐와 타임아웃으로 빠르게 실패하고, 취소가 연결을 즉시 회수하며, 풀이 공급사별로 격리됩니다.
3. **동시 실행 수·전체 예산·재시도·실패 수집을 한 계층에서 선언한다.** 별도 동시성 장치를 맞물릴 필요가 없습니다.

바꿔 말하면 이 선택지의 값어치는 "빠르다"가 아니라 **"과부하와 장애 상황에서 어떻게 행동할지가 코드에 적혀 있다"**입니다. 반대로 그 시나리오를 다루지 않는 규모라면 동기 REST + 가상 스레드가 더 단순한 게 사실이고, 그래서 회사가 WebClient를 지정으로 못 박아야 했던 것으로 보입니다.
```

```text
**3. 제어를 몇 개의 장치로 맞물려야 하는가** (능력이 아니라 표현)

동기 쪽에서 같은 동작을 만들려면 세마포어, 연결 요청 타임아웃, 소켓 타임아웃, 데드라인 계산, 결과 수집 코드가 서로 어긋나지 않게 맞물려야 합니다. 값이 하나만 어긋나면 다른 하나가 무의미해집니다. Reactor는 같은 계층에서 연산자로 적습니다. 이건 할 수 있느냐의 문제가 아니라 어디에 적히느냐의 문제입니다.
```

```text
| | MVC + WebClient | WebFlux |
|---|---|---|
| DB 접근 | JPA/JDBC 그대로 | R2DBC 또는 blocking 격리 |
| 트랜잭션 | `@Transactional` 그대로 | 리액티브 트랜잭션, 사용법이 다름 |
| 실행 준비물 | H2 하나면 끝 | H2+R2DBC의 성숙도 문제 또는 Docker |
```

```text
## 스레드 선택을 보류한 상태에서 생기는 비대칭

## MVC에만 남는 이점

**1. 블로킹 사고가 국소적입니다.** WebFlux에서 이벤트 루프를 막는 코드가 하나 들어가면 전역 처리량이 무너집니다. 위험원은 동기 라이브러리, 파일 로깅, 무거운 변환까지 넓고, 새 의존성을 추가할 때마다 다시 생깁니다. MVC에서는 같은 실수가 그 요청 하나만 느리게 만듭니다.

**2. 진단 도구가 그대로 작동합니다.** 스레드 덤프로 "지금 무엇이 어디서 막혀 있는지"를 볼 수 있습니다. WebFlux에서는 이벤트 루프 스레드 몇 개만 보이고 요청 상태는 힙 안에 있어서, 별도 계측을 붙이지 않으면 보이지 않습니다.

**3. JDBC 생태계를 그대로 씁니다.** 여기서 실무적으로 걸리는 게 스키마 마이그레이션입니다. Flyway나 Liquibase는 JDBC 기반이라, R2DBC로 앱을 짜도 마이그레이션용 JDBC 연결을 따로 둬야 합니다. 커넥션 풀도 두 벌이 됩니다. H2용 R2DBC 드라이버는 커뮤니티 관리라 성숙도도 한 단계 낮습니다.

**4. 유지보수 비용.** 이 코드를 고칠 사람이 Reactor에 익숙하지 않으면, 전 구간이 리액티브인 코드는 수정할 때마다 사고 확률이 붙습니다. MVC + WebClient는 그 위험이 공급사 호출 계층 안에만 있습니다.
```

```text
제가 "스레드는 병목 근처도 안 간다"고 단언했던 건 **풀을 기본값에 묶어 둔 상태에서만 참인 착시**였습니다. 풀을 정상적으로 사이징하면 스레드 수와 커넥션 수가 같은 자릿수로 움직입니다. 그 지점에서 "대기 중에 스레드를 붙잡느냐"가 실제 비용이 되고, 가상 스레드와 WebFlux 논의가 비로소 의미를 갖습니다.

곁들여 하나 더 정정하면, 플랫폼 스레드 비용도 제가 부풀렸습니다. 스택 1MB는 예약된 주소 공간이고 실제로 커밋되는 건 훨씬 작습니다. 수백에서 수천 개까지는 현실적입니다. 다만 그 구간부터는 컨텍스트 스위칭과 스케줄링 비용이 눈에 띄기 시작합니다.
```
