# 아키텍처

## 계층과 의존 방향

```
api      요청 검증, 응답 조립, 오류 변환
  ↓
search   검색 서비스. 표준 모델과 공급사 포트를 소유
  ↑                       ↑
supplier/a, supplier/b    mapping
공급사별 어댑터            매핑 저장소, 동기화, 스냅샷
```

- 표준 모델과 공급사 포트 인터페이스는 **도메인(search)이 소유**하고 어댑터가 구현합니다.
- 도메인은 어댑터 패키지를 import하지 않습니다. 이 규칙은 ArchUnit 테스트로 고정합니다.
- 공급사가 늘어도 도메인은 어댑터 목록을 주입받아 순회하므로 바뀌지 않습니다.

패키지 배치는 다음과 같습니다.

```
api/                컨트롤러, 요청·응답 표현, 오류 처리
search/             검색 서비스, 표준 모델(숙소·객실 타입·오퍼), 공급사 포트
supplier/a/         SupplierAAdapter(public), SupplierAMapper, A 응답 객체
supplier/b/         동일
mapping/            매핑 저장소, 숙소 목록 동기화, 메모리 스냅샷
```

## 실행 모델

**Spring MVC + 가상 스레드 + WebClient**를 씁니다. 공급사 호출은 WebClient로 만들고 Reactor로 조합한 뒤, **요청 경계에서 한 번만** 결과를 기다립니다.

- 어댑터는 `Mono`를 반환하고 내부에서 기다리지 않습니다. 호출 사이의 동시성, 전체 시간 예산, 취소, 부분 실패 수집을 Reactor가 계속 소유합니다.
- 호출마다 기다리면 이 제어를 스레드와 Future 쪽에서 다시 만들게 됩니다. 그래서 대기는 요청당 한 번으로 둡니다.
- 가상 스레드는 공급사 호출을 병렬화하는 수단이 아니라, 이 마지막 대기를 감당하는 실행 기반입니다. 외부 응답을 기다리는 요청이 고정된 플랫폼 워커 수에 먼저 묶이지 않습니다.
- 매핑 조회, 일반 업무 로직, 동기화 작업은 명령형 코드로 둡니다. Reactor를 반드시 써야 하는 범위를 공급사 호출 조합으로 좁혔습니다.

전면 리액티브(WebFlux)를 쓰지 않은 이유는 이 검색이 결과를 모두 모아 JSON 하나로 돌려주기 때문입니다. 연결 종료에 맞춘 취소 전파와 스트리밍이라는 이점보다, 동기 DB·일반 라이브러리를 그대로 쓰는 이점이 더 구체적이라고 판단했습니다. 결과를 흘려보내야 하거나 저장소까지 리액티브로 바꾸면 다시 비교할 지점입니다.

**Reactor 구간에서는 블로킹을 금지합니다.** 어댑터 내부나 콜백에서 DB 접근, 무거운 변환, 대기를 하지 않습니다.

## 어댑터 내부 구조

공급사 응답 처리를 세 단계로 나누고, 파싱과 변환 사이의 중간 상태를 타입으로 고정합니다.

```
HTTP 응답
  → [파싱] 공급사 응답 객체     스펙을 그대로 옮긴 형태. 로직 없음
  → [판정] 성공 / 실패          A는 HTTP 상태, B는 본문 결과 코드
  → [변환] 매퍼 → 표준 모델      검증, 합산, 버리기가 전부 여기
```

- **공급사 응답 객체**는 검증이나 계산을 넣지 않습니다. 생성 시점에 검증하면 파싱 실패와 변환 실패가 섞입니다. 표준 모델에서 버리는 필드도 공급사가 주면 선언해 둡니다. 무엇을 버리는지가 응답 객체와 매퍼의 차이로 코드에 드러납니다.
- **응답 객체는 어댑터 패키지 밖으로 나가지 않습니다.** 어댑터·매퍼·응답 객체를 한 패키지에 두고 응답 객체를 package-private으로 두어, 도메인이 쓰면 컴파일되지 않게 합니다.
- **매퍼는 순수 함수**입니다. 입력은 공급사 응답 객체와 검색 조건, 출력은 표준 모델입니다. HTTP도 Reactor도 모르므로 변환 규칙을 단위 테스트로 확인할 수 있습니다.

경계를 지키는 기준은 "새 클래스를 두느냐"가 아니라 **패키지 경계를 넘는 타입이 누구 것이냐**입니다. 도메인 소유 타입만 넘으면 경계가 지켜지고, 공급사 타입이 넘으면 어느 구조든 샙니다.

## 어댑터 결과

한 공급사 호출은 숙소 코드 50개씩 여러 묶음으로 나뉩니다. 그래서 결과는 성공과 실패 중 하나를 고르는 형태가 아니라, 둘을 함께 담습니다.

```java
record SupplierSearchResult(SupplierId supplier,
                            List<RoomOffer> offers,
                            List<ChunkFailure> failures) { }
// offers가 비고 failures만 있으면 그 공급사는 전부 실패
```

일부 묶음만 실패해도 성공한 묶음의 결과는 고객에게 보이고, 그 공급사는 응답의 실패 목록에 들어갑니다.

## 동시성과 커넥션 풀

| 제한 | 범위 |
|---|---|
| 검색 한 건 안에서 공급사별 동시 호출 수 | Reactor 연산자의 동시성 인자 |
| 공급사별 전역 동시 호출 상한 | 공급사마다 독립된 커넥션 풀의 상한으로 걸림 |
| 커넥션 획득 대기 한도 | 초과하면 그 묶음만 실패로 처리해 부분 실패로 흘림 |

커넥션 풀을 공급사마다 따로 두는 이유는 한 공급사가 느려질 때 그 대기가 다른 공급사 호출용 커넥션을 잠식하지 않게 하기 위해서입니다.

## 규모가 커질 때

보유 숙소가 3,000개이고 두 공급사가 절반씩 취급하면 검색 한 건이 60회 호출을 만듭니다. 처리량이 모자라면 인스턴스를 늘리고 앞단에 요청 분산 계층을 둡니다. 각 서버는 매핑 저장소를 빼면 요청-응답 사이클 바깥으로 상태를 갖지 않습니다. 인스턴스를 늘릴 때 함께 정해야 하는 것은 [범위 밖 설계](deferred-design.md)에 정리했습니다.
