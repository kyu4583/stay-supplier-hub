# 상품 단위와 판매 조건

- 날짜: 2026-09-17
- 상태: 결정 (세부 사항 일부는 숙소 목록 동기화·실패 판정·응답 계약·중복 병합 논제로 넘김)

## 논제

표준 모델에서 숙소·객실 타입·상품(오퍼)의 단위를 어떻게 잡을 것인가. 세부 쟁점은 셋이다.

1. 객실 타입 하나에 오퍼를 하나만 둘지, 여러 개를 허용할지
2. 숙소명·객실 타입명·최대 인원을 매핑 DB와 재고·요금 응답 중 어디서 가져올지
3. 공급사마다 다를 수 있는 조식 포함 여부를 어떻게 다룰지

## 모델 단위 (초안)

| 단위 | 식별 | 담는 것 | 출처 |
|---|---|---|---|
| 숙소 | 내부 숙소 ID ← (공급사, 숙소 코드) | 숙소명 | 매핑 DB 값에 조회 응답 값을 덮어씀 (쟁점 2) |
| 객실 타입 | 내부 객실 타입 ID ← (공급사, 숙소 코드, 객실 타입 코드) | 객실 타입명, 최대 인원 | 매핑 DB 값에 조회 응답 값을 덮어씀 (쟁점 2) |
| 상품(오퍼) | 객실 타입 + 판매 조건. 저장하지 않음 | 조식 여부, 요금, 예약 가능 수, 출처 공급사 | 재고·요금 조회 |

- 요금은 오퍼 단위로, 세금 포함 기간 총액과 통화를 둔다 ([표준 요금 기준](price-basis.md)).
- 재고는 공급사가 객실 타입 × 날짜로 준다. 응답에는 오퍼마다 기간 전체 예약 가능 수를 둔다. 판정 규칙은 연박 예약 가능 수 논제에서 정한다.

## 결론

### 쟁점 1 — 결정: 객실 타입 아래 오퍼 여러 개를 허용한다

- 응답은 객실 타입 아래에 오퍼 배열을 둔다. 지금 데이터에서는 배열 길이가 항상 1이다.
- 중복 병합 여부와는 무관하게 성립한다. 병합하지 않으면 공급사마다 객실 타입이 따로 있고, 각각 오퍼가 하나씩 달린다.

### 쟁점 2 — 결정: 매핑 DB 값을 기본으로 채우고, 조회 응답에 값이 있으면 덮어쓴다

- 숙소명·객실 타입명·최대 인원은 먼저 매핑 DB 값으로 채운다.
- 재고·요금 응답에 같은 값이 있으면 필드마다 따로 판단해 응답 값으로 덮어쓴다.
- 공급사가 재고·요금 응답에서 이 값들을 빼고 코드만 주면 매핑 DB 값이 그대로 쓰인다.
- 덮어쓴 값은 응답에만 쓰고 매핑 DB에 되쓰지 않는다. 매핑 갱신은 숙소 목록 동기화가 맡는다.
- 구현 위치: 매퍼는 DB를 모르므로, 통일 형식에 이 값들을 선택 필드로 담는다. 덮어쓰기 규칙은 매핑을 이미 들고 있는 검색 서비스(도메인)에서 한 번만 적용한다.
- 조회 응답의 항목은 (공급사, 숙소 코드, 객실 타입 코드)로 매핑과 맞춘다. 객실 타입 코드는 숙소 안에서만 유일하므로 숙소 코드와 함께 쓴다. 재고·요금 응답에 두 코드가 모두 온다.
- 가정: 한 공급사의 한 번의 응답에서 같은 (숙소 코드, 객실 타입 코드)는 한 번만 온다. README의 가정 목록에 적는다. 그래서 같은 객실 타입의 오퍼들이 서로 다른 이름을 줄 때의 규칙은 두지 않는다(논의 흐름 6, 7).
- 가정이 깨졌을 때의 대응 (지금 구현하지 않고 기록만 한다): 같은 코드로 온 항목을 모두 오퍼로 응답에 담는다. 예약 요청 때 코드 외의 값도 함께 보내 서버가 어느 항목인지 구분하게 한다. 그때 객실 타입 단위의 이름·최대 인원을 어느 항목 값으로 덮어쓸지도 함께 정한다.
- 매핑에 없는 객실 타입 코드가 조회 응답에 오면 (사용자 제안, 결정):
  - 그 검색의 응답에서는 해당 항목을 뺀다. 응답 최소 요건이 요구하는 내부 객실 타입 식별자가 없기 때문이다.
  - 즉시 그 공급사의 숙소 목록 동기화를 요청해, 이후 검색부터는 새 객실 타입이 응답에 포함되게 한다.
  - 트리거의 세부 조건은 Claude가 제안했고, 숙소 목록 동기화 논제에서 확정한다(논의 흐름 8).

### 쟁점 3 — 결정: 조식 여부는 오퍼의 조건 필드로 두고 가격은 보정하지 않는다

- `breakfastIncluded`를 객실 타입이 아니라 오퍼에 두고, 요금 옆에 보인다.
- 조식 여부로 가격을 보정하지 않는다. 받은 가격을 그대로 보이고 조건을 나란히 보여, 고객이 "429,000원 조식 불포함"과 "452,000원 조식 포함"을 조건째 비교하게 한다.
- 조건을 `conditions` 같은 객체로 묶지 않고 필드 하나로 둔다.

## 근거

### 쟁점 1

1. 평평한 목록을 중첩 구조로 바꾸는 것은 API 사용자를 깨뜨리는 변경이다. "나중에 쉽게 추가할 수 있으면 그때 넣는다"는 기준은 필드 추가에는 맞지만, 구조 변경에서는 반대 방향을 가리킨다. 지금 치르는 비용은 배열 한 단계다.
2. 같은 객실 타입의 요금제 여러 개(예: 조식 포함/불포함)와, 중복 병합을 할 때 한 객실 타입 아래 놓이는 두 공급사의 오퍼를 모두 구조 변경 없이 담을 수 있다. 다만 쟁점 2에서 "한 응답에서 같은 키는 한 번만 온다"고 가정했으므로, 같은 공급사의 요금제 여러 개는 지금은 가정이 깨졌을 때의 대응으로만 남는다.
3. 스펙 데이터는 객실 타입당 한 줄이므로, 이 선택은 스펙에 나오지 않는 경우까지 대비하는 것이다. 그 점을 알고 선택했다.

### 쟁점 2

1. 공급사는 재고·요금 응답에서 "이 숙소의 이 객실은 최대 인원이 몇이고 재고가 얼마"를 한 묶음의 사실로 준다. 우리는 요금 합산, 예약 가능 수 계산처럼 값을 변환하기는 하지만, 공급사의 현재 사실 안에 우리가 지난 동기화 때 찍어 둔 값을 섞어 넣으면 안 된다.
2. 특히 최대 인원은 공급사가 요청 인원을 수용하는 객실만 고른 기준이다. DB 값만 쓰면 동기화 전까지 "3인 검색 결과에 최대 2인"이 표시되는 모순이 생길 수 있는데, 응답 값으로 덮어쓰면 사라진다.
3. 공급사가 실수하지 않는다는 전제에서는 늘 최신 값을 보인다.
4. 이후 추가되는 공급사가 "정적 정보는 목록 API로 줬으니 재고 API에는 코드만 준다"고 해도 일리 있는 설계다. 덮어쓰기 방식은 이런 공급사에서도 매핑 DB 값으로 동작한다.

### 쟁점 3

1. 조식은 방의 속성이 아니라 그 가격에 딸린 판매 조건이다. 같은 객실이라도 공급사마다 다를 수 있으므로 오퍼에 둔다.
2. 조식을 뺀 가격으로 환산하려면 조식 가격이 필요한데 두 공급사 모두 주지 않는다. 보정할 근거가 없으니 조건을 보이는 것으로 비교 가능성을 확보한다.
3. 조건이 늘어도 필드 추가는 API 사용자를 깨뜨리지 않으므로 지금 객체로 묶을 이유가 없다. 쟁점 1에서 배열 구조를 미리 둔 이유(구조 변경은 사용자를 깨뜨림)와 같은 기준을 반대 방향으로 적용한 결과다.

## 논의 흐름

1. Claude가 모델 단위 초안과 세 쟁점을 냈다.
   - 쟁점 1에서 (A) 객실 타입당 오퍼 1개와 (B) 여러 개 허용을 비교해 (B)를 추천했다. 스펙 데이터는 객실 타입당 한 줄이라 스펙에 없는 경우를 대비하는 선택임을 밝혔다.
   - (B)가 떠안는 비용으로, 같은 공급사의 요금제 오퍼끼리는 같은 객실 재고를 나눠 쓰므로 예약 가능 수를 더하면 안 된다는 점을 들었다.
   - 쟁점 2에서 (가) 매핑 DB와 (나) 조회 응답을 비교해 (가)를 추천했다. 검색이 매핑을 이미 읽으므로 추가 조회가 없고, 내부 ID에 붙는 값을 우리 마스터에서 가져온다는 이유였다. 대신 동기화 전까지 변경이 늦게 반영되고, "3인 검색에 최대 2인" 같은 모순이 생길 수 있다는 위험을 밝혔다.
2. 사용자가 (B)에 동의했다. Claude 근거가 타당하다고 보고, 논거를 하나 더했다.
   - 같은 객실을 별개 객실처럼 나눠 응답하면 두 재고를 더한 값이 최대 예약 가능 수로 오인될 수 있다.
   - 그러니 "같은 객실이 다른 공급사에서 온다"는 사실을 우리 계층에서 지워서 보낼 의무가 있다. 같은 객실은 합치고 옵션은 배열로 담는 게 옳다.
3. Claude가 (B) 결정과 이 논거를 분리했다.
   - 재고 합산이 틀릴 수 있다는 위험은 인정했다. 호텔이 여러 판매 채널에 같은 재고를 공유해 내보내면 A의 1실과 B의 1실은 같은 방 하나일 수 있다. 채널마다 따로 할당했다면 합계 2실이 맞다. 우리는 어느 경우인지 알 수 없다.
   - 합치는 것만으로는 이 위험이 사라지지 않는다고 반박했다. 합치면 두 오퍼가 한 객실 타입의 배열 안에 나란히 놓여 오히려 더하기 쉬워진다. 오인을 막는 것은 "예약 가능 수는 오퍼 단위이며 오퍼끼리 더할 수 없다"는 필드 정의다.
   - 합칠 의무가 있는지는 중복 병합 논제의 질문이라고 했다. 이후 논의는 [중복 상품 병합](duplicate-merge.md)으로 옮겨 이어졌다.
4. 사용자가 쟁점 2에 대해 (가)와 (나)를 결합한 방식을 제안했다.
   - 매핑 DB 값으로 응답 값을 채워 두고, 재고 응답에 숙소명·객실명·최대 인원 중 있는 값이 있으면 그 값으로 덮어쓴다.
   - 공급사가 실수하지 않는다는 전제에서는 늘 최신의 신뢰할 수 있는 값을 보인다.
   - 공급사는 이름·최대 인원·재고를 하나의 원자적 정보로 묶어 주는데, 우리 영역에서 그 원자성을 깨고 값을 바꾸는 것은 틀렸다.
   - 이후 공급사가 재고 API에서 정적 정보를 빼고 키만 줘도 일리 있는 설계이므로, 그때도 DB 값이 쓰이도록 덮어쓰기 방식을 쓴다.
5. Claude가 받아들이고 (가) 추천을 철회했다.
   - 자신이 (가)의 위험으로 든 최대 인원 모순이 이 방식에서는 사라지고, 정적 정보를 빼는 공급사도 처리된다는 점을 들었다.
   - 원자성 논거를 다듬었다. 값을 변환하는 것 자체는 이미 하는 일(합산, 최솟값)이고, 문제는 공급사의 현재 사실 안에 우리의 지난 스냅샷을 섞는 것이다.
   - 구현 위치를 정리했다. 매퍼는 DB를 모르므로 통일 형식이 이 값들을 선택 필드로 담고, 덮어쓰기는 도메인에서 필드별로 한 번 한다.
   - 경계 사례 두 가지를 냈다. 같은 객실 타입 아래 같은 공급사 오퍼들의 값이 서로 다르면(공급사가 요금제 설명을 객실명에 섞는 경우) 그 필드는 DB 값을 쓰자고 제안했다. 병합하면 한 객실 타입에 A·B 오퍼가 함께 놓여 덮어쓸 값이 둘이 되므로, 중복 병합 논제에서 다시 보자고 했다.
6. 사용자가 "요금제 설명을 객실명에 섞어 주는 경우"가 스펙에 언급됐는지 물었다.
   - Claude가 스펙에 없는 예시였다고 확인했다. 실무 연동에서 볼 수 있는 형태라는 일반 지식에서 가져왔고, 이 두 공급사에 대해 확인한 사실이 아니다.
   - 스펙은 요금·재고가 객실 타입 단위라고 하고 예시 데이터도 객실 타입당 한 항목이다. 조식이 다를 수 있다는 언급도 같은 공급사 안이 아니라 공급사 사이의 차이다. 따라서 "같은 공급사가 한 객실 타입에 여러 오퍼를 주는 경우" 자체가 스펙 데이터에는 나오지 않는다.
   - Claude가 이 예시를 세부 규칙의 근거에서 철회했다. 남는 근거는 구조 (B)가 이 경우를 담을 수 있게 열어 두었으므로, 규칙을 정하지 않으면 구현이 첫 항목 값 같은 임의의 값을 조용히 고르게 된다는 점뿐이다.
7. 사용자가 규칙을 두지 않기로 했다.
   - 객실 타입 코드라는 고유키가 재고 응답에도 오니 그걸로 매칭하면 된다. 고유키가 같은 항목이 조금씩 다른 형태로 여러 개 오는 경우는 없다고 가정한다. 고유키가 있는데 그렇게까지 하는 공급사를 가정할 이유가 없다.
   - 그런 경우가 실제로 생기면 모두 응답에 담고, 이후 예약 요청 때 고유키 외의 값도 실어 보내 서버가 구분하게 한다. 이건 문제가 생겼을 때 적용할 사항으로 기록만 한다.
   - Claude가 보탰다. 객실 타입 코드는 숙소 안에서만 유일하므로 매칭 키는 숙소 코드와 함께 쓴다. 가정을 어긴 응답이 실제로 왔을 때 지금의 코드가 어떻게 반응할지(검증 항목으로 볼지)는 실패 판정 논제에서 본다. 가정이 깨졌을 때 모두 응답에 담는 대응은 구조 (B)의 오퍼 배열에 그대로 담긴다.
8. 사용자가 새 경우를 제안했다. 매핑 DB에 없는 객실 타입 코드가 재고 응답에 오면, 그 응답을 받을 사용자에게는 해당 객실 타입을 빼고 주고, 즉시 매핑 DB 갱신을 트리거해 이후 사용자는 새 객실 타입을 받게 한다.
   - Claude가 받아들였다. 검색 중에 응답 값으로 매핑을 바로 만드는 대안은 두 가지 이유로 제외했다. 검색 경로에서 DB에 쓰게 되어 동시 검색끼리 같은 행을 두고 경합하고, 재고 API에 정적 정보를 주지 않는 공급사에서는 이름·최대 인원이 없어 만들 수 없다. 사용자 제안은 "정적 정보는 목록 API에서 온다"는 원칙과 쟁점 2의 근거 4에 맞는다.
   - 트리거 조건 세 가지를 제안했다.
     - 검색 응답을 기다리게 하지 않는다. 동기화는 요청과 분리해 실행하고, Reactor 콜백 안에서 DB를 건드리지 않는다.
     - 공급사별로 한 번만 돈다. 숙소 목록 API는 조건 없이 전체 목록을 주므로, 동시 검색 여러 건이 같은 새 코드를 보고 각자 트리거하면 전체 목록 호출이 겹친다. 이미 진행 중이거나 최근에 돌았으면 건너뛴다.
     - 동기화 후에도 코드가 목록에 없으면 계속 다시 트리거하지 않는다. 목록 API와 재고 API가 어긋나는 공급사라면 검색마다 전체 목록을 부르게 되므로, 최소 간격을 두고 이상 신호로 기록한다.
   - 구분할 경우 하나를 덧붙였다. 매핑에 없는 숙소 코드가 오는 것은 새 객실 타입과 다르다. 우리가 요청하지 않은 숙소이므로 응답 이상이며, 실패 판정 논제에서 다룬다.
9. 쟁점 3은 Claude가 세 가지(오퍼에 둔다, 가격 보정 없음, 객체로 묶지 않음)를 스펙 참고 사항 예시와 응답 모양 예시로 설명했고, 사용자가 그대로 받아들였다.

## 남은 사항

- 매핑에 없는 객실 타입이 왔을 때의 동기화 트리거 조건(요청과 분리, 공급사별 중복 방지, 반복 트리거 방지)은 숙소 목록 동기화 논제에서 확정한다. 인스턴스가 여러 개일 때 중복 방지를 어떻게 할지도 그때 본다.
- "한 응답에서 같은 코드는 한 번만 온다"는 가정을 어긴 응답과, 요청하지 않은 숙소 코드가 온 응답의 처리는 실패 판정 논제에서 다룬다.
- 병합한 객실 타입에서 덮어쓸 값은 우리 쪽 대표 값을 쓴다. 병합은 설계로만 두기로 했다 ([중복 상품 병합](duplicate-merge.md)).
- 조회 응답 값이 매핑 DB 값과 다르면 동기화 지연 신호로 쓸 수 있다. 연동 지표 논제에서 다룬다.
- 응답의 최대 인원이 요청 인원보다 작으면 "수용 가능한 객실만 준다"는 공급사 약속과 어긋난다. 이런 항목의 처리는 실패 판정 논제에서 다룬다.
- 예약 가능 수를 오퍼끼리 더할 수 없다는 점을 응답 계약에 어떻게 드러낼지는 응답 계약 논제에서 정한다.
