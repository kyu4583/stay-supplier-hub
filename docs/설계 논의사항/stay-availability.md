# 연박 예약 가능 수와 예약 불가 상품

- 날짜: 2026-09-17
- 상태: 결정

## 논제

여러 박을 검색할 때 공급사가 주는 날짜별 잔여 객실 수로 기간 전체의 예약 가능 수를 어떻게 정할 것인가. 공급사 응답의 날짜 목록이 요청한 숙박일과 맞지 않으면 어떻게 할 것인가. 예약 가능 수가 0인 상품을 응답에서 뺄 것인가, 0으로 보일 것인가.

## 결론

### 예약 가능 수의 정의 (쟁점 아님)

- 요청한 숙박일(체크인일부터 체크아웃 전날까지) 각각의 잔여 객실 수 중 최솟값으로 한다.
- 예: 9/1~9/4 검색에서 A Riverside Deluxe Twin은 3·1·5라 1, A Namsan Standard Double은 2·0·4라 0(예약 불가).
- 방 k개를 기간 내내 쓰려면 매일 k개가 남아 있어야 하므로, 가장 적게 남은 날이 한계다. 첫날 기준이나 평균은 어느 하루에 방이 모자라도 예약 가능하게 보인다. 선택지가 갈리는 판단이 아니라 README에 적을 정의다.
- 계산은 어댑터가 아니라 검색 서비스(도메인)에서 한 번 한다 ([공급사 어댑터 계층](supplier-adapter-layer.md)).

### 날짜 목록이 요청 숙박일과 맞지 않는 응답 — 결정

- 상품 항목의 날짜 목록이 요청 숙박일 집합과 정확히 같지 않으면, 그 항목을 변환 실패로 보고 응답에서 뺀다.
  - 빠짐: 요청 {9/1, 9/2, 9/3}에 {9/1, 9/3}이 옴
  - 넘침: {9/1, 9/2, 9/3, 9/4}처럼 체크아웃일 등이 섞임
  - 중복: 같은 날짜가 두 번 옴
- 스펙은 날짜 목록이 체크인일부터 체크아웃 전날까지라고만 한다. 이 경우들은 공급사가 그 약속을 어기는 상황을 가정한 것이다.
- 날짜 검사는 공통 코드 하나로 두고 각 공급사 매퍼가 쓴다. A는 요금 합산에도 이 검사가 전제이므로 매퍼 단계에서 해야 한다.
- 이 규칙으로 [표준 요금 기준](price-basis.md)에서 넘긴 "A 요금은 모든 숙박일이 있을 때만 합산한다"는 전제도 정해졌다.

### 예약 불가 상품의 노출 방식 — 결정: 오퍼째 0으로 보인다

- 예약 가능 수가 0인 오퍼도 응답에서 빼지 않고, 요금·조식 여부 등을 담은 채 예약 가능 수 0으로 보인다.
- 예: 9/1~9/4 검색에서 Namsan Garden Stay의 Standard Double은 A 오퍼 하나가 예약 가능 수 0으로 나온다.
- 응답의 0은 "요청 기간 중 어느 날 실제로 매진"이라는 뜻만 갖는다. 날짜가 맞지 않는 항목은 위 규칙으로 이미 빠지기 때문이다.
- 예약 가능 여부 boolean 필드는 두지 않는 방향으로 Claude가 제안했다. 사용자가 따로 답하지 않았으므로 응답 계약 논제에서 필드를 정할 때 확정한다.

## 근거

### 날짜 불일치 처리

1. 날짜가 맞지 않는 응답은 공급사의 의도를 알 수 없다. 빠진 날을 0으로 보거나 있는 날짜만으로 계산하는 것은 모두 그 의도를 추측하는 것이다.
2. 빠진 날을 재고 0으로 보면 데이터 결함과 실제 매진이 구분되지 않아, 응답의 0이 뜻하는 바가 흐려진다. A는 요금도 계산할 수 없다.
3. 있는 날짜만으로 계산하면 재고를 모르는 날이 있는데 예약 가능으로 보이고, A 요금은 실제보다 싸게 나간다.
4. 넘침을 너그럽게 받으면 안 되는 이유: 공급사가 기간을 4박으로 해석했다면 B의 총액도 4박 기준일 수 있는데, 우리는 이를 가려낼 수 없다. 금액 오류로 이어진다.

### 예약 불가 상품의 노출 방식

1. 스펙은 예약 불가 상품을 빼는 것과 0으로 노출하는 것을 모두 허용한다. 응답 최소 요건도 0을 예약 불가로 보고 예약 가능 여부 boolean 필드를 선택으로 두는데, 이는 0인 상품이 응답에 들어올 수 있다는 전제다. 사용자는 이를 "예약 불가라는 사실을 UI로 구분한 채 숙소 정보는 화면에 띄울 수 있게" 가능성을 연 것으로 읽었다.
2. 매진인 객실도 보이는 쪽이 고객 경험에 낫다. 모든 객실이 매진인 숙소가 결과에서 통째로 사라지면 우리가 취급하지 않는 숙소와 구분되지 않는다.
3. 나중에 바꿀 때 깨지는 방향이 다르다. 0으로 보이다가 빼는 쪽으로 바꾸면 0을 거르던 쓰는 쪽은 그대로 동작하지만, 빼다가 0을 보이게 바꾸면 "응답에 있으면 예약 가능"을 전제한 쓰는 쪽이 깨진다.
4. 페이징이 범위 밖이라 최악의 응답 크기는 어차피 보유 숙소 전부가 예약 가능할 때와 같다. 빼는 방식은 평소 크기만 줄인다.

## 검토한 선택지 (날짜 불일치)

| 방식 | 판단 |
|---|---|
| (가) 빠진 날을 재고 0으로 본다 | 제외. 근거 2 |
| (나) 있는 날짜만으로 계산한다 | 제외. 근거 3 |
| (다) 날짜 목록이 요청 숙박일과 정확히 같지 않으면 항목을 변환 실패로 뺀다 | 선택 |

(다)의 비용: 공급사가 날짜를 넉넉히 주는 방식이면 그 공급사 상품이 전부 빠진다. 변환 실패 기록과 지표로 드러나게 해야 한다.

## 검토한 선택지 (예약 불가 상품)

| 방식 | 판단 |
|---|---|
| (1) 0인 오퍼를 빼고, 오퍼가 모두 빠진 객실 타입·숙소도 뺀다 | 제외. 매진 숙소와 취급하지 않는 숙소가 구분되지 않는다 |
| (2) 오퍼째 예약 가능 수 0으로 보인다 | 선택 |
| (3) 0인 오퍼는 거르고, 객실 타입 단계에 예약 가능 수를 두어 오퍼가 다 걸러지면 0으로 보인다 | 제외. 오퍼 배열에 살 수 있는 선택지만 남는 장점이 있지만, 예약 가능한 오퍼가 있을 때 객실 타입 값을 어떻게 계산할지 새로 정해야 하고, 병합하면 미결인 재고 합산 문제가 돌아온다. 매진 객실 타입의 요금이 빈다 |

## 논의 흐름

1. Claude가 세 쟁점을 냈다: 예약 가능 수 계산 규칙(최솟값), 날짜가 맞지 않는 응답의 처리, 예약 불가 상품을 뺄지 0으로 보일지.
2. 사용자가 첫 번째는 정답이 하나뿐인데 쟁점이라고 할 여지가 있느냐고 지적했다.
   - Claude가 동의했다. 선택지가 갈리는 논제가 아니라 README에 적을 정의이며, 쟁점으로 올린 것은 분류 실수라고 했다. 음수 재고 같은 값 검증은 실패 판정 논제에 속한다고 덧붙였다.
3. 날짜 불일치 처리에서 Claude가 (가)·(나)·(다)를 비교해 (다)를 추천했다.
   - 이 경우가 스펙에 나오지 않는 가정임을 밝혔다.
   - 넘침을 너그럽게 받지 않는 이유로, 공급사가 기간을 다르게 해석했다면 B 총액도 그 기준일 수 있다는 점을 들었다.
4. 사용자가 (다)에 동의했다. 그런 응답은 의도를 알 수 없으니 에러로 처리하는 게 맞고, Claude가 짚은 것처럼 금액 문제로 이어지기도 한다는 이유였다.
5. 예약 불가 상품에 대해 Claude가 "0으로 보이고 boolean 필드는 두지 않는다"를 추천했다. 근거는 바꿀 때 깨지는 방향, 응답 크기가 결정적이지 않다는 점, 0의 뜻이 깨끗하다는 점이었다.
6. 사용자가 "예약 가능 수가 0인 상품은 응답에 포함할 수 없는 걸러야 할 대상"이라며, Claude가 응답에 예약 가능 객실 수 필드를 넣는 얘기와 헷갈린 것 아니냐고 물었다. 0인 상품만 있을 때 응답의 예약 가능 객실 수 필드가 0이 되어야 한다고 했다.
7. Claude가 답했다.
   - 스펙에서 예약 가능 객실 수는 상품마다 붙는 값이고, 예약 불가 상품을 빼든 0으로 노출하든 자유라고 명시돼 있다. 그래서 "걸러야 할 대상"은 두 선택지 중 하나다.
   - 다만 응답 구조가 객실 타입 → 오퍼 두 단계인데 예약 가능 수를 어느 단계에 두는지 말하지 않은 것이 설명의 빈틈이었다고 인정했다.
   - 사용자의 말을 (3)으로 이해하고, Namsan 예시로 (1)·(2)·(3)을 나란히 보인 뒤 뜻을 확인했다.
8. 사용자가 이해했다고 하고 (2)를 택했다. 응답 최소 요건은 예약 불가라도 그 사실을 UI로 구분한 채 숙소 정보를 화면에 띄울 수 있도록 가능성을 연 것으로 보이고, 그쪽이 더 좋은 UX라고 봤다.

## 남은 사항

- 예약 가능 여부 boolean 필드를 둘지는 응답 계약 논제에서 확정한다.
- 예약 가능 수는 오퍼 단위이고 오퍼끼리 더할 수 없다는 점을 API 문서에 적는다. 응답 계약 논제에서 함께 다룬다.
- 날짜가 맞지 않는 항목을 항목 단위 실패로 볼지 공급사 응답 전체 실패로 볼지, 어디에 기록할지는 실패 판정·정규화 실패 격리 논제에서 정한다.
- 음수 재고 같은 값 검증은 실패 판정 논제에서 다룬다.
