- Mock은 AI로 빠르게 만들되, 타임아웃, 부분실패 구현도 테스트 가능하도록은 해야함. Mock의 데이터 다양성이 중요한 부분은 아니라 할지라도 메인 구현을 테스트하는 용도로 의미가 있기 때문에 아예 던져버리면 안됨.

- 외부 API에서 2XX 응답이 아닌 경우 1차로 거르고, 2XX 응답 내에서도 성공 여부를 거르는 2차 구조 필요

- 현재는 공급자가 2개뿐이지만, 지금 연동 대상이 2개일 뿐 실제 상황에선 2개보다 많고 또한 얼마든지 추가될 수 있음을 고려하면 좋을 듯 함. 따라서 요구사항 외적으로도 유연성/확장성을 더 추구하면 좋을듯.

- 재고·요금 조회는 한 번에 숙소 코드 50개까지만 받고 넘기면 오류다. 예시 데이터는 숙소가 적어 걸리지 않지만, 숙소가 수천 개로 늘 때 어떻게 할지를 설계 문서에 남겨야 한다.

- 숙소 목록 API를 언제 호출할지(미리 한 번, 주기적으로, 검색할 때마다 등)는 직접 판단하고 근거를 적어야 한다.

  - 자주 바뀌지 않는다는게 중요.

- 두 공급사가 같은 숙소를 취급해도 그 사실을 알려주는 공통 키가 없다. 동일 숙소 여부는 숙소명·객실 구성 등으로 직접 추정해야 한다.

  - 숙소명 유사도 계산해야할수도?
  - 일단 기록해두는 몹쓸 아이디어: 같은 숙소 의심되면 예약-조회-취소-조회로 같은 숙소 맞는지 확인 가능하긴함

- DB 조회(숙소 목록)시 로컬 캐싱 하면 좋을듯
