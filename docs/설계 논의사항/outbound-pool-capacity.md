# 아웃바운드 커넥션 풀 용량

- 날짜: 2026-09-13, 갱신 2026-09-16, 2026-09-17
- 상태: 결정 — 초기 풀 상한 목표 약 2,500개. 실제 설정과 부하 검증은 아직 수행하지 않았다.

## 논제

공급사 수용량을 충분히 알지 못하는 단계에서 아웃바운드 풀을 작게 유지할 것인지, 우리 서버의 높은 동시 처리 용량을 먼저 확보할 것인지.

## 결론

- 사용자는 Netty 아웃바운드 커넥션 풀 상한을 우선 약 2,500개로 높이는 방향을 선택했다.
- 이번 MVC(VT on) 대 WebFlux 비교에서는 동일한 풀 설정을 전제로 한다. `maxConnections`의 일반적인 적용 단위인 목적지별 풀 하나의 상한으로 해석한다. 
- 2026-09-17 적용 단위를 확정했다. 커넥션 풀은 공급사마다 독립으로 두고 상한도 공급사별 설정값으로 둔다. 한 공급사의 지연이 다른 공급사 호출용 커넥션을 잠식하지 않게 하기 위해서다. 전체 합계는 공급사 수 × 상한이 된다. [50개 한도와 수천 개 규모](chunking-and-scale.md)에 따른다.
- 2,500은 연결 최대 허용치의 초기 목표이며, 연결 선생성 수·검색 동시 처리 수·초당 처리량·검증된 최적값이 아니다.
- 공급사 수용량이 부족한 상황의 대응 설계는 추후 검토한다. 정보가 없는 공급사의 한도를 임의로 낮게 가정하여 이번 실행 모델 비교를 제한하지 않는다.

## 근거

- 풀의 상한은 조정 가능한 소프트웨어 정책이다. 이를 Netty의 구조적 한계로 취급할 근거가 없다.
- 공급사 응답 대기와 검색당 호출 분할이 겹치면 큰 동시 연결 수가 필요할 수 있다.
- 수천 단위 WebClient 풀 설정과 부하 테스트의 공개 보고가 있다. 다만 그것만으로 이 서버에서 2,500개가 적정하다고 검증된 것은 아니다.

## 논의 흐름

- Claude는 기본 풀 크기를 고정된 하류 병목처럼 취급해 플랫폼 스레드 제한의 영향이 작다고 주장했다.
- 사용자는 풀도 늘릴 수 있으며, 관측하지 않은 공급사 한도로 우리 처리량을 제한할 이유가 없다고 반박했다.
- Codex는 TCP 자원 한도와 설정 한도, 연결 재사용, 임시 포트 제약을 구분해 설명했다. 큰 풀의 실제 사용 보고를 조사하면서 설정값·활성 연결 수·안정 운영 실적을 구분했다.
- 사용자는 이를 바탕으로 약 2,500개를 초기 목표로 정했다. 높은 아웃바운드 동시성을 활용하는 방향에서 MVC(VT off)를 제외하고 MVC(VT on)과 WebFlux를 비교하기로 했다.
- 2026-09-16 사용자가 MVC(VT on) + WebClient를 최종 선택했다. 풀 상한의 초기 목표는 유지한다.
- 2026-09-17 50개 분할과 동시 호출 제한을 정하면서 적용 단위를 공급사별 독립 풀로 확정했다. 커넥션 획득 대기 한도를 두고, 초과한 묶음은 부분 실패로 흘린다.

## 남은 위험과 재검토 조건

- OS/프로세스의 자원 한도, 인스턴스 수, 목적지·프록시 구성을 구현 시 확인한다.
- 연결 획득 대기와 대기 시간, 활성·유휴 연결, 성공 처리량, 응답 지연, 연결 생성·종료 빈도로 목표를 검증한다.
- 공급사 거절·지연 증가가 관측되면 공급사별 동시성·호출률 조정과 재시도 정책 등을 재검토할 수 있다. 구체 정책은 아직 결정하지 않았다.
- 풀을 높였다는 사실만으로 Tomcat 플랫폼 스레드가 실제 첫 병목이라는 측정 결과가 생기는 것은 아니다.
