# Mock 공급사 구성

- 날짜: 2026-09-17
- 상태: 결정

## 논제

Mock을 시연용과 테스트용으로 나눌 것인가, 하나로 합칠 것인가.

## 결론

역할을 나눈다.

| 용도 | 방식 |
|---|---|
| 손으로 시연 (README 실행 절차, 장애 재현) | 별도 Gradle 모듈로 띄우는 Mock 서버, 9090 포트 |
| 자동 테스트 | 테스트 안에서 WireMock 또는 MockWebServer로 응답을 코드로 통제 |

시연용 Mock에 예시 뼈대에서 더할 것:

1. 요청한 날짜와 숙소 코드를 반영해 응답을 만든다.
2. 지연 모드(N초 뒤 정상 응답)를 더한다.
3. 숙소 목록 API에도 장애 모드를 넣는다.
4. 숙소를 50개 넘게 만드는 옵션을 둔다. 분할과 부분 실패가 실제로 도는 것을 보이기 위해서다.

## 근거

1. 고정 응답을 주는 Mock은 우리 검증 규칙과 충돌한다. 날짜 목록이 요청 숙박일과 정확히 같아야 하고 요청하지 않은 숙소 코드는 빼기로 했으므로, 스펙 예시 날짜가 아닌 조건으로 검색하면 전부 걸러져 빈 결과가 된다. 규칙이 제대로 동작한 결과인데 보는 사람은 고장으로 읽는다.
2. 요청을 반영하는 응답은 손으로 쓴 컨트롤러 쪽이 훨씬 싸다. WireMock 응답 템플릿으로도 되지만 날짜 배열을 만드는 표현식이 번거롭다.
3. 테스트는 "30묶음 중 2개만 실패", "응답 3초 지연", "B가 200 + 오류 코드" 같은 상황을 정확히 통제해야 한다. 상태를 가진 공용 Mock 서버를 테스트가 공유하면 테스트 간 간섭이 생긴다.
4. Mock 자체의 품질은 중요하지 않지만, 연동 동작을 검증하는 수단으로는 쓰인다. 저장소를 처음 받은 사람이 앱을 띄워 검색해 볼 수 있는 경로가 있으면 핵심 흐름이 도는 것을 바로 보일 수 있다.
5. 비용은 도구가 둘이고 스펙이 바뀌면 양쪽을 고쳐야 한다는 점이다. 사용자가 이 비용을 알고 확실한 역할 분리를 택했다.

## 검토한 선택지

| 방식 | 판단 |
|---|---|
| (가) 테스트 전용 하나. 시연은 테스트 실행으로 대신 | 제외. 저장소를 받은 사람이 앱을 직접 돌려 볼 경로가 없다 |
| (나) WireMock 하나를 매핑 파일로 두고 테스트와 standalone에서 같이 사용 | 제외. 근거 1·2 |
| (다) 별도 모듈 서버 + 테스트용 스텁 | 선택 |

## 논의 흐름

1. Claude가 세 선택지를 제시하고 처음에는 (나)를 추천했다.
2. 사용자가 수동 시연이 꼭 필요한지 물으며 테스트용 하나로 합치는 쪽을 제안했다. Claude가 요구사항 기준으로 수동 시연은 필수가 아니지만 앱을 띄워 볼 경로가 사라진다는 점을 짚었다.
3. 사용자가 (나)와 (다)를 더 비교해 달라고 했다. 비교 과정에서 고정 응답 Mock이 우리 검증 규칙과 충돌한다는 문제가 드러났고, Claude가 추천을 (다)로 바꿨다.
4. 사용자가 (다)를 택했다. 번거롭더라도 역할 분리가 확실하다는 이유였다.

## 남은 사항

- 시연용 Mock의 데이터 생성 범위(숙소 수, 객실 타입 수)는 구현할 때 정한다.
