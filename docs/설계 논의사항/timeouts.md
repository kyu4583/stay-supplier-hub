# 타임아웃

- 날짜: 2026-09-17
- 상태: 결정

## 논제

연결·응답 타임아웃을 얼마로 두고 그 근거를 무엇으로 삼을 것인가. 호출 하나가 아니라 검색 한 건 전체의 시간 한도를 어떻게 다룰 것인가.

## 결론

| 항목 | 값 | 걸리는 지점 |
|---|---|---|
| 검색 전체 예산 | 3초 | 공급사 호출 조합 전체 |
| 호출별 응답 타임아웃 | 2초 | 요청 전송 후 응답이 끝날 때까지 |
| 연결 타임아웃 | 1초 | 새 연결을 맺을 때만 |
| 커넥션 획득 대기 | 0.5초 | 풀에서 순서를 기다릴 때 ([50개 한도와 수천 개 규모](chunking-and-scale.md)) |

- 전체 예산이 끝나면 남은 호출을 취소하고, 그때까지 모인 결과로 응답한다. 취소된 공급사는 `failedSuppliers`에 들어간다.
- 모두 설정값으로 빼고, README에 측정값이 아니라 사용자 대기 한도에서 역산한 값이라고 적는다. Mock의 지연·무응답 모드로 동작을 확인한다.
- `Retry-After` 헤더는 두지 않는다. 클라이언트 요청을 제한하는 장치를 도입할 때 다시 본다.

## 근거

1. 공급사 응답 실측이 없다. 값의 근거로 삼을 수 있는 것은 검색 화면이 기다릴 수 있는 한도뿐이다. 그래서 전체 예산을 먼저 정하고 나머지를 그 안에서 나눴다.
2. 호출별 타임아웃만으로는 부족하다. 공급사가 무응답이면 묶음마다 2초를 기다리고, 동시 8개로 30묶음을 태우면 8초가 걸린다. 전체 예산이 있어야 부분 실패 허용이 실제로 동작한다.
3. 연결은 정상이면 수십 ms다. 1초를 넘으면 공급사가 느린 것이 아니라 경로 문제로 본다.
4. 커넥션 획득은 아직 요청도 보내지 않은 단계라 길게 기다릴 이유가 없다. 라이브러리 기본값은 대체로 수십 초대라 반드시 낮춰 잡아야 한다.
5. 값의 합(3.5초)이 예산보다 큰 것은 의도한 것이다. 전체 예산이 마지막 방어선이고 나머지는 그보다 빨리 끊는 장치다.
6. `Retry-After`는 클라이언트에게 재시도 시점을 지시하는 헤더다. 공급사 회복 시점을 모르는 상태에서 고정값을 넣으면 근거 없는 값이 클라이언트 동작을 정한다.

## 정정 이력

- "응답 타임아웃 2초면 재시도 1회 여유가 남는다"는 계산이 틀렸다. 2초 타임아웃 뒤 2초를 더 쓰면 예산 3초를 넘는다. 이 값에서는 빠르게 실패한 호출(연결 거부, 즉시 5xx)만 재시도할 수 있다. 타임아웃 난 호출까지 재시도하려면 호출별 값을 1.2~1.5초로 낮춰야 하는데, 느린 공급사를 실패로 모는 일이 늘어난다. 실측이 생기면 두 값을 함께 조정한다.

## 논의 흐름

1. Claude가 값과 근거를 제안했다.
2. 사용자가 단계별 타임아웃이 일반적인 패턴인지 물었다. Claude가 주요 HTTP 클라이언트들이 같은 단계를 각각 설정 손잡이로 두고 있음을 정리하고, 읽기 타임아웃과 응답 타임아웃의 차이, 전체 예산은 클라이언트 설정이 아니라 설계라는 점을 설명했다. 라이브러리 기본값의 구체 숫자는 구현할 때 코드로 확인하기로 했다.
3. 사용자가 제안값 그대로 결정하고, `Retry-After`는 넣지 않기로 했다. 클라이언트 요청을 제한하는 방법을 적용할 때 다시 고려하겠다고 했다.

## 남은 사항

- 실측이 생기면 전체 예산과 호출별 값을 함께 조정한다. 연결 타임아웃은 0.5초 쪽으로 줄이는 것이 자연스럽다.
- 재시도·서킷 브레이커는 선택 범위이라 범위 밖이다. 붙일 때 호출별 값과 예산을 다시 맞춘다.
