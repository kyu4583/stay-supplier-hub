# 구현 범위와 산출물

- 날짜: 2026-09-17
- 상태: 결정

## 논제

무엇을 코드로 구현하고 무엇을 설계 문서로만 둘 것인가. 산출물을 어떻게 나눌 것인가.

## 결론

### 진행 방식 — 결정: 설계·문서를 먼저 커밋하고 브랜치를 둘로 나눈다

1. 설계와 문서만 담은 단계까지 커밋한다.
2. 거기서 브랜치를 나눈다.
   - A: 핵심 흐름만 구현
   - B: 설계한 범위까지 구현
3. 두 브랜치의 결과를 보고 한쪽을 `main`에 병합한다. 브랜치명은 기능 중심으로 짓는다.

### 구현 범위

| 구분 | 항목 |
|---|---|
| 핵심 흐름 (A) | 통합 검색 API, 공급사 A·B 어댑터, 매핑 스키마와 동기화, 타임아웃·부분 실패·실패 판정, 메모리 스냅샷, 시연용 Mock, 테스트 |
| 설계만 또는 B | 연동 지표 계측, 재시도·서킷 브레이커, 요금·재고 캐시, 정규화 실패 격리, 중복 병합(미결), 통화 처리, 예약 대행, 다중 인스턴스 조율 |

- 연동 지표는 Claude가 Micrometer 카운터 몇 개를 심자고 제안했으나, 사용자가 핵심 설계에서 벗어난다고 판단해 이 방식으로 옮겼다. 요구사항에서도 설계만으로 가능하다고 둔 항목이다.
- README에 무엇을 왜 구현했고 무엇을 왜 설계로만 뒀는지 적는다.

### 산출물

| 파일 | 내용 | 작성 주체 |
|---|---|---|
| `README.md` | 빌드·실행 방법, 주요 설계 의사결정과 근거, 가정 목록, 버리는 데이터 목록, 정책값(측정값이 아님을 명시) | 함께 |
| `docs/` | 아키텍처, 통합 모델 설계, API 명세, 신규 공급사 추가 체크리스트, 설계만 한 항목들의 확장 설계 | 함께 |
| `JOURNAL.md` | 날짜별 진행, 의사결정과 폐기한 대안, 막힌 지점 | **사용자만** |
| `docs/ai-usage.md` | 무엇을 물었고 답을 어떻게 수용·수정·거부했는지 | **사용자만** |

- JOURNAL과 AI 활용 기록은 사용자가 직접 가공해서 작성한다. 에이전트가 내용을 채우거나 커밋하지 않는다. AGENTS.md 규칙에도 넣었다.
- AI 활용 기록을 별도 파일로 두는 이유는 요구사항에서 독립된 산출물로 다루기 때문이다.

### API 문서 — 결정: SpringDoc을 넣는다

- 응답 필드에 붙은 계약(예약 가능 수의 비가산성, `failedSuppliers` 항목의 뜻, 0의 뜻, 오류 형식)을 코드 옆 애노테이션에 적어 문서로 뽑는다. 별도 문서에만 적으면 응답이 바뀔 때 갈라진다.
- Swagger UI가 시연 창구가 된다. Mock 서버를 띄우고 브라우저에서 바로 검색을 호출할 수 있다.
- `docs/`의 API 명세는 자동 생성 산출물로 대체하고, 문서에는 설계 의도만 남긴다.
- 애노테이션은 계약에 해당하는 문장만 적고 자명한 필드는 비워 둔다.
- springdoc-openapi 3.x가 Spring Boot 4 대응이다. 버전은 프로젝트 만들 때 확인한다.

## 논의 흐름

1. Claude가 구현 범위 표와 산출물 구조를 제안하고, 연동 지표를 코드로 일부 심자고(핵심 지표 몇 개) 추천했다.
2. 사용자가 계측이 무엇을 뜻하는지 물었고, Claude가 자동 수집되는 것과 손으로 심을 것, 비용과 확인 방법을 설명했다.
3. 사용자가 지표 계측은 핵심 설계에서 벗어난다고 보고, 설계·문서를 먼저 커밋한 뒤 브랜치를 A(핵심 흐름)와 B(설계 범위까지)로 나누는 방식을 택했다.
4. 산출물 구조는 제안대로 가되, JOURNAL과 AI 활용 기록은 사용자가 직접 작성하기로 했다.
5. 기본 브랜치 처리는 두 브랜치의 결과를 보고 한쪽을 `main`에 병합하기로 했다.
6. SpringDoc은 "문서 자동화"보다 필드에 붙은 약속을 코드 옆에 두는 값어치 때문에 넣기로 했다.
