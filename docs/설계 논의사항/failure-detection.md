# 실패 판정

- 날짜: 2026-09-17
- 상태: 결정 (실패 사유 분류는 재시도 정책과 함께 조정)

## 논제

공급사마다 다른 실패 표현(A는 HTTP 상태, B는 200 + 본문 코드, 무응답은 우리 타임아웃)을 어떻게 하나로 모을 것인가. 항목 하나가 규약을 어길 때 어디까지 실패로 볼 것인가. 값 검증을 얼마나 엄격하게 할 것인가.

## 결론

### 판정 단계 (쟁점 아님)

```
1단계  HTTP 상태     A: 2xx가 아니면 실패 / B: 항상 200이라 여기서 성공 판정 금지
2단계  본문 봉투      B: 성공 코드가 아니면 실패, data가 null이면 실패
3단계  항목 검증      날짜·값 규약을 어기는 항목을 걸러낸다
무응답  우리 타임아웃   공급사가 알려주지 않으므로 우리가 판정한다
```

- B가 200 + 성공 코드인데 `data`가 비어 있으면 응답 이상으로 본다.
- A가 2xx인데 본문이 오류 형태면 파싱에서 걸리므로 응답 이상으로 본다.
- 판정 자리는 어댑터 안의 파싱과 변환 사이다 ([공급사 어댑터 계층](supplier-adapter-layer.md)).

### 항목 검증 실패의 범위 — 결정

- 항목 일부가 걸리면 그 항목만 빼고 나머지는 쓴다. 지표와 격리 저장에만 남기고 `failedSuppliers`에는 넣지 않는다. 공급사는 정상 응답했고 데이터 일부가 규약을 어긴 것이다.
- 한 묶음의 항목이 전부 걸리면 그 묶음을 실패로 본다. 그러면 그 공급사가 `failedSuppliers`에 들어간다. 임의의 비율 기준 없이 "쓸 수 있는 것이 없는 응답"을 걸러 낸다.

### 검증 엄격도 — 결정: 보정하지 않고 항목을 뺀다

| 검증 대상 | 처리 |
|---|---|
| 날짜 목록이 요청 숙박일과 다름 | 항목 제외 ([연박 예약 가능 수](stay-availability.md)) |
| 음수 재고 | 항목 제외 |
| 최대 인원이 요청 인원보다 작음 | 항목 제외 |
| 음수·이상 금액, 모르는 통화 코드 | 항목 제외 |
| 같은 키가 두 번 옴 | 둘 다 제외 |
| 요청하지 않은 숙소 코드 | 그 항목 제외 |
| 매핑에 없는 객실 타입 코드 | 항목 제외 + 동기화 트리거 ([숙소 목록 동기화](property-list-sync.md)) |

모두 이상으로 기록해 연동 지표에서 보게 한다.

## 근거

1. 보정은 공급사의 의도를 추측하는 일이다. 날짜 규칙에서 이미 "의도를 알 수 없으면 버린다"를 택했으므로 값 전체에 같은 기준을 적용한다.
2. 항목 단위 문제로 정상 항목까지 버리면 부분 실패를 허용하라는 요구와 반대가 된다.
3. 묶음 전체가 걸리는 경우만 실패로 올리면, 비율 기준 같은 정책값 없이도 사실상 실패한 응답을 구분할 수 있다.
4. 항목 제외를 `failedSuppliers`에 올리지 않는 이유는 그것이 공급사 호출의 실패가 아니라 데이터 품질 문제이기 때문이다. 대신 지표로 드러낸다.

## 논의 흐름

1. Claude가 판정 단계를 정의로 정리하고, 항목 실패의 범위와 검증 엄격도를 쟁점으로 냈다.
2. 사용자가 두 쟁점 모두 제안에 동의했다.

## 남은 사항

- 실패 사유 분류(타임아웃, 공급사 오류, 호출 한도 초과, 인증 실패, 응답 이상 등)는 재시도 정책을 정할 때 맞춘다. 재시도는 선택 범위이라 작업 범위 밖이다.
- 격리 저장(정규화 실패 데이터 보관)은 선택 범위이라 범위 밖이다. 지금은 기록만 남긴다.
