# 50개 한도와 수천 개 규모

- 날짜: 2026-09-17
- 상태: 결정

## 논제

재고·요금 API가 한 번에 숙소 코드 50개까지만 받는다. 이 분할을 어디서 할 것인가. 한 공급사 안에서 묶음 일부만 실패하면 어떻게 다룰 것인가. 동시 호출을 어디서 얼마로 묶을 것인가. 숙소가 수천 개로 늘면 어떻게 감당할 것인가.

## 규모 감각

보유 숙소가 3,000개이고 두 공급사가 절반씩 취급한다고 보면,

```
A: 1,500 ÷ 50 = 30회
B: 1,500 ÷ 50 = 30회
검색 1건 = 60회 호출
동시 검색 100건 = 진행 중 호출 6,000회
```

## 결론

### 분할 위치 — 결정: 어댑터 안

- 호출 쪽은 그 공급사가 취급하는 코드 전부를 넘기고, 50개로 쪼개는 일은 어댑터가 한다.
- 50은 공급사가 정한 한도다. 도메인이 그 숫자를 알면 공급사 지식이 새어 나온다. 새 공급사의 한도가 다르면 그 어댑터만 고친다.

### 묶음 일부 실패 — 결정: 성공한 묶음 결과는 쓰고 그 공급사를 실패 목록에 넣는다

- 30회 중 2회가 실패해도 28회분 결과는 고객에게 보인다. 그 공급사는 `failedSuppliers`에 들어간다.
- [검색 응답 계약](search-response-contract.md)에서 `failedSuppliers` 항목의 뜻을 "이 공급사 결과의 일부 또는 전부가 빠졌다"로 정의해 둔 것이 이 경우다.
- 어댑터 결과 모델을 성공·실패 둘 중 하나에서 둘을 함께 담는 형태로 바꾼다.

```java
record SupplierSearchResult(SupplierId supplier,
                            List<RoomOffer> offers,
                            List<ChunkFailure> failures) { }
// offers가 비고 failures만 있으면 그 공급사는 전부 실패
```

### 동시 호출 제한 — 결정

| 제한 | 내용 | 값 |
|---|---|---|
| 검색 한 건 안에서 공급사별 동시 호출 수 | Reactor 연산자의 동시성 인자 | 8 |
| 공급사별 전역 동시 호출 상한 | 모든 검색 합산. 공급사별 커넥션 풀 상한으로 걸린다 | 설정값 |
| 커넥션 획득 대기 한도 | 풀이 꽉 찼을 때 무한정 기다리지 않는다. 초과하면 그 묶음만 실패로 처리해 부분 실패로 흘린다 | 설정값 |

- 커넥션 풀은 공급사마다 독립으로 둔다. 한 공급사가 느려질 때 그 대기가 다른 공급사 호출용 커넥션을 잠식하지 않는다. [아웃바운드 커넥션 풀 용량](outbound-pool-capacity.md)에 미결이던 "2,500의 적용 단위"가 이것으로 정해진다.

### 수천 개 규모를 감당하는 방법 — 결정 (설계 문서용)

- 처리량이 모자라면 서버 인스턴스를 늘린다. 앞단에 요청 분산 계층을 라운드로빈으로 하나 둔다. 지금 다른 분배 방식이 필요할 이유가 없다.
- 각 서버는 매핑 DB를 빼면 요청-응답 사이클 바깥으로 무상태다. 이를 분명히 하려고, (공급사, 숙소 코드, 객실 타입 코드) 키로 누적되는 이벤트 트리거 대기 상태도 메모리가 아니라 매핑 DB의 테이블에 쓴다.
- 매핑 DB 조회 빈도는 메모리 스냅샷과 긴 동기화 주기 덕분에 매우 낮게 유지된다. 그래서 매핑 DB가 하나여도 당분간 병목이 될 위험은 적다.
- 따라서 인스턴스를 늘린 만큼 감당 가능한 처리량이 늘어난다.
- 인스턴스를 늘릴 때 같이 봐야 할 것 (Claude 보강):

| 항목 | 내용 |
|---|---|
| 동기화 실행 주체 | 주기 동기화를 모든 인스턴스가 돌리면 공급사 전체 목록 호출이 인스턴스 수만큼 늘고 같은 행에 동시에 쓴다. 한 인스턴스만 돌도록 조율이 필요하다 |
| 공급사 쪽 한도 | 우리 처리량은 인스턴스 수만큼 늘지만 공급사 수용량은 그대로다. 동시 호출 상한은 인스턴스 수로 나눠 설정해야 하고, 병목이 우리에서 공급사로 옮겨 간다 |
| 새 인스턴스의 준비 | 기동 시 동기화가 끝나 매핑이 준비되기 전에는 트래픽을 받지 않게 한다. 공급사별 매핑 준비 상태를 그대로 쓸 수 있다 |
| 스냅샷 시점 차이 | 인스턴스마다 스냅샷 교체 시점이 달라 같은 시각에 다른 결과를 볼 수 있다. 차이는 동기화 주기 안으로 한정된다 |
| 대기 상태 테이블 | DB에 두면 인스턴스 간 중복 트리거도 조건부 갱신으로 함께 막을 수 있다. 쓰기는 요청 스레드가 아니라 비동기 트리거 작업에서 한다 |

## 근거

1. 50이라는 값은 공급사 지식이므로 경계 안(어댑터)에 둔다. 공급사마다 다를 수 있다.
2. 묶음 일부가 실패했다고 나머지 결과를 버리면, 부분 실패를 허용하라는 요구와 반대가 된다. 응답 계약이 이미 "일부 또는 전부"를 표현할 수 있게 정의돼 있다.
3. 검색 한 건이 수십 회 호출을 만들기 때문에, 제한이 없으면 검색 몇 건만으로 공급사와 우리 자원이 함께 무너진다.
4. 공급사별 풀 분리는 한 공급사의 지연이 다른 공급사 호출로 번지는 것을 막는다.
5. 규모 대응을 인스턴스 증설로 잡을 수 있는 이유는, 요청 처리에 인스턴스 로컬 상태가 없고 공유 자원인 매핑 DB의 조회 빈도가 낮기 때문이다.

## 논의 흐름

1. Claude가 규모 계산을 보이고 세 쟁점(분할 위치, 묶음 일부 실패, 동시 호출 제한)을 냈다. 분할은 어댑터 안, 묶음 일부 실패는 성공분 사용, 동시성은 세 층으로 제한하고 풀을 공급사별로 분리하자고 추천했다.
2. 사용자가 세 쟁점 모두 이견이 없다고 했다.
3. 사용자가 "수천 개로 늘면 어떻게 할지"에 대한 답으로 인스턴스 증설 계획을 더했다. 각 서버가 매핑 DB를 빼면 무상태라는 점, 이를 분명히 하려고 이벤트 트리거 대기 상태를 DB 테이블에 둔다는 점, 매핑 DB 조회 빈도가 낮아 단일 DB가 아직 병목이 아니라는 점, 앞단에 라운드로빈 분산 계층을 두면 처리량이 인스턴스 수만큼 늘어난다는 점을 들었다.
4. Claude가 받아들이면서 인스턴스를 늘릴 때 같이 봐야 할 다섯 가지(동기화 실행 주체, 공급사 쪽 한도, 새 인스턴스 준비, 스냅샷 시점 차이, 대기 상태 테이블의 쓰기 위치)를 보탰다.

## 남은 사항

- 구현은 단일 인스턴스로 한다. 인스턴스 증설은 설계 문서에 적는 확장 경로다. 실제로 늘릴 때는 위 표의 다섯 가지를 먼저 정해야 한다.
- 동시성 값(검색 내 8, 공급사별 전역 상한, 획득 대기 한도)은 측정값이 아니다. 부하를 보고 조정한다.
- 요금·재고 캐시를 두면 공급사 호출 수가 줄어든다. 캐시 논제에서 함께 본다.
