# 비동기 처리 모델 선택

- 논의 기간: 2026-09-11 ~ 2026-09-16
- 상태: 결정

## 논제

두 공급사의 다수 청크를 병렬 호출하는 검색에서, 요청을 처리하는 실행 모델을 무엇으로 둘 것인가. 비교 대상은 MVC의 플랫폼/가상 스레드와 WebFlux였고, 공급사 호출은 어느 경우에도 WebClient와 Reactor를 사용한다는 전제에서 논의했다.

## 결론

**MVC + 가상 스레드 + WebClient**를 선택한다.

- Tomcat은 가상 스레드로 사용자 요청을 처리한다.
- 공급사 어댑터는 `WebClient`로 호출을 만들고 `Mono`를 반환한다. 어댑터 안에서 `block()`하지 않는다.
- 검색 서비스는 Reactor로 모든 청크를 조합하여 병렬 실행, 호출별 타임아웃·재시도, 부분 실패 처리를 구성한다.
- 조합된 검색 결과만 요청 경계에서 한 번 `block()`한다. 가상 스레드는 공급사 호출을 병렬화하는 수단이 아니라 이 최종 대기를 감당하는 실행 기반이다.
- 아웃바운드 풀은 초기 목표를 약 2,500개로 둔다. 이는 이 실행 모델의 승패 근거가 아니라, 두 최종 후보에 공통으로 둔 별도 용량 가정이다. 적용 단위와 적정성은 아직 검증되지 않았다. 자세한 내용은 [아웃바운드 커넥션 풀 용량](outbound-pool-capacity.md)을 따른다.

WebFlux를 기술적으로 배제한 것은 아니다. 이 검색이 결과를 모아 JSON 하나로 돌려주고, 동기 DB·일반 라이브러리를 자연스럽게 쓰는 이점이 더 구체적이라고 판단하여 선택하지 않았다. 사용자 연결 종료부터 응답 전송까지 하나의 비동기 수명으로 묶는 가치가 커지거나, DB까지 리액티브로 바꾸기로 하면 다시 비교한다.

## 결정 근거

1. 핵심인 공급사 호출 제어는 MVC와 WebFlux의 차이가 아니다. 두 경우 모두 WebClient와 Reactor 연산자로 병렬 호출, 호출별 시간 제한, 재시도, 실패를 값으로 전환하는 처리를 같은 코드로 구성할 수 있다. MVC에서는 완성된 `Mono<SearchResponse>`를 한 번 기다리고, WebFlux에서는 그대로 반환할 뿐이다.
2. 호출 하나마다 기다리는 구조와 요청 전체를 한 번 기다리는 구조는 다르다. 후자에서는 Reactor가 호출들 사이의 동시성, 전체 시간 예산, 취소, 부분 실패 수집을 계속 소유한다. 따라서 가상 스레드와 Reactor가 같은 비동기 제어를 이중으로 구현하지 않는다.
3. 가상 스레드가 켜진 MVC는 외부 응답을 기다리는 동안 플랫폼 워커 200개 같은 고정된 요청 스레드 수에 먼저 묶이지 않는다. 이 작업에는 기존 런타임을 유지해야 하는 제약도 없으므로, 이 장점을 포기할 이유가 약했다.
4. MVC에서는 매핑 DB 접근, 일반 업무 로직, ORM 및 동기 라이브러리를 명령형 코드로 유지할 수 있다. Reactor를 반드시 써야 하는 범위를 공급사 호출 조합으로 국소화할 수 있다.
5. WebFlux의 가장 분명한 추가 가치는 사용자 연결 종료에 맞춘 취소 전파, 요청·응답 I/O의 일관된 비동기 처리, 스트리밍이다. 하지만 현재는 결과를 모두 모아 단일 응답으로 반환하며, 그 이점은 블로킹 코드 격리·리액티브 DB 또는 별도 실행 자원·전 구간의 Reactor 문맥 관리라는 구체적인 비용보다 작다고 보았다.

## 후보를 좁힌 과정

| 후보 | 판단 | 이유 |
|---|---|---|
| MVC(플랫폼) + WebClient, 공급사 호출마다 `block()` | 제외 | 요청마다 플랫폼 스레드에 더해 청크별 작업 스레드/풀을 별도로 관리하게 된다. Reactor가 이미 표현하는 호출 간 동시성 제어에 작업 풀을 중복하고, 풀을 하나로 줄이면 순차 대기가 된다. |
| MVC(가상) + WebClient, 공급사 호출마다 `block()` | 제외 | 가상 스레드 비용은 낮아도 호출 간 제어를 스레드/Future 쪽으로 옮기는 구조다. Reactor 조합을 끝까지 유지하는 요청당 단일 `block()`보다 얻는 것이 없다. |
| MVC(가상) + 동기 HTTP 클라이언트 | 제외 | 동기 방식에도 제한·취소·실패 수집을 만들 수는 있다. 그러나 소켓 타임아웃, 전체 데드라인, 세마포어, 취소와 예외 수집을 맞물리게 하는 책임이 애플리케이션에 남는다. Reactor는 이 제어들을 조합 가능한 연산자로 제공한다. 메모리 점유 차이는 보조 근거로만 보았다. |
| MVC(플랫폼) + WebClient, 요청당 단일 `block()` | 설계 방향에서 제외 | 풀을 충분히 확보한 뒤에는 외부 응답을 기다리는 요청이 플랫폼 워커 상한을 점유할 수 있다. 풀 크기와 요청 스레드는 모두 측정·설정 대상이며, 기본값 비교만으로 어느 쪽이 먼저 포화한다고 단정할 수 없다. 가상 스레드로 이 대기 상한을 낮추는 쪽을 택했다. 실제 첫 병목이라는 측정 결론은 아니다. |
| MVC(가상) + WebClient, 요청당 단일 `block()` | 선택 | 명령형 일반 코드와 Reactor 기반 외부 호출 제어의 경계가 명확하다. |
| WebFlux + WebClient | 선택하지 않음 | 연결 종료 취소, 전면 비동기 수명, 스트리밍은 장점이다. 현재 흐름에서는 그 이득이 MVC의 동기 생태계 호환성과 국소적인 Reactor 사용보다 결정적이지 않았다. |

## 시간순 논의 흐름

### 2026-09-11 — WebClient가 왜 필요한지부터 확인

- 사용자는 WebClient의 배경지식이 없었으므로, 외부 HTTP 호출 도구와 `Mono`/`Flux`·Reactor 연산자의 역할을 먼저 확인했다.
- AI는 WebClient를 요청을 즉시 수행하는 동기 값이 아니라, 나중에 실행·조합할 수 있는 작업으로 설명했다. 사용자는 이를 바탕으로 "여러 호출을 합친 뒤 마지막에 한 번 기다리면 내부 호출들은 동시에 진행되는가"를 물었다.
- 이때 사용자는 다음 이해를 명시적으로 확인했다. 여러 호출을 Reactor 안에서 합친 뒤 한 번 `block()`하면 내부 비동기 로직은 유지된다. 반대로 호출마다 `block()`하면 호출 사이의 병렬 실행과 수집을 개발자가 다시 만들어야 한다. AI는 이 이해를 수용하되, `Flux`는 "묶는 행위"가 아니라 여러 값을 다루는 타입이고 `Mono.zip`·`flatMap` 등이 조합 방식이라는 점을 보완했다.
- 가상 스레드를 공급사 병렬 호출의 주수단으로 쓰면 WebClient를 사실상 동기 클라이언트처럼 쓰게 된다는 초기 우려가 나왔다. 다만 요청 경계에서 최종 결과를 기다리는 가상 스레드까지 같은 문제는 아니라는 구분은 이후 논의로 확정했다.

### 2026-09-13 오전 — `block()`의 위치와 여섯 가지 후보 비교

- 사용자는 "MVC + WebClient인데 공급사 호출 하나마다 가상 스레드를 할당해 `block()`하면, WebClient를 억지로 한 겹 더 얹는 것 아닌가"라고 반박했다.
- AI는 이 반박을 받아들여, **호출마다** `block()`하는 경우에는 가상 스레드/Future와 Reactor의 제어가 겹친다고 설명했다. 그러나 Reactor로 호출들을 먼저 조합하고 **요청당 한 번만** `block()`하는 경우에는, Reactor가 병렬 호출을 맡고 가상 스레드는 최종 대기만 맡으므로 역할이 겹치지 않는다고 구분했다.
- 사용자는 "`block()`하면 타임아웃·재시도·동시 호출 수 제한·부분 실패 수집을 전부 다시 만들어야 한다"는 표현을 실제 코드 수준에서 검증하라고 요구했다. AI는 이 표현이 과장임을 인정했다. 개별 호출 내부에 붙인 타임아웃·재시도는 `block()` 전에도 유지될 수 있다. 다시 구현해야 하는 것은 호출들을 가로지르는 동시성, 전체 데드라인·취소, 부분 실패 수집이다.
- 사용자는 플랫폼/가상 스레드, 사용자 요청당/공급사 호출당 `block()`, 동기 HTTP, WebFlux의 여섯 후보에 대해 요청 수신·외부 호출·대기 중 어떤 스레드가 점유되는지 비교표를 요구했다. 이 표를 토대로 플랫폼 스레드에서 공급사 호출마다 기다리는 후보와 가상 스레드에서 공급사 호출마다 기다리는 후보를 먼저 제외했다.
- 사용자는 동기 HTTP 후보도 따로 검토했다. 공급사별 풀 격리는 다른 클라이언트에도 설정으로 만들 수 있으므로 WebClient만의 구조적 장점이 아니라는 지적을 냈고, AI가 이를 수용해 근거에서 제거했다. 최종적으로 사용자가 수용한 WebClient의 핵심 근거는 기본값이나 이벤트 루프 자체가 아니라, 취소·시간 제한·재시도·동시성·부분 실패를 같은 신호 체계에서 조합하도록 이미 제공한다는 점이었다. 이에 따라 MVC(가상) + 동기 HTTP 후보도 제외했다.

### 2026-09-13 정오~오후 — 플랫폼 스레드와 가상 스레드의 병목 주장을 재검증

- AI는 처음에 작은 기본 아웃바운드 풀을 전제로, 하류 커넥션 풀이 먼저 포화하므로 Tomcat 플랫폼 스레드 200개는 병목이 되기 어렵고 가상 스레드가 불필요하다고 주장했다.
- 사용자는 이 주장에 세 가지 근거를 요구했다. 플랫폼 스레드가 포화되기 전에 커넥션 풀이 반드시 포화한다는 사실, 플랫폼 단계에서 빠르게 거절하는 것이 실제로 다음 단계 부하를 줄인다는 사실, 또는 플랫폼과 가상 스레드의 비용 차이가 충분히 크다는 사실 중 하나가 필요하다고 반박했다. 기본값과 임의의 응답 시간으로는 어느 것도 증명되지 않는다고 지적했다.
- 사용자는 설명할 항목이 늘어난다는 이유는 엔지니어링 근거가 아니라고 제외했고, 기존 런타임 제약이 없으니 최신 LTS를 선택할 수 있다는 점을 들었다. 가상 스레드의 특정 버전 문제를 일반적인 불이익으로 드는 주장도 이 근거만으로는 유지할 수 없다고 보았다. AI는 이 두 근거를 철회했다.
- 사용자는 특히 "실제 병목이 Netty 풀이라면 그 지점이 관측되게 하는 편이 원인 추적에 낫지 않은가"라고 주장했다. AI는 앞단 거절이 항상 나쁜 것은 아니며, 자체 자원·지연 목표를 이유로 한 명시적 수용량 정책은 여전히 필요하다고 반박했다. 다만 관측하지 않은 공급사 429를 미리 가정해 우리 처리량을 낮추는 근거로 쓰는 것은 잘못된 위치의 논거라고 철회했다.
- 사용자가 "비위를 맞추지 말고 반박 근거가 없으면 없다고 하라"고 지적한 뒤, AI는 일부 양보를 다시 번복하며 기본 풀 수치로 플랫폼 스레드가 구조적으로 포화하지 않는다고 주장했다. 이 논증은 다음 세션에서 오류로 판정됐다. 이 변화 자체도 최종 설계 근거로 사용하지 않는다.

### 2026-09-13 오후 — 커넥션, 풀, 스레드를 분리하고 초기 풀 목표를 둠

- 사용자는 인바운드 연결, 아웃바운드 연결, 연결 풀, 이벤트 루프, 요청 스레드를 한 숫자로 비교하는 설명에 문제를 제기했다. 특히 HTTP/1.1의 아웃바운드 연결은 요청 전송부터 응답 수신까지 그 교환에 점유되고, 이벤트 루프 스레드만 이벤트가 있을 때 여러 연결을 번갈아 처리한다는 점을 짚었다.
- Codex는 연결 수·진행 중인 요청 수·스레드 수를 분리해 다시 설명했다. 풀의 최대치 도달은 애플리케이션 정책상의 풀 고갈이고, 소켓·FD·메모리·주소/포트 한도 때문에 새 연결을 만들 수 없는 시스템 자원 고갈과는 다른 문제라고 정리했다.
- 사용자는 RAM과 OS/애플리케이션 한도를 충분히 확보하고 공급사가 수용한다고 가정하면 아웃바운드 풀을 크게 잡아 플랫폼 요청 스레드가 주 병목이 되게 할 수 있는지 확인했다. 답은 조건부로 그렇다였다. 다만 임시 포트, FD, 커널·direct 메모리, NAT/프록시, 실제 지연과 이벤트 루프 처리량은 별도의 한계이므로, 큰 풀 자체가 안전하거나 적정하다는 뜻은 아니다.
- 사용자는 불필요한 과호출은 막되, 관측하지 않은 공급사 429를 두려워해 정상적인 요청 처리량을 미리 낮추지는 않겠다고 주장했다. 이 입장에서 공급사 수용량이 아직 알려지지 않았다는 이유만으로 우리 서버의 가용량을 낮게 잡지 않기로 했고, 아웃바운드 풀의 초기 목표를 약 2,500개로 잡았다. 수천 단위 풀 설정 사례가 있다는 조사 결과는 참고했지만, 2,500개가 실제 운영 적정값이라는 증거로 취급하지 않았다.
- 이 가정 아래 MVC(플랫폼)를 설계 방향에서 제외하고 MVC(가상)와 WebFlux를 최종 비교 대상으로 남겼다. 풀 상한의 적용 단위, 전역 동시성·호출률 정책, 실제 OS 자원 검증은 별도 미결로 분리했다.

### 2026-09-13 오후 — Claude의 전제 오류를 별도 검토하고 MVC/WebFlux 축을 다시 세움

- Codex는 기존의 "기본 연결 16개" 전제가 일반적인 기본 `HttpClient` 생성 경로와 맞지 않는다고 지적했다. 공유 풀의 문서상 기본값과 사용자 정의 `ConnectionProvider`의 기본값을 혼동한 것이며, 어느 숫자든 실제 버전·생성 방식·설정 없이는 이 프로젝트의 사실이 아니다. 최대 풀 크기는 미리 활성 연결을 그 수만큼 여는 뜻도 아니다.
- Codex는 공급사 호출 수나 풀 획득 대기 수를 사용자 검색 수와 동일시한 계산도 성립하지 않는다고 지적했다. DB 대기, 재시도 간격, 병합·응답 전송 등 다른 상태가 있고, 검색 한 건은 여러 공급사·여러 청크 호출을 만들 수 있다.
- 또한 검색 체인마다 `flatMap(call, 8)`을 둔 숫자는 **검색 한 건 안의** 동시성일 뿐, 모든 사용자 요청에 대한 전역 공급사 제한이 아니라는 점을 정리했다. Reactor는 조합 도구를 주지만 전역 수용량 정책까지 자동으로 결정하지 않는다.
- 이 검토 후 비교 축을 커넥션 기본값에서 분리했다. MVC(가상)는 명령형 DB·일반 코드와 Reactor 외부 호출 조합을 경계로 나누는 모델이고, WebFlux는 요청 수신부터 DB·외부 호출·응답까지 하나의 파이프라인으로 잇는 모델이다.
- WebFlux의 장점은 사용자 연결 종료에서 공급사 호출 취소까지 이어지는 경로, non-blocking 응답·스트리밍, 하나의 문맥이라는 점으로 정리됐다. 반면 "WebFlux에서는 JPA를 쓸 수 없다"는 초기 설명은 정정했다. 별도 실행 자원으로 격리하면 사용할 수 있으며, 불가능이 아니라 복잡성과 실행 모델의 비용 문제다. MVC에서도 WebClient 콜백 안에 블로킹 코드를 넣으면 이벤트 루프를 막을 수 있으므로, "MVC의 블로킹은 항상 요청 하나에만 영향"이라는 말도 정정했다.
- 사용자는 이 단계에서 엔지니어링 외적인 관점의 설명을 중단하고 기술 기준만으로 논의할 것을 요청했다. 이후 판단에는 그런 용어를 근거로 쓰지 않았다.

### 2026-09-16 — 공급사 호출 제어의 동등성을 확인하고 최종 선택

- 사용자는 "타임아웃·재시도·병렬 호출 제어가 MVC보다 WebFlux에서 확실히 쉬운가"를 마지막으로 확인했다.
- Codex는 그렇지 않다고 답했다. MVC(가상) + WebClient와 WebFlux + WebClient는 WebClient/Reactor에서 같은 `timeout`, `retryWhen`, `Mono.zip`/`flatMap`, `onErrorResume` 등을 사용한다. MVC의 단일 `block()`은 공급사마다 순차 대기하는 것이 아니라 이미 조합된 전체 작업을 한 번 기다리는 것이다.
- 사용자는 가상 스레드를 켜면 두 모델의 격차가 크게 줄고, WebFlux의 "경계 없는 파이프라인"은 구현의 자연스러움 외에 현재 흐름에서 결정적 기능 이득으로 느껴지지 않는다고 판단했다. 반대로 ORM·다른 동기 라이브러리·블로킹 코드 격리의 비용은 구체적이라고 보았다. 기존 기반이나 JDK 제약이 없어 가상 스레드를 선택할 수 있다는 점도 근거로 들었다.
- 그 판단에 따라 MVC(가상) + WebClient를 최종 선택했다.

## 정정·철회 이력

최종 결론은 아래의 폐기된 설명에 기대지 않는다.

| 초기 주장 또는 표현 | 정정 내용 |
|---|---|
| 기본 아웃바운드 풀이 16개이므로 플랫폼 스레드는 구조적으로 포화하지 않는다 | 16이라는 값은 다른 생성 경로·설정과 혼동한 수치였다. 실제 값은 라이브러리 버전과 `ConnectionProvider` 생성 방식으로 확인해야 하며, 기본값만으로 실행 모델의 병목을 단정할 수 없다. |
| 풀 대기 수와 사용자 검색 수를 같은 단위로 계산할 수 있다 | 검색은 여러 공급사·청크 호출을 만들고 DB·재시도·병합 등 다른 상태가 있으므로 동일시할 수 없다. |
| 호출마다 `block()`하면 호출별 타임아웃·재시도도 전부 사라진다 | 호출 내부에 붙인 연산자는 남을 수 있다. 사라지는 것은 호출 **사이**의 동시성, 전체 데드라인·취소, 부분 실패 수집을 Reactor가 한 체인에서 소유하는 구조다. |
| `flatMap(..., 8)`이면 공급사 전체 동시성이 8로 제한된다 | 요청마다 별도 체인을 만들면 요청마다 8이다. 전역·공급사별 제한은 별도 정책과 구현이 필요하다. |
| WebFlux에서는 JPA를 쓸 수 없다 | 이벤트 루프에서 직접 호출하면 안 되지만 별도 실행 자원으로 격리할 수 있다. 비교해야 할 것은 불가능 여부가 아니라 복잡성과 위험이다. |
| MVC의 블로킹은 언제나 해당 요청에만 영향이 있다 | WebClient의 이벤트 루프 콜백에서 블로킹하면 MVC에서도 다른 외부 호출에 영향을 줄 수 있다. Reactor 구간에는 같은 금지 규칙이 적용된다. |
| TIME_WAIT가 아웃바운드에만 생긴다 | 능동적으로 TCP 연결을 닫는 쪽에 생길 수 있다. 아웃바운드에서 특정 목적지로 연결이 집중될 때의 임시 포트 제약과 구분해야 한다. |

## 남은 위험과 재검토 조건

- 약 2,500개 풀의 실제 적용 범위(목적지별인지 전체인지), OS·프로세스 FD/메모리/포트 한도, 프록시·NAT 조건, 인스턴스 수를 구현 전에 확인한다.
- 가상 스레드를 켠다고 전역 수용량 정책이 사라지지 않는다. 사용자 요청 전체와 공급사별 청크에 대해 어떤 한계를 둘지, 포화 시 어떤 오류·관측 지표를 낼지는 별도로 결정한다.
- `block()`은 요청 경계에만 한 번 둔다. 어댑터 내부 또는 Reactor 콜백에서의 `block()`·JDBC·무거운 변환은 이벤트 루프를 막을 수 있으므로 금지한다.
- 사용자 연결 종료 뒤 불필요한 공급사 호출을 빨리 취소해야 하는 요구가 강해지거나, 결과 스트리밍이 필요해지거나, DB까지 리액티브로 바꾸면 WebFlux를 다시 검토한다.
- 실제 부하에서 활성·유휴 연결, 풀 획득 대기, 호출 지연, 재시도·취소 수, 요청 대기, FD/direct memory·포트 사용량을 관측한 뒤 풀 크기와 동시성 정책을 조정한다. 현재 수치는 성능 검증 결과가 아니다.
