# 검색 응답 계약

- 날짜: 2026-09-17
- 상태: 결정

## 논제

통합 검색 API가 돌려줄 응답의 모양을 어떻게 정할 것인가. 일부 공급사 조회가 실패한 사실을 어떻게 드러낼 것인가. 호출한 공급사가 모두 실패했을 때 어떤 상태 코드를 줄 것인가. 요청을 어떤 규칙으로 검증하고 오류를 어떤 형식으로 돌려줄 것인가.

## 응답 초안

다른 논제에서 정한 것을 모은 것이다. 필드 이름은 임시다.

```json
{
  "properties": [
    {
      "propertyId": "…",
      "propertyName": "Namsan Garden Stay",
      "roomTypes": [
        {
          "roomTypeId": "…",
          "roomTypeName": "Standard Double",
          "maxOccupancy": 2,
          "offers": [
            { "supplier": "…", "breakfastIncluded": false,
              "totalPrice": 283800, "currency": "KRW", "availableRooms": 0 }
          ]
        }
      ]
    }
  ],
  "failedSuppliers": []
}
```

- 구조는 숙소 → 객실 타입 → 오퍼다 ([상품 단위](offer-unit.md)).
- 요금은 세금 포함 기간 총액이고 내부 타입은 `long`이다 ([표준 요금 기준](price-basis.md)).
- `availableRooms`는 그 오퍼로 예약할 수 있는 수이며 오퍼끼리 더할 수 없다. API 문서의 필드 설명에 적는다 ([연박 예약 가능 수](stay-availability.md)).
- 예약 가능 여부 boolean 필드는 초안에서 뺐다. 사용자가 따로 이견을 내지 않으면 이대로 둔다.
- 내부 ID 형식은 매핑 논제, 공급사 값 표현은 신규 공급사 추가 논제에서 정한다.

## 결론

### 부분 실패 표현 — 결정: 실패 공급사 객체 목록

- `failedSuppliers`에 실패한 공급사를 객체로 담는다. 실패가 없으면 빈 배열로 둔다.
- 항목의 뜻은 "이 공급사의 결과 중 일부 또는 전부가 빠졌다"로 정의한다.
- 실패 사유는 응답에 담지 않는다. 로그와 지표로 보낸다.

### 호출한 공급사가 모두 실패했을 때의 상태 코드 — 결정: 503

- 이번 검색에서 실제로 호출한 공급사가 모두 실패하면 503으로 응답한다.
- 매핑된 숙소가 없어 아무 공급사도 호출하지 않았다면 실제로 결과가 없는 것이므로 200 빈 결과다.
- 부분 실패는 200으로 남은 결과를 돌려준다.
- `Retry-After` 헤더를 둘지는 본문 형식과 함께 요청 검증 논의에서 정한다.

### 요청 검증 — 일부 결정

선택지가 갈리지 않는 규칙 (위반하면 400):

- 필수 파라미터(`checkIn`, `checkOut`, `adults`, `children`)가 없거나 날짜 형식이 `YYYY-MM-DD`가 아니다.
- `checkOut`이 `checkIn`보다 뒤가 아니다. 숙박일이 0 이하가 된다.
- `adults`가 1 미만이거나 `children`이 0 미만이다.

과거 날짜 — 결정: 우리가 400으로 막는다.

- 체크인일이 오늘보다 이전이면 공급사를 부르지 않고 400으로 거절한다.
- "오늘"의 기준 시간대는 Asia/Seoul로 고정한다. 원칙적으로는 숙소가 있는 지역의 날짜여야 하지만 공급사가 위치를 주지 않아 알 수 없다. 이 한계는 README에 적는다.

정책 한도 — 결정: 세 가지를 두고 설정값으로 뺀다.

| 한도 | 값 |
|---|---|
| 최대 숙박일수 | 30박 |
| 예약 가능 기간 | 오늘부터 180일 |
| 최대 인원 | 성인+아동 36명 |

- 측정해서 얻은 값이 아니라 널리 쓰이는 숙박 앱의 검색 범위를 참고한 값이다. README에도 그렇게 적는다. 특정 서비스 이름은 쓰지 않는다.
- 36명은 여러 객실을 묶어 파는 검색을 전제한 값으로 보인다. 이 프로젝트는 한 객실 기준이라 그 정도 인원이면 결과가 거의 비지만, 자원 보호를 위한 상한으로서는 문제가 없다.

오류 응답 형식 — 결정: RFC 9457 Problem Details.

- `application/problem+json`으로 오류를 돌려준다. Spring Boot가 기본 제공하는 형식이다.
- 503 본문도 같은 형식으로 두고, 확장 필드에 실패한 공급사 목록을 담는다. 그러면 200 부분 실패와 503이 같은 정보를 같은 이름으로 전달한다.
- `Retry-After` 헤더는 두지 않는다. 클라이언트 요청을 제한하는 장치를 도입할 때 다시 본다 ([타임아웃](timeouts.md)).

## 근거

### 부분 실패 표현

1. 실패 여부만 주면 어느 공급사 결과가 빠졌는지 알 수 없다.
2. 문자열 목록으로 두면 나중에 정보를 붙일 때 문자열을 객체로 바꿔야 해서 쓰는 쪽이 깨진다. 객체 목록이면 필드 추가로 끝난다.
3. 모든 공급사의 상태와 실패 사유를 담으면 인증 실패나 호출 한도 초과 같은 내부 운영 사정이 고객용 API에 드러난다. 사용자에게 불필요하게 많은 정보다.
4. 항목의 뜻을 "일부 또는 전부가 빠졌다"로 두면, 50개 묶음 중 일부만 실패하는 경우도 계약을 바꾸지 않고 담을 수 있다.

### 과거 날짜를 우리가 막는 것

1. 클라이언트 요청 형식은 명확히 정의할 수 있다. 거기서 어긋난 요청이 "사용자는 정상적으로 썼는데 이상한 요청이 나간" 경우일 가능성은 매우 낮다. 서버가 존중할 정상 요청이 아니다.
2. 공급사에 그대로 넘기면, 공급사가 400을 줬을 때 우리 쪽에서는 "호출한 공급사가 모두 실패"가 되어 503을 내게 된다. 클라이언트 잘못이 서버 장애로 보인다.
3. 팔 수 없는 요청에 공급사 호출 한도를 쓰지 않는다.
4. 시간대는 통용되는 기준인 Asia/Seoul로 고정할 수 있다.

### 오류 응답 형식

1. 표준 형식이라 API 문서와 클라이언트 처리에 그대로 쓸 수 있고, 프레임워크가 기본 제공한다.
2. 확장 필드가 있어 503 본문에 실패 공급사 목록을 담을 수 있다. 자체 형식을 쓰면 같은 정보를 두 가지 이름으로 두게 된다.
3. 비용은 필드 이름이 낯설 수 있다는 점이다.

### 정책 한도

1. 한도가 없으면 요청 하나가 만드는 부하에 상한이 없다. 긴 기간 검색은 숙소마다 날짜 항목을 그만큼 만든다.
2. 지금 정답을 알 수 있는 값이 아니다. 그래서 널리 쓰이는 숙박 앱의 검색 범위를 대표값으로 인용했다. 남의 판단에 의존한 것이 아니라, 근거를 댈 수 없는 값에 참고 기준을 쓴 것이다.
3. 설정값으로 빼 두면 실제 사용 데이터를 본 뒤 조정할 수 있다.
4. 비용은 드물게 정당한 요청(장기 투숙 등)이 거절되는 것이다.

### 전체 실패 시 503

1. 결과가 비었을 때 그것이 "조건에 맞는 숙소가 없음"인지 "검색 자체를 못 함"인지 구분되지 않으면, 고객에게도 운영에도 틀린 정보가 된다.
2. 5xx 비율을 보는 모니터링에 장애가 잡힌다. 200으로 내보내면 장애가 HTTP 수준에서 보이지 않는다.
3. 200 빈 결과는 받는 쪽이 정상 결과로 저장하거나 캐시할 수 있다.
4. 비용은 쓰는 쪽 처리가 두 갈래가 되는 것과, 5xx를 자동 재시도하는 클라이언트가 장애 중인 공급사에 부하를 더할 수 있다는 점이다. 후자는 `Retry-After`로 완화한다.

## 검토한 선택지 (부분 실패 표현)

| 방식 | 판단 |
|---|---|
| (가) 여부만 (`partial: true`) | 제외. 근거 1 |
| (나) 실패 공급사 문자열 목록 | 제외. 근거 2 |
| (다) 실패 공급사 객체 목록 | 선택 |
| (라) 모든 공급사의 상태와 사유 | 제외. 근거 3 |

## 논의 흐름

1. Claude가 지금까지의 결정을 모아 응답 초안을 보이고, 부분 실패 표현과 전체 실패 시 상태 코드를 쟁점으로 냈다.
2. 부분 실패 표현에서 (가)~(라)를 비교해 (다)를 추천했다. 근거는 어느 공급사가 빠졌는지 알 수 있어야 한다는 점, 나중에 필드를 더해도 쓰는 쪽이 깨지지 않는다는 점, 실패 사유는 응답이 아니라 지표로 보내야 한다는 점이었다.
3. 사용자가 (다)에 동의했다. (라)는 사용자에게 불필요하게 많은 정보를 노출한다는 이유를 들었다.
4. 전체 실패 시 상태 코드에서 Claude가 200과 503을 비교해 503을 추천했다. 사용자가 이견의 여지 없이 503이 맞고, 아무 공급사도 호출하지 않은 경우를 200 빈 결과로 두는 것도 맞다고 했다.
5. 요청 검증에서 Claude가 선택지가 갈리지 않는 규칙을 먼저 정리하고, 과거 날짜·정책 한도·오류 응답 형식을 쟁점으로 냈다.
6. 과거 날짜는 사용자가 400으로 막기로 했다. 요청 형식은 명확히 정의될 수 있고, 거기 어긋나는 요청이 "사용자는 정상적으로 썼는데 이상한 요청이 나간" 경우일 가능성은 매우 낮으므로 서버가 존중할 정상 요청이 아니며, 시간대도 통용되는 기준인 Asia/Seoul로 고정할 수 있다는 이유였다.
7. 정책 한도는 사용자가 30박, 180일, 36명으로 정했다. 잘 쓰이는 숙박 앱의 검색 범위를 인용한 것이며, 남의 판단에 기댄 것이 아니라 지금으로선 정답을 알 수 없는 값이라 대표값을 가져왔다고 밝혔다. Claude는 36명이 여러 객실을 묶는 검색을 전제한 값으로 보이며, 한 객실 기준인 이 프로젝트에서는 그 인원이면 결과가 거의 빈다는 점을 덧붙였다.
8. 오류 응답 형식은 사용자가 Problem Details로 정했고, `Retry-After` 결정은 장애 처리 방식을 논의한 뒤로 미루기로 했다.

## 남은 사항
- 오류 응답 형식. 503 본문 형식과 `Retry-After` 여부도 함께 정한다.
- 예약 가능 여부 boolean 필드를 두지 않는 초안에 대한 확인
