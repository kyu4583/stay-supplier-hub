# 공급사 어댑터 계층

- 날짜: 2026-09-12, 갱신 2026-09-16, 2026-09-17 (두 차례)
- 상태: 결정

## 논제

공급사 A·B, 이후 N개로 늘어날 공급사의 서로 다른 요청·응답 형식을 호출 쪽에서 어떻게 감출 것인가. 그리고 통일 형식에 담기지 않는 공급사 데이터를 어떻게 다룰 것인가.

## 결론

- 호출 쪽은 공통 요청·응답 형식만 본다. 공급사별 요청 변환, 응답 변환, 실패 매핑은 공급사마다 하나씩 두는 어댑터 안에 둔다. 공급사를 추가할 때는 어댑터와 설정만 추가하고 호출 쪽은 고치지 않는다.
- 공통 타입과 인터페이스는 호출하는 쪽(도메인) 패키지가 소유하고, 어댑터가 그걸 구현한다. 도메인 패키지는 어댑터 패키지를 import하지 않는다.
- 어댑터의 출력은 성공·실패를 담는 결과 객체로 감싼다. A의 HTTP 오류, B의 HTTP 200 + 오류 코드, 타임아웃이 모두 같은 실패 형식으로 나온다.
- 어댑터는 결과를 `Mono`로 반환한다. 호출 조합과 제어를 Reactor에 유지하고, 어댑터 내부에서 block하지 않는다. MVC 요청 경계의 가상 스레드에서 조합한 최종 결과를 한 번 기다린다. [실행 모델 결정](async-model-choice.md)에 따른다.
- 어댑터는 공통 형식으로 옮기는 데까지만 한다. 예약 가능 객실 수 계산, 예약 불가 상품 제외 같은 판단은 호출 쪽에서 한 번만 한다. 그래서 통일 형식에는 날짜별 재고를 그대로 담는다. 요금은 [표준 요금 기준](price-basis.md)에 따라 기간 총액으로 옮긴다.
- "통일 형식 밖 추가 데이터" 칸은 두지 않는다. 대신 README에 통일 형식에서 버리는 데이터 목록과, 필요해지면 되살리는 네 가지 경로를 적는다.

### 어댑터 내부 구조 (2026-09-17 추가)

어댑터 안에서 응답 처리를 세 단계로 나누고, 파싱과 변환 사이의 중간 상태를 공급사별 응답 객체로 정형화한다.

```
HTTP 응답
  → [파싱] 공급사 응답 객체   스펙 그대로, 로직 없음
  → [판정] 성공/실패          A: HTTP 상태 / B: resultCode (세부는 실패 판정 논제)
  → [변환] 매퍼 → 공통 형식    검증·합산·버리기가 전부 여기
```

```
supplier/a/
  SupplierAAdapter        public. 도메인 인터페이스 구현. 호출 → 판정 → 매퍼
  SupplierAMapper         package-private. 순수 함수
  AAvailabilityResponse…  package-private record
```

- 공급사 응답 객체는 스펙을 그대로 옮긴 형태로만 둔다.
  - 검증·계산을 넣지 않는다. 생성 시 검증하면 파싱 실패와 변환 실패가 다시 섞인다.
  - 버리는 필드도 스펙에 있으면 선언한다. 무엇을 버리는지가 응답 객체와 매퍼 사이의 차이로 코드에 드러나고, README의 버리는 데이터 목록과 대조할 수 있다.
- 공급사 응답 객체는 어댑터 패키지 밖으로 나가지 않는다. 어댑터·매퍼·응답 객체를 한 패키지에 두고 응답 객체를 package-private으로 해서, 도메인이 이를 쓰면 컴파일되지 않게 한다.
- 매퍼는 HTTP와 Reactor를 모른다. 입력은 공급사 응답 객체와 검색 조건, 출력은 공통 형식이다.
- 경계를 지키는 기준은 "패키지 경계를 넘는 타입이 누구 것이냐"다. 도메인 소유 타입만 넘으면, 기존 어댑터를 넓히든 새 public 클래스를 두든 경계가 지켜진다. 공급사 타입이 넘으면 어느 쪽이든 샌다.

결과 모델 (2026-09-17 변경): 성공과 실패 중 하나를 고르는 초안에서, 한 결과에 둘을 함께 담는 형태로 바꿨다. 50개 분할을 어댑터가 맡으므로 한 공급사 호출에서 일부 묶음만 실패할 수 있기 때문이다. [50개 한도와 수천 개 규모](chunking-and-scale.md)에 따른다.

```java
record SupplierSearchResult(SupplierId supplier,
                            List<RoomOffer> offers,
                            List<ChunkFailure> failures) { }
// offers가 비고 failures만 있으면 그 공급사는 전부 실패

enum FailureReason { TIMEOUT, SUPPLIER_ERROR, RATE_LIMITED, AUTH_FAILED, BAD_REQUEST, INVALID_RESPONSE }
```

## 근거

1. 스펙이 요구하는 두 가지, 즉 공급사 형식이 도메인으로 새지 않는 경계와 신규 공급사 추가 시의 수정 범위 설명을 이 구조가 직접 만족한다.
2. 실패 형식이 공급사마다 다르면 호출 쪽이 공급사를 구분해야 한다. 그래서 실패도 통일 형식의 일부여야 한다.
3. 판단 규칙을 어댑터에 두면 공급사 수만큼 같은 규칙이 복제된다.
4. 추가 데이터 칸을 두지 않는 이유:
   - 칸에 담기는 건 정의상 공급사마다 다른 데이터라서, 읽는 코드는 공급사 형식을 알아야 한다. 이 칸이 우회하는 대상이 계층의 경계 자체다. 어느 공급사에서 왔는지는 알아도 되지만 공급사별 형식은 몰라야 한다.
   - 공급사마다 내용이 달라 `Map<String, Object>`나 `JsonNode` 같은 타입 없는 칸이 되기 쉽다. 공급사 형식에 의존하는 코드가 생겨도 컴파일러가 잡지 못한다.
   - 결과 객체는 실패 정보 때문에 어차피 생기므로, 필요해지면 필드 하나만 추가하면 된다. [인원 필터 결정](occupancy-prefilter.md)에서 세운 기준, 즉 "요구되지 않은 요소는 정당성이 낮고 나중에 쉽게 추가할 수 있으면 그때 넣는다"와 같다.
5. 공급사 응답 객체를 중간 단계로 두는 이유:
   - 파싱은 공급사 구조가 바뀌어도 반드시 필요한 단계다. 파싱 결과를 회색지대로 두지 않고 타입으로 고정하면, 공급사 고유 형태에서 공통 형태로 갈 때 무엇이 바뀌는지를 매퍼 하나 안에서 확인할 수 있다.
   - 파싱 실패(응답 전체가 깨짐)와 변환 실패(항목 하나의 값이 맞지 않음)를 구분할 자리가 생긴다. 실패 판정과 정규화 실패 격리가 이 구분에 기댄다.
   - B의 `resultCode` 판정은 파싱 뒤, 변환 전에만 할 수 있다. "HTTP 상태로 1차 판정, 본문으로 2차 판정"하는 구조가 들어갈 자리가 된다.
   - 매퍼가 순수 함수라 A 합산, 날짜 누락 같은 변환 규칙을 HTTP 없이 단위 테스트할 수 있다.
   - 공급사 값이 이미 타입으로 파싱돼 있어서, 되살리는 경로를 택할 때 매퍼만 고치면 된다.

## 버려지는 데이터를 되살리는 경로

| 필요해지는 이유 | 경로 | 새 public 계층 | 호출 쪽이 공급사 형식을 알게 되나 |
|---|---|---|---|
| 같은 검색 응답 안의 값을 도메인이 쓰고 싶어짐 (예: A의 세금 내역, 1박 요금) | 통일 형식에 선택 필드로 추가. 기존 매퍼가 한 번의 변환에서 채움. 값을 줄 수 있는 공급사만 채움 | 없음 | 아니오. 값이 있는지만 확인 |
| 도메인은 해석하지 않고 나중에 같은 공급사에 돌려줘야 함 (예: 예약 API가 요구하는 토큰. 현재 공급사에는 없음) | 어댑터만 해석하는 불투명한 값으로 들고 다님 | 없음 | 아니오. 들고 다니기만 함 |
| 분석·감사·재처리 | 원본 응답 보관, 변환 실패 데이터 격리. 반환값이 아니라 저장소로 보냄 | 없음 | 아니오 |
| 공급사의 다른 기능·API를 도메인이 쓰고 싶어짐 (예: 예약, 일부 공급사만 주는 상세 조회) | 도메인이 새 포트 인터페이스를 정의하고, 공급사 패키지의 새 public 클래스가 구현. 내부에서 매퍼 사용. 반환은 도메인 소유 타입 | 있음 | 아니오 |

- 첫 번째 경우를 별도 public 계층으로 풀지 않는 이유: 공급사 응답 객체는 호출 순간 어댑터 안에서만 생긴다. 같은 응답의 값을 별도 계층이 매퍼로 꺼내려면 공급사를 다시 부르거나 응답 객체를 쌓아 두고 나눠야 한다. 매퍼가 한 번에 채우는 것보다 비싸다.
- 선택 필드를 호출부가 선택적으로 얻는 방식은 두 가지다.
  - 같은 응답에 든 값처럼 채우는 비용이 거의 없으면, 매퍼가 항상 채우고 호출부는 필요할 때 읽는다.
  - 추가 API 호출처럼 채우는 데 비용이 들면, 호출부가 도메인 소유 요청 타입에 옵션을 실어 어댑터가 그때만 가져오게 한다.
  - 어느 경우든 호출부는 값의 유무만 보고, 공급사 식별자로 분기해 값을 해석하지 않는다.

추가 데이터 칸 하나에 이 용도들을 섞어 담으면, 누군가 첫 번째 용도로 읽기 시작하는 순간 경계가 샌다.

## 논의 흐름

1. 사용자가 설계를 제안했다.
   - 공급사 요청·응답을 공통 형식으로 가공하는 계층을 두고, 호출 쪽은 공급사 형식이 원래 같았던 것처럼 인지하게 한다. 요청도 마찬가지다. 공급사는 몇 개든 늘어날 수 있어야 한다.
   - 계층의 출력은 통일된 응답(메인)과 통일 형식을 벗어난 추가 데이터를 함께 감싼 객체로 한다. 추가 데이터 칸은 당장 채우지도 읽지도 않고, "통일 형식 밖 데이터는 항상 버려지는 구조"를 우회할 확장 여지로 남긴다.
2. Claude가 검토했다.
   - 공통 형식과 어댑터 구조, 결과를 객체로 감싸는 것은 수용했다.
   - 보강할 점 세 가지를 냈다: 통일 형식을 도메인 쪽이 소유하기, 실패를 결과 객체에 담기, 변환과 판단 나누기.
   - 추가 데이터 칸에는 반대했다(근거 4). 감싸는 객체의 두 번째 칸은 추가 데이터가 아니라 실패 정보로 채우자고 했다.
   - 추가 데이터 칸이 막으려던 문제(버려지는 데이터) 자체는 실제 문제라고 인정했다. 필요해지는 이유를 셋으로 나누고 이유별로 경계를 지키는 경로를 제시했다.
   - 그래도 자리를 남기고 싶다면 도메인이 읽을 수 없는 불투명한 값으로 한정하자는 대안도 냈다.
3. 사용자가 제안을 받아들였다. 추가 데이터 칸은 두지 않는다.
4. 2026-09-16 사용자가 MVC(VT on) + WebClient를 선택했다. 이에 따라 보류했던 어댑터의 Mono 반환과 요청 경계의 단일 block 구조를 확정했다. 결과 객체의 구체적인 필드와 청크별 부분 실패 표현은 별도 미결 사항으로 유지한다.
5. 2026-09-17 요금 기준을 정한 뒤, 사용자가 어댑터 내부 구조를 제안했다.
   - 공급사 응답 파싱은 구조가 바뀌어도 필수이니, 파싱 후 공통 형식으로 바꾸기까지의 중간 상태를 회색지대로 두지 말고 "공급사 X의 응답 객체"로 정형화한 뒤 공통 형식으로 변환하는 경계를 두자.
   - 그러면 공급사 고유 형태에서 공통 형태로 갈 때 필요한 변화를 좁은 경계 안에서 확인할 수 있고, 특정 공급사의 값을 별도로 써야 하는 요구가 생겨도 확장하기 쉽다.
6. Claude가 수용했다.
   - 사용자 논거 외에 이점 세 가지를 더했다: 파싱 실패와 변환 실패의 구분, B `resultCode` 판정이 들어갈 자리, HTTP 없는 매퍼 단위 테스트.
   - 조건 세 가지를 붙였다: 응답 객체는 스펙을 그대로 옮기고 로직을 넣지 않는다, 응답 객체는 패키지 밖으로 나가지 않는다, 매퍼는 순수 함수다.
   - 확장성 주장은 "되살리는 비용이 줄어든다"는 뜻으로만 동의했다. 공급사 응답 객체를 공통 응답 옆에 실어 내보내는 뜻이라면 전에 뺀 추가 데이터 칸이 타입만 붙어 돌아오는 것이라 반대한다고 했다.
   - 사용자가 앞의 뜻이 맞다고 확인했다.
7. 사용자가 "별도로 쓰는 경로가 생기면 `SupplierAMapper`를 호출하는 새 public 계층이 생기는 형태일 것"이라고 제안했다.
   - Claude가 일부만 동의했다. 공급사의 다른 기능·API를 쓰는 경우에는 맞지만, 같은 검색 응답 안의 값은 공급사 재호출이나 응답 객체 보관이 필요해 기존 매퍼를 넓히는 쪽이 맞다고 했다.
   - 기준을 "새 public 계층을 두느냐"에서 "패키지 경계를 넘는 타입이 누구 것이냐"로 옮기자고 했다.
   - 사용자가 "공통 응답을 반환할 때 호출부가 선택적으로 추가 값을 얻을 수 있다"는 뜻인지 확인하고 동의했다. Claude는 선택 필드를 항상 채우는 방식과, 비용이 들 때 요청 옵션으로 채우는 방식 두 가지로 정리했다.

## 남은 위험과 미결 사항

- 50개 분할은 어댑터 안에서 하고, 묶음 일부 실패는 결과 모델이 성공분과 실패 목록을 함께 담아 표현한다 ([50개 한도와 수천 개 규모](chunking-and-scale.md)). 실패 사유의 구체 목록은 재시도 정책을 정할 때 함께 조정한다.
- 변환 실패를 항목 단위로 처리할지(해당 항목만 제외·기록) 공급사 응답 전체 실패로 볼지는 실패 판정 논제에서 정한다.
- 통일 형식의 구체적인 필드는 [표준 요금 기준](price-basis.md)과 [상품 단위](offer-unit.md)에서 정했다.
- Jackson이 package-private record를 역직렬화할 수 있는지 구현할 때 확인한다. 안 되면 응답 객체를 패키지 밖으로 내보내지 않는 규칙을 다른 방법으로 지켜야 한다.
- package-private은 공급사 응답 객체가 새는 것만 막는다. 도메인이 public 어댑터 클래스를 직접 import하는 것은 ArchUnit 테스트로 막기로 했다 ([신규 공급사 추가 범위](supplier-registration.md)).
- 통일 형식 밖 데이터가 필요해지면, 위 네 경로 중 어느 것에 해당하는지부터 판단한다.
