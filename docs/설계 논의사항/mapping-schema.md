# 매핑 스키마와 내부 식별자

- 날짜: 2026-09-17
- 상태: 결정 (비활성으로 보는 시점은 숙소 목록 동기화 논제로 넘김)

## 논제

공급사 코드와 자사 내부 식별자의 매핑을 어떤 스키마로 저장할 것인가. 내부 식별자를 무엇으로 만들 것인가. 공급사 목록에서 사라진 숙소를 어떻게 다룰 것인가.

## 결론

### 스키마 (쟁점 아님)

```
property
  id                     PK
  supplier               공급사
  supplier_property_code 공급사의 숙소 코드
  name                   숙소명
  unique (supplier, supplier_property_code)

room_type
  id                      PK
  property_id             FK → property.id
  supplier_room_type_code 공급사의 객실 타입 코드
  name                    객실 타입명
  max_occupancy           최대 인원
  unique (property_id, supplier_room_type_code)
```

- 공급사마다 내부 식별자가 따로인 기본 동작을 따른다. 중복 병합은 미결이라 병합용 테이블은 두지 않는다.
- 객실 타입 코드는 숙소 안에서만 유일하므로 `(property_id, 코드)` 유니크 제약이 (공급사, 숙소 코드, 객실 타입 코드) 세 값을 표현한다.
- 이 유니크 제약이 "같은 공급사 상품은 항상 같은 내부 ID"를 보장하는 장치다. 동기화는 이 키로 upsert하고, 동시에 두 번 들어와도 제약이 중복을 막는다.
- 이름과 최대 인원을 함께 저장하는 이유는 [상품 단위](offer-unit.md) 쟁점 2의 덮어쓰기에서 기본값으로 쓰기 때문이다.
- 상태 칼럼(`active` 등)과 마지막으로 목록에서 확인한 시각을 둔다. 아래 결정에 따른다.

### 내부 식별자 — 결정: DB 시퀀스 숫자

### 공급사 목록에서 사라진 숙소 — 결정: 행을 지우지 않고 비활성으로 표시

- 검색 대상에서만 빼고 행은 남긴다. 다시 나타나면 같은 내부 ID를 그대로 쓴다.
- 언제 비활성으로 볼지는 숙소 목록 동기화 논제에서 정한다.

## 근거

### 내부 식별자

1. "같은 상품은 항상 같은 ID"는 유니크 제약과 upsert가 보장하므로, 식별자 값 자체가 결정적일 필요가 없다.
2. 공급사 코드로 만든 결정적 해시는 코드가 바뀌면 ID도 바뀐다. 코드 공간이 좁아 추측될 여지도 있다.
3. 공급사 코드를 조합한 문자열은 사실상 공급사 코드를 그대로 노출하는 것이라, 자사 식별자를 주라는 요구와 어긋난다.
4. UUID는 노출 관점에서 낫지만, 인덱스가 커지고 무작위 값은 정렬이 흩어진다. 숫자 ID로 전체 숙소 수와 증가 속도가 드러나는 위험보다 얻는 것이 적다고 봤다.

### 사라진 숙소를 지우지 않는 이유

1. 행을 지우면 같은 숙소가 다시 등록될 때 새 ID가 부여되어 "항상 같은 ID" 약속이 깨진다.
2. 공급사 목록 조회가 실패했을 때 전체를 비활성으로 만드는 사고를 막기 쉽다.
3. 비용은 쓰지 않는 행이 쌓이는 것이다.

## 검토한 선택지 (내부 식별자)

| 방식 | 판단 |
|---|---|
| (가) DB 시퀀스 숫자 | 선택 |
| (나) UUID | 제외. 근거 4 |
| (다) 공급사 코드로 만든 결정적 해시 | 제외. 근거 2 |
| (라) 코드 조합 문자열 (`A:A-10023`) | 제외. 근거 3 |

## 논의 흐름

1. Claude가 스키마 초안을 보이고, 내부 식별자 방식과 사라진 숙소 처리 두 가지를 쟁점으로 냈다.
2. 사용자가 내부 식별자는 (가)에 동의하며 이견 여지가 적다고 했고, 사라진 숙소는 비활성 표시를 택했다.

## 남은 사항

- 언제 비활성으로 볼지(한 번 안 보이면 바로인지, 연속으로 안 보일 때인지)는 숙소 목록 동기화 논제에서 정한다.
- 병합용 테이블이나 칼럼은 [중복 상품 병합](duplicate-merge.md)이 정해진 뒤에 다시 본다.
- DB 종류(H2/PostgreSQL/MySQL)는 스택 논제에서 정한다.
