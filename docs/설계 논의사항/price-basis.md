# 표준 요금 기준

- 날짜: 2026-09-17
- 상태: 결정

## 논제

두 공급사의 요금 표현을 흡수할 표준 요금을 무엇으로 둘 것인가. A는 날짜별 세전 요금과 세금을 따로 주고, B는 세금 포함 기간 총액만 준다. A에만 있는 날짜별 요금과 세금 내역을 검색 응답에 살릴 것인가.

## 결론

- 표준 요금은 숙박 기간 전체의 세금 포함 총액과 통화로 둔다.
  - A: 숙박일마다 `nightlyRate + taxAmount`를 구해 모두 더한다.
  - B: `totalPrice`를 그대로 쓴다.
- A의 날짜별 요금과 세금 내역은 응답에 담지 않는다. README의 "버리는 데이터" 목록에 올린다.
- 1박 평균 요금은 응답에 넣지 않는다.

## 근거

1. 두 공급사에서 같은 뜻으로 정확히 얻을 수 있는 금액이 이것 하나다. B의 총액은 날짜별 요금이나 세금액으로 나눌 수 없어서, 세전 금액을 기준으로 삼으면 B에서 계산할 수 없다.
2. A 내역을 선택 필드로 살리면 필드 모양은 같아도 공급사에 따라 값이 빈다. 같은 객실인데 A 상품만 세금이 따로 보이는 식으로 공급사 차이가 고객에게 드러난다.
3. 버린 내역은 필요해지면 통일 형식에 선택 필드를 추가하는 경로로 되살릴 수 있다([공급사 어댑터 계층](supplier-adapter-layer.md)). 인원 필터 논의에서 세운 "나중에 쉽게 추가할 수 있으면 그때 넣는다"는 기준과 같다.
4. 1박 평균은 실제 날짜별 요금과 다른 값이다. 서버가 정수 반올림 규칙을 정해야 하고, 평균에 박수를 곱해도 총액과 맞지 않는다. 클라이언트가 총액과 박수로 직접 계산할 수 있다.

## 검토한 선택지

| 선택지 | 판단 |
|---|---|
| 세금 포함 총액 + 통화 | 선택 |
| 총액 + A 전용 선택 필드(날짜별 요금, 세금액) | 제외. 근거 2 |
| 총액 + 1박 평균 | 제외. 근거 4 |
| 세전 금액 기준 | 제외. B에서 계산할 수 없음 |

## 논의 흐름

1. Claude가 네 선택지를 비교해 "총액 + 통화"를 추천했다. 쟁점을 "무엇을 기준으로 삼을지"에서 "A에만 있는 내역을 살릴지"로 좁혔다.
2. 사용자가 추천을 받아들였다.
3. 이어서 사용자가 공급사 응답을 공급사별 응답 객체로 먼저 정형화하고, 그 객체를 공통 형식으로 변환하도록 경계를 두자고 제안했다. 어댑터 내부 구조에 관한 제안이라 [공급사 어댑터 계층](supplier-adapter-layer.md)에서 이어서 다룬다.
4. Claude가 세부 사항으로 금액 타입(`long`)과 net의 해석(공급사 금액을 판매가로 보고 마진·수수료는 다루지 않음)을 제안했다. 사용자가 두 가지 모두 제안대로 받아들였다.

## 세부 사항

| 항목 | 내용 | 상태 |
|---|---|---|
| A 합산의 전제 | `dailyRates`가 요청한 숙박일을 모두 채울 때만 더한다. 날짜 하나가 빠진 채 더하면 오류 없이 실제보다 싼 가격이 나간다 | 결정. 날짜 목록이 요청 숙박일과 정확히 같지 않으면 항목을 변환 실패로 뺀다 ([연박 예약 가능 수](stay-availability.md)) |
| 금액 타입 | 내부는 `long`으로 둔다. KRW는 `int`로 충분하지만, IDR처럼 최소 단위 금액이 큰 통화를 연박으로 합산하면 `int` 범위를 넘을 수 있다 | 결정 |
| net의 뜻 | 업계에서 net은 마진을 붙이기 전 도매가를 뜻하기도 하지만, 이 스펙에서는 세금 별도라는 뜻으로 쓴다. 공급사 금액을 고객 판매가로 보고 마진·수수료 구조는 다루지 않는다고 README에 적는다 | 결정 |

## 남은 위험과 재검토 조건

- 고객 화면에 1박 요금이나 세금 내역을 보여줘야 한다는 요구가 생기면 다시 본다. A만 줄 수 있는 값이라, 공급사에 따라 표시가 달라지는 것을 받아들일지부터 정해야 한다.
- 조식처럼 요금에 딸린 조건이 달라 총액을 그대로 비교할 수 없는 문제는 상품 단위 논제에서 다룬다.
- 서로 다른 통화의 총액을 함께 보일 때의 처리는 통화 처리 논제에서 다룬다.
