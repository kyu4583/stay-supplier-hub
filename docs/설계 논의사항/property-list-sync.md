# 숙소 목록 동기화

- 날짜: 2026-09-17
- 상태: 결정

## 논제

매핑을 만드는 공급사 숙소 목록 API를 언제 호출할 것인가. 동기화가 실패하면 검색이 어떻게 응답할 것인가. 목록에서 사라진 숙소를 언제 비활성으로 볼 것인가. 검색이 매핑을 어떻게 읽을 것인가.

## 결론

### 호출 시점 — 결정: 네 가지를 조합한다

| 계기 | 내용 |
|---|---|
| 기동 시 1회 | 매핑이 없는 상태로 검색을 받지 않기 위해 |
| 주기적 | 6시간. 설정값으로 빼고 측정값이 아님을 밝힌다 |
| 수동 트리거 | 공급사가 숙소 추가를 알려왔을 때 주기를 기다리지 않기 위한 관리용 엔드포인트나 커맨드 |
| 이벤트 트리거 | 매핑에 없는 객실 타입 코드가 재고 응답에 올 때 ([상품 단위](offer-unit.md)) |

- 검색할 때마다 호출하는 방식은 제외했다. 검색이 느려지고 공급사 호출 한도를 쓰며, 정적 데이터를 매번 받는 것이라 이 항목이 요구하는 성격 차이 반영과 정반대다.

### 트리거 실행 규칙 — 결정

- 어느 계기든 검색 응답이 동기화를 기다리지 않게 요청과 분리해 실행한다.
- 이미 동기화가 진행 중일 때:

| 계기 | 동작 |
|---|---|
| 주기 | 건너뛴다 |
| 수동 | 끝난 뒤 한 번 더 돈다. 신호가 여러 번 와도 예약은 한 번으로 합친다 |
| 이벤트 | 수동과 같다. 단 아래 코드별 대기 규칙에 걸리면 돌지 않는다 |

- 수동·이벤트 트리거는 "매핑을 갱신해야 한다"는 강한 신호이므로 최근에 돌았다는 이유로 건너뛰지 않는다. 진행 중인 동기화는 신호가 오기 전에 목록을 받아 왔을 수 있으므로, 그것을 기다려 결과로 삼지 않고 한 번 더 돈다.
- 이벤트 트리거의 코드별 대기 규칙: 어떤 코드 때문에 동기화를 돌렸는데도 그 코드가 목록에 없으면, 같은 코드로는 3분 → 10분 → 30분 → 90분 → 270분 뒤에만 다시 돌리고, 그 다음부터는 이벤트로는 돌리지 않는다. 단계가 올라갈 때마다 이상으로 기록한다.
  - 대기 상태의 키는 (공급사, 숙소 코드, 객실 타입 코드)다. 코드가 목록에 들어와 매핑이 생기면 대기 상태를 지운다.
  - 마지막 단계에서 이벤트 트리거를 멈춰도 주기 동기화는 계속 돌므로, 공급사가 나중에 목록을 고치면 그때 매핑에 들어온다.
  - 여러 코드가 동시에 신호를 내도 실행은 공급사 단위로 합쳐 한 번 돈다. 대기 판단만 코드별로 한다.
  - 대기 상태가 무한히 쌓이지 않도록 마지막 단계에 이른 항목은 일정 시간 뒤 정리한다.
- 단일 인스턴스를 전제한다. README의 가정 목록에 적는다.

### 인스턴스가 여러 개일 때의 조율 — 결정: 설계 문서에만 둔다 (구현은 단일 인스턴스)

동기화를 어느 인스턴스가 돌릴지 DB로 조율한다. 사용자 제안이며, Claude가 붙인 보강을 포함한다.

- **동기화 시도 테이블**: 어떤 공급사를 언제 동기화하려 했는지와 반영 여부를 남긴다. 주기 동기화와 기동 시 동기화는 이 테이블을 보고 실행 여부를 정한다.
- **유기된 시도 회수**: 반영 여부가 false인 채 시도 시각이 20분 넘게 지난 행은, 그 시도를 하던 인스턴스가 죽었거나 오류를 낸 것으로 본다. 이를 발견한 인스턴스가 그 시도를 정리하고 자기가 동기화한다.
- **공급사 요청(수동) 트리거**: 요청을 받은 즉시 DB 갱신으로 잇지 않고 요청 기록 테이블에 시도 시각과 완료 여부를 남긴다. 다른 인스턴스는 1분 주기로 이 요청이 끝났는지 확인하고, 끝나지 않았으면 이어받는다. 공급사 요청을 오래 방치할 수 없기 때문에 주기가 짧다.
- **이벤트 트리거**: 위 테이블이 아니라 코드별 누적 대기 테이블을 기준으로 동작한다.
- Claude 보강:
  - 점유는 원자적인 한 문장으로 한다. 조건을 붙인 갱신이나 유니크 제약이 걸린 삽입으로 하고, "지우고 다시 넣기"로 나누지 않는다. 나누면 두 인스턴스가 동시에 점유할 수 있다.
  - 실패했을 때 행을 지우지 말고 실패로 마감한다. 그래야 실패 이력이 남는다. 그러면 "진행 중"은 완료 표시가 없는 행이고, 20분이 지난 그런 행이 유기된 시도다.
  - 느렸을 뿐 살아 있는 인스턴스가 20분 뒤에 커밋할 수 있다. 커밋 전에 자기 시도가 여전히 소유자인지 확인해서, 인수인계된 뒤의 결과가 덮어쓰지 않게 한다.
  - 테이블은 잠금용(공급사당 한 행)과 이력용으로 나누는 편이 낫다. "진행 중인 시도는 공급사당 하나"를 부분 유니크 인덱스로 거는 방법은 DB마다 지원이 다르다.
  - 공급사 요청은 기록한 인스턴스가 곧바로 시도하고, 1분 주기 확인은 인수인계 경로로 쓴다. 그래야 정상 경로에서 최대 1분을 기다리지 않는다.
  - 20분과 1분은 정책값이다. 동기화가 실제로 걸리는 시간보다 충분히 길어야 한다.

### 동기화 중 들어온 검색 — 결정: 갱신 전 상태를 읽고 기다리지 않는다

- 매핑 갱신 중에 검색 요청이 오면 갱신이 끝나기를 기다리지 않고, 갱신 시작 전 상태를 보고 처리한다.
- 이를 보장하는 방법 (Claude 보강):
  - 한 공급사의 동기화(추가·수정·비활성 표시)를 **한 트랜잭션에서 커밋**한다. 그래야 읽는 쪽이 갱신 전이나 후만 보고 중간 상태를 보지 않는다. 행마다 따로 커밋하면 어떤 격리 수준을 써도 중간 상태가 보인다.
  - 검색은 매핑을 한 번의 조회로 읽는다. 검색 경로에서 잠금 읽기(`SELECT … FOR UPDATE`)를 쓰지 않는다.
  - 관계형 DB의 기본 동작(MVCC)에서 읽는 쪽은 쓰는 쪽을 기다리지 않는다. 격리 수준은 "기다리지 않음"보다 "무엇을 보는가"를 정한다.
  - 매핑 캐시를 두기로 하면 검색은 교체 가능한 스냅샷을 읽게 되어 이 요구가 구조적으로 해결된다.

### 동기화 실패 시 검색 응답 — 결정: 매핑 준비 상태를 둔다

- 공급사마다 매핑 준비 상태를 둔다. 한 번이라도 동기화에 성공해 유효한 매핑이 있으면 준비됨이다.
- 준비되지 않은 공급사는 검색에서 `failedSuppliers`에 넣는다. 호출도 못 한 것이니 결과가 빠진 것이 맞다.
- 준비된 공급사가 하나도 없으면 503이다. [검색 응답 계약](search-response-contract.md)의 "호출한 공급사가 모두 실패"와 같은 취급이다.
- 기동 시 동기화가 실패해도 앱은 뜬다. 이전에 저장된 매핑이 있으면 그대로 쓴다.
- 주기 동기화가 실패하면 이전 매핑을 유지한다. 공급사 하나만 실패하면 그 공급사만 이전 상태로 둔다.

### 비활성 판단 시점 — 결정: 이번 목록에 없으면 즉시, 단 급감 가드를 둔다

- 동기화에 성공한 목록에 없는 숙소·객실 타입은 바로 비활성으로 표시한다. 목록 API는 조건 없이 전체를 주므로, 성공한 응답에 없다면 공급사가 더는 취급하지 않는 것이다.
- 목록이 비었거나 이전보다 크게 줄었으면(제안값 30% 이상 감소) 그 동기화를 반영하지 않고 이상으로 기록한다. 공급사 쪽 부분 장애로 대량 비활성되는 사고를 막기 위한 것이다. 30%는 근거를 댈 수 없는 정책값이라 설정으로 뺀다.

### 매핑 조회 방식 — 결정: 메모리 스냅샷을 동기화 후 교체

- 검색은 메모리에 올린 매핑 스냅샷을 읽는다. 동기화가 커밋된 뒤 스냅샷을 통째로 교체한다.
- TTL은 두지 않는다. 매핑이 바뀌는 시점이 동기화뿐이므로 TTL은 근거 없는 지연만 만든다.
- 검색이 불변 스냅샷을 읽으므로 "갱신 전 상태를 보고 기다리지 않는다"가 구조적으로 보장된다.
- 수천 개 규모에서는 메모리 부담이 작다. 수십만 규모가 되면 다시 본다.

## 근거

### 호출 시점

1. 숙소 목록은 자주 바뀌지 않고 재고·요금은 매번 바뀐다. 그 차이를 반영하는 것이 이 항목의 핵심이라, 정적 데이터는 미리 받아 두고 검색은 재고·요금만 호출한다.
2. 한 번의 호출이 공급사별 전체 목록이라 주기가 잦으면 낭비다.
3. 6시간은 보수적인 값이지만, 이벤트 트리거가 "새 상품이 뜰 때까지 기다리는" 최악의 경우를 크게 줄여 준다. 사용자가 이 점을 들어 6시간을 받아들였다.

### 코드별 대기 시간을 늘려 가는 이유

1. 공급사의 두 API가 어긋나면(재고 응답에는 있는 코드가 목록 API에 없으면) 코드별 대기가 없을 때 검색마다 전체 목록을 받아오게 된다.
2. 고정된 대기 시간 하나로 두면 두 위험 중 하나를 고르게 된다. 짧으면 과호출, 길면 공급사가 잠깐 늦게 반영한 경우에 우리 갱신도 그만큼 늦어진다.
3. 3분에서 시작해 늘려 가면 "잠깐 늦은 반영"은 앞쪽 단계에서 따라잡고, 계속 어긋나는 경우는 호출이 빠르게 줄어든다.
4. 마지막에 이벤트로는 돌리지 않더라도 주기 동기화가 계속 돌기 때문에, 공급사가 나중에 목록을 고치면 그때 매핑에 들어온다.

### 동기화 중 검색이 갱신 전 상태를 보는 것

1. 응답이 빠르면서 UX를 크게 해치지 않는다. 사용자 요청 시점에 숙소가 추가되는 빈도가 낮고, 갱신 직전에 요청한 극소수만 새 숙소를 놓친다.
2. 특정 시각에 열리는 숙소를 노리는 사용자라도 뜰 때까지 재요청한다. 매핑 갱신은 수십 초 이상 걸리는 작업이 아니므로 몇 번의 재요청 안에 보이고, 심리적으로 허용 가능한 오차 범위다.
3. 갱신 전 상태를 보는 기간은 동기화가 걸리는 시간뿐이라, 주기(6시간)로 생기는 지연에 비하면 작다.

### 동기화 실패와 비활성 판단

1. 매핑이 빈 이유가 동기화 실패라면 그것은 "결과 없음"이 아니라 "검색을 못 한 것"이다. 준비 상태를 두지 않으면 장애가 빈 결과로 보인다.
2. 사라진 숙소를 즉시 비활성으로 하지 않으면, 공급사가 더는 취급하지 않는 숙소를 계속 재고 조회 대상에 넣게 된다.
3. 반대로 무조건 즉시 반영하면 공급사의 부분 장애나 목록 API 결함 한 번으로 대량 비활성이 일어난다. 급감 가드가 그 사고만 걸러 낸다.

## 논의 흐름

1. Claude가 호출 시점의 선택지를 비교하고 네 가지 조합(기동 시·주기적·수동·이벤트)을 추천했다. 주기는 6시간을 제안했다.
2. 사용자가 동의했다. 기동 시 1회와 수동 트리거는 당연하고, 6시간은 꽤 보수적이지만 이벤트 트리거가 그 보수성을 상당히 덮는다고 봤다.
3. 사용자가 보강했다. 매핑 갱신 중에 요청이 오면 기다리지 않고 갱신 시작 전 스냅샷으로 처리해야 하며, 이를 위해 격리 수준을 정해야 한다고 했다. 근거로 위의 UX 논거를 들었다.
4. Claude가 받아들이면서 보장 방법을 보탰다. 격리 수준만으로는 부족하고, 공급사 단위 동기화를 한 트랜잭션으로 커밋해야 중간 상태가 보이지 않는다. 읽는 쪽이 쓰는 쪽을 기다리지 않는 것은 관계형 DB의 기본 동작이며, 격리 수준이 정하는 것은 무엇을 보는가다. 매핑 캐시를 두면 이 요구가 구조적으로 해결된다는 점도 덧붙였다.
5. Claude가 이벤트 트리거 조건을 확정하자고 하자 사용자가 항목별로 답했다.
   - 수동·이벤트 트리거는 "매핑을 갱신해야 한다"는 강한 신호이므로 건너뛰기의 예외로 둬야 한다.
   - "동기화 후에도 코드가 목록에 없으면"이 무슨 뜻인지 설명을 요구했다.
   - 인스턴스가 여러 개인 것을 지금 고려할 단계인지 물었다.
6. Claude가 답했다.
   - 진행 중인 동기화는 신호 이전에 목록을 받아 왔을 수 있으므로, 기다려 결과로 삼지 말고 끝난 뒤 한 번 더 돌자고 보탰다. 신호가 여러 번 와도 예약은 한 번으로 합친다.
   - 코드별 대기 규칙의 뜻을 예시로 설명했다. 재고 응답에는 있는 코드가 목록 API에 끝내 없으면 검색마다 전체 목록을 받아오게 된다.
   - 다중 인스턴스 고려는 지금 단계가 아니라는 지적을 받아들여 제안에서 뺐다. 단일 인스턴스를 전제로 두고 README에 적기로 했다.
7. 사용자가 코드별 대기 시간을 누적 증가(3분·10분·30분·90분·270분·이후 무시)로 하자고 제안했다. 공급사가 잠깐 늦게 반영한 경우의 지연과 과호출을 함께 줄이기 위해서다. Claude가 받아들이면서 세 가지를 보탰다. 코드가 목록에 들어오면 대기 상태를 지운다. 마지막 단계에서 이벤트 트리거를 멈춰도 주기 동기화가 이어받는다. 여러 코드가 동시에 신호를 내도 실행은 공급사 단위로 합친다.
8. 남은 세 가지(동기화 실패 시 응답, 비활성 판단 시점, 매핑 조회 방식)는 사용자가 Claude 제안에 모두 동의했다. 매핑 조회 방식은 사용자 노트의 "로컬 캐싱"이 뜻한 바와 같다고 확인했다.
9. 인스턴스가 여러 개일 때의 조율을 사용자가 설계했다. 동기화 시도 테이블, 20분 유기 판정과 인수인계, 공급사 요청 기록 테이블과 1분 확인 주기, 이벤트 트리거는 코드별 대기 테이블 기준이라는 구분이다.
10. Claude가 받아들이면서 다섯 가지를 보탰다. 점유는 원자적 한 문장으로 할 것, 실패한 행은 지우지 말고 실패로 마감할 것, 느린 소유자가 나중에 커밋하지 못하게 소유 확인을 걸 것, 잠금용과 이력용 테이블을 나눌 것, 공급사 요청은 받은 인스턴스가 즉시 시도하고 1분 확인은 인수인계 경로로 쓸 것.

## 남은 사항

- 주기(6시간), 급감 가드(30%), 코드별 대기 단계는 모두 측정값이 아닌 정책값이다. 실제 데이터를 보고 조정한다.
- 트랜잭션 크기와 DB 종류에 따른 주의점은 구현할 때 확인한다.
- 매핑 스냅샷 크기는 수십만 규모가 되면 다시 본다.
- 조율 테이블은 설계 문서에만 두기로 했다. 구현은 단일 인스턴스 기준이며 메모리 플래그로 충분하다. 다만 이벤트 트리거의 코드별 대기 상태는 무상태 원칙에 따라 DB 테이블로 둔다.
- 유기 판정 시간(20분), 공급사 요청 확인 주기(1분)는 정책값이다.
