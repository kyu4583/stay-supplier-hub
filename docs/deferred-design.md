# 범위 밖 설계

지금 구현하지 않고 설계만 남긴 것들입니다. 핵심 흐름이 끊김 없이 도는 것을 먼저 두고, 아래는 필요해지는 조건과 그때의 방향만 정해 두었습니다.

## 중복 상품 병합

두 공급사가 같은 숙소를 각자의 코드로 팔 때 하나로 합치는 일입니다. **지금은 합치지 않고 별개의 숙소로 노출합니다.**

합치려면 같은 숙소임을 알아야 하는데, 공급사 사이에 공통 키가 없고 위치 정보도 오지 않습니다. 남는 단서는 숙소명과 객실 구성뿐이라 추정이 됩니다. 이때 실패의 무게가 한쪽으로 치우칩니다.

| 실패 | 고객이 겪는 일 | 무게 |
|---|---|---|
| 같은 숙소를 못 합침 | 같은 숙소가 두 줄로 보임 | 가벼움 |
| 다른 숙소를 잘못 합침 | 보고 고른 것과 다른 숙소가 예약됨 | 무거움 |

이름이 같은 다른 지역의 숙소를 구분할 방법이 없는 상태에서 자동 병합은 아래쪽 실패를 만듭니다. 그래서 합치지 않는 쪽을 택했습니다. "같은 숙소 후보" 같은 약한 표시도 두지 않습니다. 확정할 근거가 없는 상태에서 후보라고 말해도 판단을 고객에게 떠넘기는 것이기 때문입니다.

### 위치 정보를 받을 수 있게 되면

아래는 **공급사가 주소와 좌표를 준다는 전제**의 설계입니다.

1. **저장**: 숙소 목록 동기화가 주소와 좌표를 함께 저장합니다.
2. **후보 추출**: 좌표 근접(예: 반경 150m) + 숙소명 정규화 후 유사도 + 객실 구성 비교로 후보를 뽑습니다. 검색 경로가 아니라 배치로 돕니다.
3. **확정**: 점수가 높은 구간만 자동 확정하고, 중간 구간은 사람이 검토합니다. 검색 중에 추정으로 합치지 않습니다.
4. **연결 저장**: `canonical_property`와 `property.canonical_id`를 둡니다. 객실 타입도 같은 방식으로 잇습니다. 공급사별 내부 식별자는 그대로 두고 연결만 추가하므로 "같은 상품은 항상 같은 식별자"가 유지됩니다.
5. **단계적 병합**: 객실 타입 매칭은 숙소보다 근거가 약합니다(이름과 최대 인원뿐). 확정하지 못하면 숙소만 묶고 객실 타입은 따로 노출합니다.
6. **응답**: 연결이 있으면 한 객실 타입 아래 두 공급사의 오퍼가 배열로 들어갑니다. 지금의 응답 구조가 이미 그 형태라 계약을 바꾸지 않습니다.
7. **재고 표시**: 오퍼 단위 값만 보이고 합계를 만들지 않습니다. 객실 단위 숫자가 필요하면 최솟값을 씁니다. 두 공급사가 같은 재고를 공유하는지 따로 할당받았는지 알 수 없기 때문입니다.
8. **이름**: 병합된 숙소·객실 타입은 우리 쪽 대표 값을 씁니다.
9. **되돌리기**: 잘못된 병합은 연결만 끊습니다. 공급사별 식별자가 그대로라 고객이 본 식별자가 사라지지 않습니다.

### 검토했다 버린 방법

같은 숙소가 의심될 때 한쪽에 예약을 넣고 다른 쪽 재고가 줄어드는지 보는 방법이 있습니다. 쓰지 않습니다. 확인을 위해 실제 예약을 만들어야 하고, 채널마다 재고를 따로 할당한 공급사라면 재고가 줄지 않아 판정 자체가 되지 않으며, 관측하는 사이 다른 고객의 예약이 들어오면 반대로 오판합니다.

## 재시도와 서킷 브레이커

지금은 실패한 호출을 다시 보내지 않습니다. 타임아웃·부분 실패·실패 판정이 먼저 확실히 도는 것을 택했습니다.

- 재시도 대상은 다시 보내면 결과가 달라질 수 있는 실패뿐입니다. 잘못된 요청이나 인증 실패는 다시 보내도 같습니다. 호출 한도 초과는 간격을 두지 않으면 상황을 악화시킵니다.
- 현재 값(호출별 2초, 전체 예산 3초)에서는 빠르게 실패한 호출만 재시도할 여유가 있습니다. 타임아웃 난 호출까지 재시도하려면 호출별 값을 낮춰야 하고, 그러면 느린 공급사를 실패로 모는 일이 늘어납니다. 두 값은 같이 조정해야 합니다.
- 반복해서 실패하는 공급사를 끊는 장치는 그다음입니다. 끊는 기준과 복구 시점을 정해야 하고, 끊긴 동안의 응답은 지금의 "빠진 공급사" 표현을 그대로 씁니다.
- 프레임워크가 재시도와 동시 실행 제한을 기본 제공하므로 외부 라이브러리를 새로 들일 필요는 없습니다.

## 요금·재고 캐시

검색마다 공급사를 부르는 구조라, 같은 조건의 검색이 몰리면 호출이 그대로 늘어납니다. 캐시를 둔다면 정할 것은 셋입니다.

- **유효 기간**: 재고는 빠르게 변합니다. 짧게 잡으면 효과가 작고 길게 잡으면 매진된 방을 팔게 됩니다. 허용할 오차 범위를 먼저 정해야 합니다.
- **몰림 방지**: 인기 조건의 캐시가 동시에 만료되면 그 순간 공급사로 요청이 몰립니다. 같은 키의 재계산은 하나만 돌게 합니다.
- **키**: (공급사, 숙소 코드 묶음, 날짜, 인원)이 키가 됩니다. 인원이 키에 들어가므로 적중률이 생각보다 낮을 수 있습니다.

## 정규화 실패 데이터 격리

지금은 규약을 어긴 항목을 결과에서 빼고 기록만 남깁니다. 격리를 구현한다면, 변환하지 못한 원본을 따로 저장해 나중에 무엇이 왜 실패했는지 분석하고 재처리할 수 있게 합니다. 저장 대상은 공급사 응답 원문과 실패 사유이며, 반환값이 아니라 저장소로 보냅니다. 개인정보가 섞이지 않는 데이터라 보관 자체의 제약은 낮습니다.

## 통화 처리

지금은 공급사가 준 통화를 그대로 노출합니다. 서로 다른 통화의 상품을 한 화면에 나란히 보이면 고객이 비교할 수 없습니다. 환산해서 보여 주려면 기준 통화, 환율의 출처와 갱신 주기, 표시 금액과 결제 금액의 차이를 어떻게 다룰지 정해야 합니다. 환산값을 저장하면 언제 찍은 환율인지도 함께 남겨야 합니다.

## 예약 대행

검색까지만 다룹니다. 예약을 붙이면 공급사에 예약을 만들고 실패 시 보상하는 흐름이 필요합니다.

- 예약 요청은 검색 결과의 오퍼를 가리키는데, 그 사이 재고와 요금이 바뀔 수 있습니다. 예약 시점에 다시 확인하는 단계가 필요합니다.
- 공급사 응답이 없을 때 예약이 생성됐는지 알 수 없습니다. 같은 요청을 안전하게 다시 보낼 수 있는 키와 조회로 확인하는 경로가 필요합니다.
- 어댑터가 예약을 다룬다면 새 포트 인터페이스를 도메인이 정의하고 공급사 패키지가 구현합니다. 검색과 같은 경계 규칙을 씁니다.

## 여러 인스턴스로 늘릴 때

지금은 단일 인스턴스를 전제합니다. 각 서버는 매핑 저장소를 빼면 요청-응답 사이클 바깥으로 상태를 갖지 않으므로, 앞단에 요청 분산 계층을 두고 인스턴스를 늘리면 처리량이 따라 늘어납니다. 다만 아래를 함께 정해야 합니다.

| 항목 | 내용 |
|---|---|
| 동기화 실행 주체 | 모든 인스턴스가 돌리면 전체 목록 호출이 인스턴스 수만큼 늘고 같은 행에 동시에 씁니다. 한 인스턴스만 돌도록 조율이 필요합니다 |
| 공급사 쪽 한도 | 우리 처리량은 늘어도 공급사 수용량은 그대로입니다. 동시 호출 상한을 인스턴스 수로 나눠야 하고, 병목이 공급사로 옮겨 갑니다 |
| 새 인스턴스 준비 | 기동 동기화가 끝나기 전에는 트래픽을 받지 않게 합니다. 공급사별 매핑 준비 상태를 그대로 쓸 수 있습니다 |
| 스냅샷 시점 차이 | 인스턴스마다 교체 시점이 달라 같은 시각에 다른 결과가 나올 수 있습니다. 차이는 동기화 주기 안입니다 |
| 이벤트 대기 상태 | 코드별 대기 상태를 저장소 테이블에 두면 인스턴스 간 중복 트리거도 함께 막힙니다 |

동기화 조율은 저장소를 잠금으로 씁니다.

- 공급사마다 한 행을 두고, 조건을 붙인 갱신 **한 문장**으로 점유합니다. "지우고 다시 넣기"로 나누면 두 인스턴스가 동시에 점유할 수 있습니다.
- 반영되지 않은 채 오래(예: 20분) 지난 시도는 그 인스턴스가 죽은 것으로 보고 다른 인스턴스가 이어받습니다.
- 실패한 시도는 지우지 말고 실패로 마감합니다. 그래야 이력이 남습니다.
- 느렸을 뿐 살아 있던 인스턴스가 나중에 커밋하지 못하도록, 커밋 전에 자기가 아직 소유자인지 확인합니다.
- 수동 계기는 받은 인스턴스가 곧바로 시도하고, 다른 인스턴스의 짧은 주기 확인은 인수인계 경로로 씁니다.

## 연동 지표

기록할 지점은 이미 설계에 들어 있습니다. 계측을 붙인다면 아래가 대상입니다.

| 지표 | 어디서 | 무엇을 보는가 |
|---|---|---|
| 묶음 호출 결과 | 어댑터의 실패 분류 | 공급사별 타임아웃·장애·응답 이상 비율 |
| 검색 부분 실패 | 응답 조립 | 부분 실패로 나간 검색의 비율 |
| 항목 검증 실패 | 항목 검증 | 사유별 발생량. 공급사 데이터 품질 신호 |
| 응답 값과 저장 값의 불일치 | 이름·최대 인원 덮어쓰기 | 동기화가 늦고 있다는 신호 |
| 동기화 결과 | 동기화 완료·실패 | 실패율, 급감 가드 발동 횟수 |
| 이벤트 대기 단계 상승 | 코드별 대기 규칙 | 공급사의 두 API가 어긋난다는 신호 |

공급사 호출의 응답 시간과 상태는 HTTP 클라이언트 계측으로 자동 수집됩니다. 위 표는 그것으로 알 수 없는, 우리가 판정해서 아는 것들입니다. 경보 임계값과 대시보드 구성은 실제 값이 쌓인 뒤에 정할 일입니다.
