# 검색 API

```
GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
```

검색 조건은 날짜와 인원뿐이고, 대상은 보유한 숙소 전체입니다. 지역·키워드 필터와 정렬·페이징은 범위 밖입니다.

## 요청 검증

위반하면 400입니다.

| 규칙 | 이유 |
|---|---|
| 네 파라미터가 모두 있고 날짜는 `YYYY-MM-DD` 형식 | — |
| 체크아웃일이 체크인일보다 뒤 | 숙박일이 0 이하가 됨 |
| 체크인일이 오늘(Asia/Seoul)보다 이르지 않음 | 팔 수 없는 요청 |
| 성인 1명 이상, 아동 0명 이상 | — |
| 숙박 30박 이하 | 요청 하나가 만드는 부하에 상한을 둠 |
| 체크인일이 오늘부터 180일 이내 | 같음 |
| 성인 + 아동 36명 이하 | 같음 |

체크인일이 과거인 요청을 공급사에 그대로 넘기지 않는 이유가 있습니다. 공급사가 그 요청을 거절하면 우리 쪽에서는 "호출한 공급사가 모두 실패"가 되어 **503**을 내게 됩니다. 클라이언트 잘못이 서버 장애로 보이고, 팔 수 없는 요청에 공급사 호출 한도를 씁니다.

"오늘"의 기준 시간대는 Asia/Seoul로 고정합니다. 원칙적으로는 숙소가 있는 지역의 날짜여야 하지만 공급사가 위치 정보를 주지 않아 알 수 없습니다.

## 응답

```json
{
  "properties": [
    {
      "propertyId": "…",
      "propertyName": "Namsan Garden Stay",
      "roomTypes": [
        {
          "roomTypeId": "…",
          "roomTypeName": "Standard Double",
          "maxOccupancy": 2,
          "offers": [
            {
              "supplier": "…",
              "breakfastIncluded": false,
              "totalPrice": 283800,
              "currency": "KRW",
              "availableRooms": 0
            }
          ]
        }
      ]
    }
  ],
  "failedSuppliers": []
}
```

| 필드 | 뜻 |
|---|---|
| `propertyId`, `roomTypeId` | 내부 식별자. 공급사 코드가 아닙니다. 같은 공급사 상품은 언제 조회해도 같은 값으로 돌아옵니다 |
| `maxOccupancy` | 객실 1실의 최대 수용 인원 (성인 + 아동) |
| `totalPrice`, `currency` | 숙박 기간 전체의 세금 포함 총액 |
| `availableRooms` | **그 오퍼로** 요청 기간 전체를 예약할 수 있는 객실 수. 0이면 예약할 수 없습니다. **오퍼끼리 더할 수 없습니다** |
| `supplier` | 그 오퍼가 온 공급사 |
| `failedSuppliers` | 결과의 **일부 또는 전부**가 빠진 공급사. 실패가 없으면 빈 배열입니다 |

### 예약할 수 없는 상품도 담습니다

예약 가능 수가 0인 오퍼를 응답에서 빼지 않습니다.

- 매진된 숙소가 결과에서 통째로 사라지면, 고객은 그것이 매진인지 우리가 취급하지 않는 숙소인지 구분할 수 없습니다.
- 나중에 빼는 쪽으로 바꾸면 0을 거르던 쪽은 그대로 동작하지만, 반대로 바꾸면 "응답에 있으면 예약 가능"이라고 믿던 쪽이 매진 상품에 예약 버튼을 띄웁니다.
- 응답의 0은 언제나 "요청 기간 중 어느 날 실제로 매진"이라는 뜻입니다. 규약을 어긴 데이터는 이미 결과에서 빠지기 때문입니다.

예약 가능 여부를 나타내는 별도 boolean 필드는 두지 않습니다. `availableRooms > 0`과 같은 뜻이고, 필요해지면 필드를 더하는 것으로 충분합니다.

### 부분 실패

일부 공급사 조회가 실패해도 나머지 결과로 응답합니다(200). 빠진 공급사는 `failedSuppliers`에 객체로 담습니다.

- **왜 여부만 두지 않는가**: 어느 공급사 결과가 빠졌는지 알 수 없습니다.
- **왜 문자열 배열이 아닌가**: 나중에 정보를 붙일 때 문자열을 객체로 바꾸면 쓰는 쪽이 깨집니다.
- **왜 실패 사유를 담지 않는가**: 인증 실패나 호출 한도 초과 같은 운영 사정을 고객용 API에 드러낼 이유가 없습니다. 사유는 로그와 지표로 보냅니다.
- 항목의 뜻을 "일부 또는 전부가 빠졌다"로 정의했기 때문에, 한 공급사의 묶음 중 일부만 실패한 경우도 계약을 바꾸지 않고 담을 수 있습니다.

## 상태 코드

| 코드 | 언제 |
|---|---|
| 200 | 결과를 만들었을 때. 조건에 맞는 숙소가 없어 빈 목록인 경우와 일부 공급사가 빠진 경우를 포함합니다 |
| 400 | 요청 검증에 걸렸을 때 |
| 503 | 이번 검색에서 **호출한** 공급사가 모두 실패했을 때 |

매핑된 숙소가 없어 아무 공급사도 호출하지 않았다면 실제로 결과가 없는 것이므로 200 빈 결과입니다. 다만 동기화에 한 번도 성공하지 못해 매핑이 없는 공급사는 호출 대상이 아니라 **실패한 공급사**로 봅니다. 그런 공급사만 있다면 503입니다.

결과가 비었을 때 그것이 "조건에 맞는 숙소가 없음"인지 "검색 자체를 못 함"인지 구분되지 않으면 고객에게도 운영에도 틀린 정보가 됩니다. 200으로 내보내면 장애가 HTTP 수준에서 보이지 않고, 받는 쪽이 빈 결과를 정상 결과로 저장할 수도 있습니다.

`Retry-After` 헤더는 두지 않습니다. 공급사가 언제 회복될지 모르는 상태에서 고정값을 넣으면 근거 없는 값이 클라이언트의 재시도 시점을 정하게 됩니다.

## 오류 응답

`application/problem+json` 형식(RFC 9457)을 씁니다.

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "checkOut must be after checkIn",
  "instance": "/api/v1/stays/search"
}
```

503 본문도 같은 형식으로 두고 확장 필드에 빠진 공급사 목록을 담습니다. 그러면 200 부분 실패와 503이 같은 정보를 같은 이름으로 전달합니다.

## API 문서

SpringDoc으로 OpenAPI 문서를 생성합니다. 위 계약 중 필드에 붙은 약속(예약 가능 수의 비가산성, `failedSuppliers` 항목의 뜻, 0의 뜻)은 필드 설명에 함께 적어, 응답이 바뀔 때 문서가 따로 놀지 않게 합니다.
