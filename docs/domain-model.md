# 도메인 모델

## 단위

| 단위 | 식별 | 담는 것 | 값의 출처 |
|---|---|---|---|
| 숙소 | 내부 숙소 식별자 ← (공급사, 숙소 코드) | 숙소명 | 매핑에 저장된 값을 기본으로, 조회 응답에 값이 있으면 덮어씀 |
| 객실 타입 | 내부 객실 타입 식별자 ← (공급사, 숙소 코드, 객실 타입 코드) | 객실 타입명, 최대 인원 | 같음 |
| 오퍼 | 객실 타입 + 판매 조건 | 조식 포함 여부, 요금, 예약 가능 수, 출처 공급사 | 재고·요금 조회 |

- 객실 타입 코드는 숙소 안에서만 유일합니다. 그래서 객실 타입 하나를 가리키려면 (공급사, 숙소 코드, 객실 타입 코드) 세 값이 필요합니다.
- 공급사가 다르면 내부 식별자도 다릅니다. 같은 숙소를 두 공급사가 팔아도 각각의 식별자로 노출됩니다.
- 오퍼는 저장하지 않습니다. 재고와 요금의 원본은 공급사에 있고 호출할 때마다 달라집니다.

### 객실 타입 아래에 오퍼를 여러 개 둘 수 있게 한 이유

지금 데이터에서는 객실 타입마다 오퍼가 하나입니다. 그런데도 배열로 둔 것은, 같은 객실의 요금제가 여러 개가 되거나 두 공급사의 오퍼를 한 객실 타입 아래 묶게 될 때 **응답 구조를 바꾸지 않기 위해서**입니다. 필드를 더하는 변경은 쓰는 쪽을 깨뜨리지 않지만, 평평한 목록을 중첩으로 바꾸는 변경은 깨뜨립니다.

예약 가능 수는 오퍼마다 붙는 값이고 **오퍼끼리 더할 수 없습니다.** 같은 객실 타입의 오퍼들은 같은 재고를 나눠 쓰는 것일 수도, 공급사마다 따로 할당받은 것일 수도 있는데 우리는 구분할 수 없습니다.

## 요금

표준 요금은 **숙박 기간 전체의 세금 포함 총액과 통화**입니다.

| 공급사 | 만드는 방법 |
|---|---|
| A | 숙박일마다 (1박 요금 + 세금)을 구해 모두 더함 |
| B | 기간 총액을 그대로 사용 |

두 공급사에서 같은 뜻으로 정확히 얻을 수 있는 금액이 이것뿐입니다. 반대 방향은 성립하지 않습니다. B의 총액은 날짜별 요금이나 세금액으로 나눌 수 없어서, 세전 금액을 기준으로 삼으면 B에서 계산할 수 없습니다.

내부 금액은 `long`으로 다룹니다. 통화의 최소 단위 정수라 원화는 `int`로도 충분하지만, 최소 단위 금액이 큰 통화를 여러 박 합산하면 범위를 넘을 수 있습니다.

### 버리는 것과 되살리는 경로

| 버리는 것 | 왜 | 필요해지면 |
|---|---|---|
| A의 날짜별 요금, 세금 내역 | 선택 필드로 살리면 A 상품에만 값이 있어 고객이 공급사 차이를 보게 됨 | 표준 모델에 선택 필드를 더하고 매퍼가 한 번의 변환에서 채움 |
| 1박 평균 요금 | 실제 날짜별 요금과 다른 값이고, 서버가 반올림 규칙을 정해야 하며 평균에 박수를 곱해도 총액과 어긋남 | 쓰는 쪽이 총액과 박수로 계산 |
| B의 세금 포함 표시 | 표준 요금이 언제나 세금 포함이라 값이 고정됨 | — |

값이 필요해지는 이유는 셋으로 나뉘고 경로가 각각 다릅니다. 도메인이 해석해서 쓰려면 표준 모델의 선택 필드로, 나중에 같은 공급사에 돌려주기만 하면 도메인이 읽지 않는 불투명한 값으로, 분석이나 감사 목적이면 반환값이 아니라 저장소로 보냅니다. 세 용도를 한 칸에 섞어 담으면 누군가 첫 번째 용도로 읽는 순간 경계가 새기 때문에, "표준 모델 밖 데이터" 칸은 두지 않습니다.

## 재고와 연박 판정

요청 기간의 숙박일은 체크인일부터 체크아웃 전날까지입니다. 9/1 체크인, 9/4 체크아웃이면 9/1·9/2·9/3 세 날입니다.

**예약 가능 수는 숙박일별 잔여 객실 수의 최솟값**입니다. 방 k개를 기간 내내 쓰려면 매일 k개가 남아 있어야 하므로, 가장 적게 남은 날이 한계입니다.

```
9/1: 3, 9/2: 1, 9/3: 5  →  1
9/1: 2, 9/2: 0, 9/3: 4  →  0 (예약 불가)
```

계산은 어댑터가 아니라 검색 서비스에서 한 번만 합니다. 어댑터는 날짜별 재고를 그대로 표준 모델에 옮기고, 판단은 공급사 수와 무관하게 한 곳에 둡니다.

### 날짜가 맞지 않는 응답

응답의 날짜 목록이 요청한 숙박일 집합과 **정확히 같지 않으면** 그 상품을 변환 실패로 보고 결과에서 뺍니다. 빠진 날짜, 기간 밖 날짜, 중복된 날짜가 모두 해당합니다.

- 빠진 날을 재고 0으로 보면 데이터 결함과 실제 매진이 구분되지 않습니다. A는 요금도 계산할 수 없습니다.
- 있는 날짜만으로 계산하면 재고를 모르는 날이 있는데도 예약 가능으로 보이고, A의 요금은 실제보다 싸게 나갑니다.
- 기간 밖 날짜를 너그럽게 받아도 안 됩니다. 공급사가 기간을 다르게 해석했다면 B의 총액도 그 기준일 수 있는데 우리는 가려낼 수 없습니다.

## 판매 조건

조식 포함 여부는 방의 속성이 아니라 그 가격에 딸린 조건이라, 객실 타입이 아니라 **오퍼**에 둡니다. 같은 객실이라도 공급사마다 값이 다를 수 있습니다.

조식 가격을 알 수 없으므로 조식 여부로 가격을 보정하지 않습니다. 받은 가격을 그대로 두고 조건을 나란히 보여, 고객이 "조식 불포함 429,000원"과 "조식 포함 452,000원"을 조건째 비교하게 합니다.

조건을 객체로 묶지 않고 필드로 둡니다. 환불 규정 같은 조건이 늘어도 필드를 더하는 변경은 쓰는 쪽을 깨뜨리지 않습니다.

## 이름과 최대 인원을 어디서 가져오는가

매핑에 저장된 값으로 채운 뒤, 재고·요금 응답에 같은 값이 있으면 **필드마다 따로 판단해 응답 값으로 덮어씁니다.**

- 공급사는 "이 숙소의 이 객실은 최대 인원이 몇이고 재고가 얼마"를 한 묶음의 사실로 줍니다. 그 안에 지난 동기화 때 저장해 둔 값을 섞어 넣지 않습니다.
- 특히 최대 인원은 공급사가 요청 인원을 수용하는 객실만 고른 기준입니다. 저장된 값만 쓰면 3인 검색 결과에 "최대 2인"이 표시되는 모순이 생길 수 있습니다.
- 재고·요금 응답에서 정적 정보를 빼고 코드만 주는 공급사가 생겨도 같은 규칙으로 동작합니다.

덮어쓴 값은 응답에만 쓰고 저장소에 되쓰지 않습니다. 저장된 값의 갱신은 숙소 목록 동기화가 맡습니다.
