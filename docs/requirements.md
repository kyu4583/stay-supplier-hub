# 요구사항

이 문서는 만들어야 할 것을 정의합니다. 왜 그렇게 만들기로 했는지는 [아키텍처](architecture.md), [도메인 모델](domain-model.md), [검색 API](search-api.md), [공급사 연동](supplier-integration.md)에 있습니다.

## 배경

숙박 플랫폼은 자사에 직접 등록된 숙소 외에 외부 공급사의 상품도 함께 팝니다. 문제는 공급사마다 API가 다르다는 점입니다. 같은 객실을 두고도 어떤 곳은 날짜별 1박 단가를 주고 어떤 곳은 숙박 전체 총액만 줍니다. 세금을 요금에 포함하는 곳도, 따로 주는 곳도 있습니다. 실패를 HTTP 상태 코드로 알리는 곳도, 항상 200을 주면서 본문 코드로만 알리는 곳도 있습니다.

이 차이를 고객에게 그대로 노출할 수는 없습니다. 고객은 어느 공급사에서 온 상품인지와 무관하게 같은 형태의 검색 결과를 봐야 합니다.

## 범위

**포함**

- 여러 공급사의 숙박 상품을 흡수하는 표준 모델
- 공급사 코드와 내부 식별자의 매핑 저장
- 공급사별 연동 어댑터
- 날짜·인원으로 검색하는 통합 검색 API
- 외부 연동 실패를 전제로 한 견고성
- 공급사를 흉내 내는 Mock

**제외**

- 인증·인가, 결제
- 관리자 기능, 프론트엔드
- 지역·키워드 검색 필터. 공급사가 지역 정보를 주지 않으므로 다루지 않습니다. 검색 조건은 날짜와 인원뿐이고 대상은 보유 숙소 전체입니다
- 정렬·페이징

## 기능 요구사항

### 1. 표준 숙박 상품 모델

공급사마다 다른 표현을 흡수하는 자사 표준 모델을 정의합니다. 숙소·객실·요금·재고를 각각 어떤 단위로 잡을지 직접 정합니다. 두 공급사가 주는 정보가 완전히 겹치지 않으므로, 무엇을 표준으로 삼고 무엇을 버릴지 판단하고 근거를 문서에 남깁니다.

### 2. 매핑 저장

공급사가 쓰는 코드와 내부 식별자의 매핑을 관계형 DB에 저장합니다. 요금과 재고의 원본은 외부에 있으므로 쌓지 않습니다.

| 매핑 대상 | 공급사 쪽 키 | 자사 쪽 |
|---|---|---|
| 숙소 | (공급사, 숙소 코드) | 내부 숙소 식별자 |
| 객실 타입 | (공급사, 숙소 코드, 객실 타입 코드) | 내부 객실 타입 식별자 |

- 객실 타입 코드는 해당 숙소 안에서만 유일하므로 매핑 키에 숙소 코드가 함께 들어가야 합니다.
- **같은 공급사 상품이 다시 조회되면 항상 같은 내부 식별자가 나와야 합니다.**
- 공급사가 다르면 내부 식별자도 다를 수 있습니다. 두 공급사의 같은 숙소를 하나로 합치는 것은 선택 사항입니다.
- 매핑은 공급사의 숙소 목록 API로 만듭니다. 언제 호출할지는 직접 정하고 근거를 남깁니다.
- 숙소 목록은 자주 바뀌지 않고 재고·요금은 매번 바뀝니다. 이 성격 차이를 설계에 반영해야 합니다.

### 3. 공급사 연동 어댑터

WebClient로 각 공급사 API를 호출하고 응답을 표준 모델로 변환하는 계층을 둡니다.

- 공급사별 요청·응답 형식이 도메인 계층으로 새어 나가지 않도록 경계를 둡니다.
- 새 공급사를 추가할 때 무엇을 고쳐야 하는지 문서로 설명합니다.

### 4. 통합 검색 API

검색 요청 한 건을 받아 여러 공급사를 병렬 조회하고, 정규화·병합한 결과를 돌려줍니다.

```
GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
```

응답에 최소한 담아야 할 것:

| 항목 | 설명 |
|---|---|
| 내부 숙소 식별자 · 숙소명 | 공급사 코드가 아닌 자사 식별자 |
| 내부 객실 타입 식별자 · 객실 타입명 | 동일 |
| 최대 수용 인원 | 객실 1실 기준 |
| 예약 가능 객실 수 | 요청 기간 전체를 예약할 수 있는 객실 수. 0이면 예약 불가 |
| 출처 공급사 | 어느 공급사에서 온 상품인지 |
| 요금 | 필드 구성은 직접 설계. 무엇을 기준으로 삼을지가 핵심 판단 |
| 부분 실패 사실 | 일부 공급사 조회가 실패했다면 그 사실이 드러나야 함 |

그 밖의 필드 구성과 구조는 자유입니다. 추가로 정할 것:

- 재고·요금 API는 한 번에 숙소 코드를 최대 50개까지 받습니다. 지금 데이터로는 걸리지 않지만 숙소가 수천 개일 때의 처리 방식을 설계에 남깁니다.
- 여러 박을 검색할 때 예약 가능 객실 수를 어떻게 판정할지 정의합니다.
- 예약 불가 상품을 응답에서 뺄지 0으로 노출할지 정하고 근거를 남깁니다.

### 5. 연동 견고성

외부 연동은 실패합니다. 실패를 전제로 설계합니다.

- **병렬 호출**: 여러 공급사를 동시에 조회합니다.
- **타임아웃**: 연결과 응답에 시간 제한을 두고, 값을 그렇게 정한 이유를 설명합니다.
- **부분 실패 허용**: 한 공급사가 응답하지 않아도 나머지 결과로 고객에게 응답할 수 있어야 합니다.
- **실패 판정 통일**: 장애 상황에서도 HTTP 200을 주고 본문 코드로만 실패를 알리는 공급사가 있습니다. 이를 다른 공급사의 4xx·5xx와 같은 실패로 다뤄야 합니다.

재시도 정책과 서킷 브레이커는 선택 사항입니다. 위 네 가지가 먼저입니다.

### 6. Mock 공급사

실제 공급사 서버가 없으므로 아래 스펙대로 흉내 내는 Mock을 구성합니다. 구성 방식은 자유입니다.

재현할 수 있어야 하는 상황은 세 가지입니다. 정상 응답, 공급사 장애, 무응답. 이 셋이 있어야 타임아웃과 부분 실패가 실제로 동작함을 보일 수 있습니다. 응답 지연도 있으면 타임아웃 값을 정할 때 쓸 수 있습니다.

Mock은 본 구현과 같은 포트에 두지 않습니다. 자기 자신을 HTTP로 호출하게 되어 연동 문제로 오해하기 쉬운 실패가 생깁니다.

## 선택 사항

- 재시도 정책 — 무엇을 재시도하고 무엇을 하지 않을지, 백오프를 둘지
- 서킷 브레이커 — 반복 실패하는 공급사를 어떻게 끊고 언제 복구할지
- 요금·재고 캐시 — 유효 기간, 몰림 방지, 원본과의 오차 허용 범위
- 정규화 실패 데이터 격리 — 변환할 수 없는 응답을 버리지 않고 남겨 분석 가능하게
- 중복 상품 병합 — 두 공급사가 같은 숙소를 각자의 코드로 팔 때
- 통화 처리 — 서로 다른 통화의 상품을 함께 노출할 때
- 예약 대행 — 공급사에 예약을 만들고 취소하는 흐름과 실패 시 보상
- 검색 이력·원본 응답 보관
- 연동 지표·모니터링 — 공급사별 성공률, 응답 지연, 타임아웃 비율

## 기술 제약

| 항목 | 내용 |
|---|---|
| 언어 | Java 21 이상 또는 Kotlin. 이 프로젝트는 Java 25를 씁니다 |
| 프레임워크 | Spring Boot 3.4 이상. 이 프로젝트는 4.1.x를 씁니다 |
| 빌드 | Gradle (Kotlin DSL) |
| DB | 관계형 DB 하나 이상. 이 프로젝트는 H2를 씁니다 |
| HTTP 클라이언트 | Spring WebClient. 다수 공급사를 동시에 호출하는 흐름이 핵심이라, 타임아웃·재시도·병렬 호출 제어를 다루기 위해 지정됐습니다 |
| 실행 모델 | WebFlux 전면 도입은 필수가 아닙니다. MVC 위에서 WebClient만 써도 되며, 어떤 방식을 택했든 이유를 문서에 남깁니다 |

## 공급사 연동 규약

두 공급사가 공통으로 지키는 약속입니다.

| 항목 | 규약 |
|---|---|
| 인증 | 요청 헤더 `X-Api-Key: <발급키>` |
| 날짜 형식 | `YYYY-MM-DD` |
| 날짜 경계 | 체크아웃일은 숙박일에 포함되지 않습니다. 9/1 체크인 · 9/4 체크아웃이면 3박입니다 |
| 인원 | 요청은 `adults`와 `children`을 나눠 보냅니다. `maxOccupancy`는 성인 + 아동 합산 기준입니다 |
| 재고 | 날짜별 잔여 객실 수(`remainingRooms`, 정수) |
| 통화 | ISO 4217 코드 (`KRW`, `USD` 등) |
| 금액 | 통화의 최소 단위 정수. 원화는 원 단위이고 소수점이 없습니다 |
| 조식 | `breakfastIncluded` (boolean). 요금에 조식이 포함되는지이며, 같은 객실이라도 공급사마다 다를 수 있습니다 |

### 조회는 두 단계

공급사는 지역으로 재고·요금을 검색해 주지 않습니다.

| 단계 | 성격 |
|---|---|
| ① 숙소 목록 | 공급사가 취급하는 숙소·객실 타입 전체 목록. 조건 파라미터 없음. 요금·재고 없음. 자주 바뀌지 않음 |
| ② 재고·요금 조회 | 숙소 코드 목록을 받아 한 번에 조회. 호출할 때마다 값이 달라짐 |

②는 한 번에 숙소 코드를 최대 50개까지 받고, 넘으면 오류입니다.

### 상품 구조와 식별자

- 두 공급사 모두 상품을 `숙소 > 객실 타입` 2단계로 표현합니다. 101호 같은 개별 물리 객실은 노출되지 않습니다.
- 요금과 재고는 모두 객실 타입 단위입니다. `remainingRooms: 3`은 그 타입의 객실이 그날 3개 남았다는 뜻입니다.
- 공급사는 요청 인원을 수용할 수 있는 객실 타입만 반환합니다(`adults + children <= maxOccupancy`). 인원이 넘쳐 여러 객실을 묶어 파는 경우는 다루지 않습니다.
- 숙소 식별자는 공급사 안에서 유일하고, 객실 타입 식별자는 해당 숙소 안에서만 유일합니다. 따라서 객실 타입 하나를 가리키려면 (공급사, 숙소 코드, 객실 타입 코드) 세 값이 필요합니다.
- 코드 값은 안정적입니다. 같은 상품은 언제 조회해도 같은 코드로 돌아옵니다.
- 두 공급사가 같은 숙소를 취급해도 그 사실을 알려주는 공통 키는 없습니다.

## 공급사 A 계약

특징: 날짜별 1박 단가 · 세금 별도 · HTTP 상태 코드로 실패 표현

### ① 숙소 목록

```
GET /a/v1/hotels
X-Api-Key: {key}
```

```json
{
  "items": [
    {
      "hotelCode": "A-10023",
      "hotelName": "Riverside Hotel Seoul",
      "roomTypes": [
        { "roomTypeCode": "DLX-TWN", "roomTypeName": "Deluxe Twin", "maxOccupancy": 2 }
      ]
    }
  ]
}
```

### ② 재고·요금 조회

```
GET /a/v1/availability?hotelCodes=A-10023,A-10044&checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
X-Api-Key: {key}
```

`hotelCodes`는 쉼표로 구분한 숙소 코드 목록입니다(최대 50개).

```json
{
  "items": [
    {
      "hotelCode": "A-10023",
      "hotelName": "Riverside Hotel Seoul",
      "roomTypeCode": "DLX-TWN",
      "roomTypeName": "Deluxe Twin",
      "maxOccupancy": 2,
      "breakfastIncluded": false,
      "currency": "KRW",
      "dailyRates": [
        { "date": "2026-09-01", "remainingRooms": 3, "nightlyRate": 120000, "taxAmount": 12000 },
        { "date": "2026-09-02", "remainingRooms": 1, "nightlyRate": 150000, "taxAmount": 15000 },
        { "date": "2026-09-03", "remainingRooms": 5, "nightlyRate": 120000, "taxAmount": 12000 }
      ]
    }
  ]
}
```

**요금 규약**: `nightlyRate`는 세금 별도 금액입니다. 그 날짜에 고객이 내는 금액은 `nightlyRate + taxAmount`이고, 숙박 전체 금액은 날짜별 합계입니다.

`dailyRates[].date`는 체크인일부터 체크아웃 전날까지의 숙박일입니다.

### 실패 응답

HTTP 상태 코드와 본문의 `error` 값으로 알립니다.

```json
{ "error": "INVALID_DATE_RANGE", "message": "checkOut must be after checkIn" }
```

| 상태 | error | 의미 |
|---|---|---|
| 400 | `INVALID_DATE_RANGE` / `INVALID_PARAMETER` | 잘못된 요청 |
| 400 | `TOO_MANY_HOTEL_CODES` | 숙소 코드가 50개 초과 |
| 401 | `UNAUTHORIZED` | 인증 실패 |
| 429 | `RATE_LIMIT_EXCEEDED` | 호출 한도 초과 |
| 500 | `INTERNAL_ERROR` | 공급사 내부 오류 |
| 503 | `SERVICE_UNAVAILABLE` | 일시적 장애 |

## 공급사 B 계약

특징: 숙박 전체 총액 · 세금 포함 · 항상 HTTP 200 + 본문 `resultCode`로 실패 표현

### ① 숙소 목록

```
GET /b/api/properties
X-Api-Key: {key}
```

```json
{
  "resultCode": "0000",
  "resultMessage": "SUCCESS",
  "data": {
    "items": [
      {
        "propertyId": "B77120",
        "propertyName": "Riverside Hotel Seoul",
        "rooms": [
          { "roomId": "R-401", "roomName": "Deluxe Twin Room", "maxOccupancy": 2 }
        ]
      }
    ]
  }
}
```

### ② 재고·요금 조회

```
GET /b/api/search?propertyIds=B77120&checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
X-Api-Key: {key}
```

`propertyIds`는 쉼표로 구분한 숙소 코드 목록입니다(최대 50개).

```json
{
  "resultCode": "0000",
  "resultMessage": "SUCCESS",
  "data": {
    "items": [
      {
        "propertyId": "B77120",
        "propertyName": "Riverside Hotel Seoul",
        "roomId": "R-401",
        "roomName": "Deluxe Twin Room",
        "maxOccupancy": 2,
        "breakfastIncluded": true,
        "currency": "KRW",
        "totalPrice": 452000,
        "taxIncluded": true,
        "inventory": [
          { "date": "2026-09-01", "remainingRooms": 3 },
          { "date": "2026-09-02", "remainingRooms": 1 },
          { "date": "2026-09-03", "remainingRooms": 5 }
        ]
      }
    ]
  }
}
```

**요금 규약**: `totalPrice`는 요청한 숙박 기간 전체의 총액이며 세금이 포함돼 있습니다. 날짜별 요금은 제공하지 않고, 세금 금액도 따로 주지 않습니다. `taxIncluded`는 항상 `true`입니다.

`roomId`는 이름과 달리 개별 물리 객실이 아니라 객실 타입입니다. 공급사 A의 `roomTypeCode`에 대응합니다.

### 실패 응답

HTTP는 항상 200이고 본문의 `resultCode`로 알립니다. 실패하면 `data`는 `null`입니다.

```json
{ "resultCode": "E503", "resultMessage": "TEMPORARILY_UNAVAILABLE", "data": null }
```

| resultCode | 의미 |
|---|---|
| `0000` | 성공 |
| `E400` | 잘못된 요청 (숙소 코드 50개 초과 포함) |
| `E401` | 인증 실패 |
| `E429` | 호출 한도 초과 |
| `E500` | 공급사 내부 오류 |
| `E503` | 일시적 장애 |

## 예시 데이터에서 눈여겨볼 점

- A의 `A-10023`과 B의 `B77120`은 같은 숙소·같은 객실 타입입니다. 다만 이를 알려주는 공통 키는 없습니다.
- 같은 3박의 총액이 다릅니다. A는 429,000원, B는 452,000원입니다. 값만 다른 게 아니라 조건이 다릅니다. B는 조식 포함이고 A는 미포함입니다. 단순히 싼 쪽을 고르면 조건이 다른 상품을 비교하게 됩니다.
- `Namsan Garden Stay`는 A에만 있고, `2026-09-02`의 재고가 0입니다.
- 예시 값을 그대로 쓸 필요는 없습니다. 구조만 지키면 됩니다.
